# 推定人手工数の判定

[README](../README.md) に戻る。

「同じ作業を人が AI なしでやったら何時間かかるか」は LLM に推定させます。**判定するのは、あなたが使っている外部の LLM です。このツールは LLM を呼びません**(LLM を呼ぶのは、明示したときの [skill-draft](outputs.md) だけです)。このツールは渡すファイルを作り、返ってきた答えを検証して取り込みます。渡し方は 2 つです。

- **チャットに貼って判定する**: 添付ファイル(指示とパケット数件を 1 ファイルにまとめたもの)を M365 Copilot などのチャットに添付するか貼り付け、返答を貼って取り込みます。M365 Copilot のアプリなら、このツールが画面を操作して送ることもできます(Windows)。
- **ZIP にまとめてエージェントに渡す**: フォルダを読めるエージェントやローカルの LLM に ZIP を渡し、結果を書かせたファイルを取り込みます。

判定するものは 3 つあり、どれも同じ 2 つの渡し方で使えます。

| 判定するもの | 単位 | 結果 | 節 |
|---|---|---|---|
| 工数(推定人手工数と、成果の質・手戻り) | セッション | `out/judgments.json` | 下の 1・2 |
| 依頼ごとの採用(採用・合わなかった点・工程) | 依頼 | `out/turn-judgments.json` | [3](#3-依頼ごとの採用) |
| 管理ツールのタスクへの紐づけ(タスクを設定したときだけ) | セッション | `atlas-notes/task-links.json` | [4](#4-管理ツールのタスクへの紐づけ) |

設定のフォルダ(共有の `AtlasSettings`。[README の「本番の置き方」](../README.md#本番の置き方sessionlog-と-atlassettings))を使って開いたフォルダでは、工数と依頼ごとの判定の結果は `out/` ではなく `AtlasSettings/judgments.json`・`AtlasSettings/turn-judgments.json` に書き、集計する人のあいだで共有します(タスクの紐づけは、設定に `tasks` があるとき `AtlasSettings/task-links.json`)。取り込みは、どの置き場でもファイルのロックの中で読み直して、セッションごと(依頼ごとはセッションと依頼番号ごと)に混ぜて書きます。

結果は次の `atlas export`(画面の「レポートに反映する」「集計し直す」)でレポートに合成されます。

**推定は推定です。** レポートには幅(low〜high)と確信度を一緒に出しますが、人手での実測ではありません。

**合計は、大きな推定の数件で決まることがあります。** AI が数百ファイルを一度に生成したセッションは、成果物の量から数百〜数千時間と推定されやすく、1〜2 件で合計の大半を占めます。そのため次の 3 つをしています。

- 判定の指示(評価軸)で、成果物の量をそのまま工数にしないこと、動くか・使われたかをパケットから確かめられない大量生成は `hours` を確かめられた分に留め(量から見た上限は `high`)、`confidence` を 0.3 以下にして根拠に「大量生成・検証不能」と書くことを求めています。
- **レポートは、確信度が 0.3 以下の推定を合計に入れません。** 件数と時間を別枠で出します(幅・中央値・「推定人手工数 ÷ AI の実働」・モデル別の「人手工数 / AIU」も同じ。セッション一覧と詳細ページには値をそのまま出します)。評価軸を変えて大量生成のセッションを判定し直しても、確信度は 0.3 以下に下がる一方で、時間は数千時間のまま変わらなかったためです(2026-11-14 に 2 セッションで確認)。LLM が出す時間そのものは指示で抑えられないので、確信度を手掛かりにレポートの側で分けています。
- レポートは合計の横に中央値を出し、合計に入れたセッションのうち推定の大きい上位 5% が合計の半分以上を占めるときはその割合を知らせます([screen.md](screen.md) の「AI 投入量 vs 推定人手工数」)。

評価軸を変える前に判定したセッションは、前の基準のままです(確信度が高いまま、合計に入ります)。判定し直すには、そのセッションだけで添付ファイルを作り直して渡します(下の「[範囲を絞る(1 セッション)](#範囲を絞る1-セッション)」)。未判定だけで作った添付(`bundle --unjudged`・画面の「添付ファイルを作る」)には判定済みのセッションが入っていないので、判定し直すのには使えません。

## 1. 評価バンドルを作る(LLM は呼ばない)

```
bin\atlas.exe            # まだなら先に集計(out/sessions.json と out/snapshot を作る)
bin\atlas.exe bundle  # out/bundle/ を作る。--project / --since / --client などで対象を絞れる。--zip で out/bundle.zip も作る
```

`out/bundle/` の中身:

| ファイル | 内容 |
|---|---|
| `INSTRUCTIONS.md` | 判定する LLM への指示(役割・評価軸・出力形式・手順)。最初に読ませる |
| `manifest.json` | パケットの一覧(セッション ID とファイルの場所、件数、サイズ) |
| `schema.json` | 返してもらう `judgments.json` の JSON Schema |
| `sessions/<セッション ID>.md` | 評価パケット。依頼文、最終応答、変更ファイル、ツール / skill / agent / hook、ターン数・時間・トークン、摩擦、指示ファイル・wiki の参照(索引・ページ・wiki の skill・そのほかの呼び出し・書き込みの回数。vault に触れていなければ「参照なし」、vault を指定せずに集計したときは「この集計では数えていません」。どちらも wikiEffect は 0 にするよう指示に書いてある。ページを読んだセッションでは、ページごとの判定の材料(下の「[llm-wiki のページごとの判定](#llm-wiki-のページごとの判定)」))、compaction 要約 |
| `parts/part-<番号>.md` | ZIP やフォルダを渡せない相手(テキストの添付だけの M365 Copilot など)用。指示・JSON Schema と、パケット数件(既定 5 件。`--per-part <n>` で変更)を 1 ファイルにまとめたもの。パケットはファイルごとの乱数の境界で囲み、本文の中の指示に従わないよう指示に書いてある。中身は `sessions/` と同じ |

`--zip` を付けると、`INSTRUCTIONS.md`・`manifest.json`・`schema.json`・`sessions/` を 1 つの ZIP(`out/bundle.zip`。`--bundle <dir>` を指定したときは `<dir>.zip`)にもまとめます。展開すると `bundle` フォルダが 1 つできます。`parts/` は `sessions/` と同じ中身なので入れません。圧縮はしていません(依存を増やさないため。大きさは `sessions/` の合計とほぼ同じです)。ファイルが 65,535 個か全体が 4 GB を超えるときは作らずに止まるので、`--since` や `--unjudged` で絞ってください。依頼ごとの採用(`turns bundle --zip`)とタスクの紐づけ(`tasks bundle --zip`)の ZIP も、同じ決まりで作ります。

- `--zip` を付けずにバンドルを作り直すと(画面の「添付ファイルを作る」も同じ)、前に作った `bundle.zip` は消します。中身が今のバンドルと合わなくなるためです(`turn-bundle.zip`・`task-bundle.zip` も同じ)。
- 依頼の記録が無いセッション(開いただけで使っていないもの)はパケットにしません(`manifest.json` の `skipped` に理由付きで載ります)。含めたいときは `--include-empty`。
- 本文はスナップショットのログから全文を読み直しますが、1 パケット 24,000 字に収まるよう長い本文は中略します(中略した箇所には字数を書きます)。
- パケットにはセッションのモデルの名前と推論強度、推論のトークン数(推論強度とほぼ連動するため)を入れません。レポートはモデルや推論強度で判定を比べるので、判定する LLM が条件を知ったまま質を付けて偏らないようにするためです(依頼の文や応答の本文、文脈圧縮の要約、タスク完了の報告、セッション名など、記録の文にモデルの名前が書かれていれば、それはそのまま入ります。出力のトークン数は、提供元によっては推論の分を含み、推論強度と多少連動します。摩擦指標の「モデル変更」の回数からは、途中でモデルを替えたことが分かります。どちらも作業の規模と摩擦を示す基本の情報なので残しています)。モデルの名前を入れていたころに判定したセッションも、判定済みのまま使えます(判定済みかどうかは、セッション ID だけで決めます)。
- **パケットには依頼文や応答の本文、パス、リポジトリ名がそのまま入ります。** 外部のサービスに渡す前に中身を確認してください。

## 2. 外部の LLM で判定する

### 画面から(おすすめ)

`atlas.bat` から開いた画面の「判定する…」で、判定するものに「工数」、判定の方法に「チャットに貼って判定する」を選びます。相手は M365 Copilot に限りません。ファイルの添付か貼り付けができる LLM なら、同じ手順で使えます(フォルダを読めるエージェントに ZIP で渡すときは、下の「[エージェントやローカルの LLM に渡す](#エージェントやローカルの-llm-に渡す)」)。あとは画面の 4 つの手順に沿って進めます。ターミナルもファイルの置き場所も気にしなくてかまいません。

1. **添付ファイルを作る**: 「未判定 N 件で作る」を押します。判定済みのセッションを除いて、5 件ずつのファイルにまとめます(LLM は呼びません)。作ったあとは「作成済み」と出ます。「作り直す」はファイルの番号が振り直されるので、途中のファイルをダウンロード済みなら押さないでください。作れなかったときは、ボタンの下に「添付ファイルを作れませんでした」と理由(処理が「atlas: 失敗しました: 」に続けて書いた文)、ログ(折りたたみ)が出ます。原因を直してから、もう一度押してください。新しいものは別の場所に作り終えてから入れ替えるので、作り直しに失敗しても、前に作った添付ファイルはそのまま使えます(「作成済み」のまま。返答の取り込みも続けられます)。途中で止めたときは「添付ファイルの作成を止めました」と出ます。この知らせは、ダイアログを閉じるか、次に作れたら消えます(画面を読み込み直した後には出ません)。
2. **チャットに渡す**: 「part-01.txt をダウンロード」を押し、ブラウザの保存先(ふつうは「ダウンロード」フォルダー)に入ったファイルをチャットに添付します。画面の依頼文(「添付したファイルの指示に従って判定し、JSON を返してください。」)を「依頼文をコピー」で写して送ります。添付できないときは「本文をコピー」で中身を貼り付けます。保存は `.txt` にしています。相手が `.md` を受け付けるか分からないためで、中身は `part-01.md` と同じです。
3. **返答を取り込む**: チャットの返答をまるごとコピーして欄に貼り、「取り込む」を押します。返答をファイルに保存してあるとき(エージェントやローカルの LLM に書かせた `.json`、保存した `.md` / `.txt`。5 MB まで)は、欄の下でそのファイルを選ぶと中身が欄に入るので、確かめてから「取り込む」を押します。説明文が混じっていてもかまいません(JSON のコードブロックだけを読みます)。形が合わない項目が 1 件でもあると何も取り込まず、何件目のどのセッションのどの欄が違うかを出します(貼った返答は欄に残ります)。その場合は「直す点をコピー」で一覧を写してチャットに貼り、「この点を直した JSON をもう一度返してください」と頼むか、同じファイルをもう一度判定させてください。取り込むと次のファイルに進みます。
4. **レポートに反映する**: 何ファイルか取り込んだら「レポートに反映する」を押します。レポートの作り直し(`export`)が終わると帯に「再読み込み」が出ます。

「ファイルの一覧」を開くと、どのファイルが取り込み済みかを確かめられ、どのファイルでも保存・コピーできます。

### M365 Copilot のアプリを自動で操作する(Windows)

手順 2〜4 を手でする代わりに、開いている M365 Copilot のアプリをこのツールが操作します(Windows の UI Automation。Windows PowerShell で動きます)。工数・依頼ごとの採用・タスクの紐づけのどれでも使えます。

1. M365 Copilot のアプリを開いてサインインし、チャットの画面を出しておきます(Edge で `m365.cloud.microsoft` を開いた画面も探しますが、確かめたのはアプリだけです)。
2. 「判定する…」→「チャットに貼って判定する」で添付ファイルを作り、手順 2 の「M365 Copilot で自動で判定する」の「M365 Copilot で N ファイルを判定する」を押します。
3. 未判定のファイルを 1 つずつ、新しいチャットで送ります。1 つごとに、モデルの選択で **Think Deeper** を選び(既に選ばれていればそのまま)、依頼文を入れ、「画像とファイルのアップロード」でファイル(`part-01.txt` など)を添付して送り、返答が終わるまで待って、返答の文字を取り込みます。全部終わると、取り込めた分をレポートに反映します(`export`)。

- **終わるまで M365 Copilot の画面に触らないでください。** 1 ファイルに数分かかることがあります(1 ファイルの待ち時間の上限は 900 秒)。
- **ほかのアプリでの作業は続けられます。** 画面の部品を押すと M365 Copilot が前面に出ることがありますが、出たらすぐ、直前に使っていた窓へ戻します(Windows が前面の切り替えを止めて戻せないときは、3 秒ほど試してあきらめ、次に出たときにまた戻します。経過には、前面に出た回ごとに数えて、戻せた回数と戻せなかった回数を出します)。依頼文は、M365 Copilot を一瞬(0.3 秒ほど)前面に出してキー入力で打ちます(UI Automation では、入力欄に文字が残っていると書き換えられないため)。クリップボードは使いません。その間に打った文字が入力欄に混ざったときは、送る前に気づいて消し、打ち直します。
- 途中で画面の操作が崩れたファイル(添付が見つからない、送れない、返答が始まらないなど)は、新しいチャットで 2 回までやり直します。M365 Copilot の画面が見つからないときはやり直しません。
- **M365 Copilot には 1 日の利用上限があります。** 上限に達すると返答が「1 日の上限に達しました」になるので、そこで止まり、残りのファイルは送りません。M365 Copilot に出ている時刻(翌朝)を過ぎてから、もう一度実行すると続きを送ります(「使用量を増やす」は有料なので、このツールは押しません)。Think Deeper で依頼 20 件ほどのファイルを送ったときは、50 ファイルほどで上限に達しました。
- 添付したファイルは、手で添付したときと同じく **OneDrive に入ります**(M365 Copilot の決まり)。
- 返答は `out/bundle/replies/<名前>.md`(依頼ごとの判定は `out/turn-bundle/replies/`、タスクの紐づけは `out/task-bundle/replies/`)に残します。画面から読んだ文字はコードブロックに行番号とボタンの名前が混じるので、`<名前>.md` には ```json のブロックに組み立て直したものを、`<名前>.raw.txt` には読んだままの文字を置きます。形が合わずに取り込めなかった返答は、直して「返答を取り込む」に貼るか `judge import`(`turns import`・`tasks import`)で取り込めます。そのファイルは次の回にもう一度送ります。
- 画面の要素(「新しいチャット」、モデルの選択、「ソースの追加と管理」、送信、返答のコピーのボタンなど)が見つからないときは、やり直しても見つからなければ、何を探していたかを出して止まり、残りのファイルは送りません。M365 Copilot の画面の作りが変わると、この操作は動かなくなります。そのときは手順 2〜4 を手で行ってください。

コマンドでは次のとおりです(`--model` は M365 Copilot のモデルの選択の名前。`Auto` / `Quick Response` / `Think Deeper`。`--limit` は送るファイルの数、`--timeout` は 1 ファイルの待ち時間の秒数)。

```
bin\atlas.exe bundle --unjudged     # 添付ファイルを作る(まだなら)
bin\atlas.exe judge m365            # 未判定のファイルを M365 Copilot で判定して取り込み、レポートに反映する
bin\atlas.exe turns m365 --limit 2  # 依頼ごとの判定(turns bundle --unjudged で作ったもの)を 2 ファイルだけ
bin\atlas.exe tasks m365            # タスクの紐づけ(tasks bundle で作ったもの)
```

### コマンドで

渡し方は、相手が受け取れる形で選びます。

- **テキストの添付だけのとき(M365 Copilot など)**: `out/bundle/parts/` の `part-01.md` を 1 つ添付し、「このファイルの指示に従って判定して」と頼みます。指示・JSON Schema・パケット数件が 1 ファイルに入っているので、ほかのファイルは要りません。返答を保存して取り込んだら、`part-02.md`、`part-03.md` … と続けます。1 ファイルは最大 12 万字ほど(5 件 × 24,000 字)です。途中のセッションの判定が抜けるときは `--per-part 2` などで件数を減らして作り直してください。
- **ZIP を渡せるとき**: 画面の「ZIP にまとめてエージェントに渡す」か `bin\atlas.exe bundle --unjudged --zip` で作った `out/bundle.zip` を添付して「`INSTRUCTIONS.md` に従って判定して」と頼みます。件数が多いときは何回かに分けて返してもらってかまいません。
- **フォルダを読めるエージェントやローカルの LLM に渡すとき**: 下の「[エージェントやローカルの LLM に渡す](#エージェントやローカルの-llm-に渡す)」。

返ってきた JSON(または JSON のコードブロックを含む返答をそのまま貼った `.md` / `.txt`)を保存し、取り込みます。分けて返ってきた分は 1 つずつ取り込めます。

```
bin\atlas.exe judge import 返答.md  # 検証して out/judgments.json に取り込み(同じセッションは上書き)、レポートを作り直す(export)
```

`judge import` は、1 件以上取り込めて集計の結果(`out/sessions.json`)があれば、そのままレポートを作り直します(`export`。`tasks import`・`turns import` と同じです)。形が合わない項目(範囲外の値、必須欄の欠け)が 1 件でもあると、何も取り込まずに、何件目のどのセッションの何が違うかを表示します(作り直しもしません)。合成に素の `build` を使うと、セッション記録(`out/sessions/*.md`)が消えて詳細ページの「記録を読む」も消えるので、`export` か「集計し直す」を使ってください。

### エージェントやローカルの LLM に渡す

フォルダやファイルを読める相手(GitHub Copilot CLI を自分で開いたもの、ほかのコーディングエージェント、ローカルの LLM の画面など)には、バンドルをそのまま渡せます。費用は渡した相手の側で決まります。

画面からは、「判定する…」で判定するものを選び(工数・依頼ごとの採用・タスクの紐づけのどれでも)、判定の方法に「ZIP にまとめてエージェントに渡す」を選び、4 つの手順に沿って進めます。工数のときは次のとおりです(ほかのものは、ZIP とフォルダと結果のファイルの名前が違うだけです。下の 3・4)。

1. **ZIP を作る**: 「未判定 N 件で ZIP を作る」を押します。判定済みのセッションを除いたバンドルと ZIP を、同じ回に作ります(下のコマンドと同じ。LLM は呼びません)。「チャットに貼って判定する」の添付ファイルも同じ中身で作り直され、ファイルの番号が振り直されます。
2. **エージェントに渡す**: 「bundle.zip をダウンロード」で保存し(ブラウザの保存先。ふつうは「ダウンロード」フォルダー)、そこで展開して、できた `bundle` フォルダだけをエージェントに開かせます。ZIP を受け取れる相手には、展開せずに添付してもかまいません。画面の依頼文(「bundle フォルダの INSTRUCTIONS.md に従って判定し、結果を bundle フォルダの中の judgments.json に書いてください。」)は「依頼文をコピー」で写せます。書き込みを許可するのは、この `judgments.json` だけにします。ファイルを書けない相手(チャットの画面など)には、依頼文の後ろを「JSON を返してください」に変えて頼みます。画面は、出力先の中の ZIP の場所(フルパス)を出しません。出力先でエージェントを開かせないためです(下の注意)。
3. **結果を取り込む**: エージェントに書かせた `judgments.json` か、返答を保存したファイルを選ぶと中身が欄に入るので、確かめてから「取り込む」を押します(5 MB まで。JSON を返答でもらったときは欄に貼り付けます)。
4. **レポートに反映する**: 「レポートに反映する」を押します。途中までの結果でも取り込めます(残りは、次に作る ZIP に入ります)。

| 判定するもの | ZIP(展開してできるフォルダ) | 結果を書かせるファイル | 取り込むコマンド |
|---|---|---|---|
| 工数 | `bundle.zip`(`bundle`) | `judgments.json` | `judge import` |
| 依頼ごとの採用 | `turn-bundle.zip`(`turn-bundle`) | `turn-judgments.json` | `turns import` |
| タスクの紐づけ | `task-bundle.zip`(`task-bundle`) | `links.json` | `tasks import` |

ZIP(フォルダ)の `INSTRUCTIONS.md` と、チャットに貼る添付ファイル(`parts/`)の指示は、渡し方に合わせて 2 点だけ書き分けています(工数・依頼ごとの採用・タスクの紐づけで同じ)。パケットの中の指示に従わないことは、どちらにも書いています。

| | `INSTRUCTIONS.md`(フォルダ・ZIP で渡す) | `parts/`(チャットに貼る) |
|---|---|---|
| ツール | フォルダのファイルを読むことと、結果のファイルを 1 つ書くこと以外(シェルでの実行・Web 検索・フォルダの外の読み書きなど)は使わない | 使わない |
| 結果 | フォルダの中の、上の表の「結果を書かせるファイル」に書く(中身は JSON だけ)。ファイルを書けない相手は、JSON をコードブロックで返答してよい | JSON をコードブロックで返答する |

コマンドでは次のとおりです。

```
bin\atlas.exe bundle --unjudged --zip  # out/bundle/ と out/bundle.zip を作る
```

1. `out/bundle.zip` を別のフォルダに写して渡す(または、そこで展開した `bundle` フォルダを開かせる。`out/` は開かせない)。フォルダを読めない相手には `parts/part-01.md` を 1 つずつ渡します(1 ファイルが相手の入力の上限に収まらないときは `--per-part 1` で作り直します)。
2. 「`INSTRUCTIONS.md` に従って判定し、結果を `judgments.json` という 1 つのファイルに書いてください」と頼みます。
3. できたファイルを取り込みます。画面なら「判定する…」→「ZIP にまとめてエージェントに渡す」(「チャットに貼って判定する」でも同じ)の手順 3 でファイルを選んで「取り込む」、コマンドなら `bin\atlas.exe judge import judgments.json`(取り込めたらレポートも作り直します)。形が合わない項目が 1 件でもあると何も取り込まず、「何件目(セッション …)の、どの項目が、どう違うか」を並べて出します。その文をそのままエージェントに返すと直して書き直せるよう、`INSTRUCTIONS.md` にも書いてあります(画面では「直す点をコピー」で写せます)。途中までの結果でも取り込めます(残りは次の `bundle --unjudged` に入ります)。

`INSTRUCTIONS.md` には、読み方として次のことを書いています(工数・依頼ごとの採用・タスクの紐づけで同じです)。

- `manifest.json` は件数とファイルの一覧の確認用で、全部を読まなくてよい(タスクの紐づけの束では、タスクの数だけ候補の ID が並んで大きくなるので、候補の ID は `manifest.json` から `candidates.json` に分けています)。パケットは `sessions/`(依頼ごとの採用は `chunks/`)を順に読む。
- 各パケットを読んで、そのパケットだけを根拠に決める。同じ依頼のセッションが続くときは並べて読んでもよいが、結果はパケットごとに決める。
- 取り込みで形の誤りが見つかると、その文が返ってくるので、挙がった項目を直して結果のファイルを全体で書き直す。

工数の判定の「達成(`aiOutcome.completed`)」は、依頼が求めた中身を満たしたら達成です。中身が違う・足りないときは達成にしません。依頼が決めた出力の形(ファイルの名前・置き場所・形式・書式など)との違いは、達成かどうかを変えず、`quality` を下げて `aiOutcome.rationale` に書きます。正解のデータがパケットに無いときは、パケットの記録(テストやビルドの結果、最終応答、後の依頼)から判断できる範囲で決め、`aiOutcome.rationale` に「正解のデータが無く、記録から判断した」と書きます。工数の推定の確信度(`humanEffort.confidence`)は、正解のデータが無いことでは下げません(成果物の規模が読み取れるか、大量の生成で確かめられないか、という今までの基準で決めます)。チャットに貼る添付ファイル(`parts/`)の指示にも、同じ文を書いています。

この文は 2026-11-24 に変えました。前の文は「中身と形の両方を満たしたら達成」「形だけ違うときは達成」と食い違っており、正解のデータが無いときに `humanEffort.confidence` を下げさせていました。評価軸の版を持つ仕組みは無いので、前の文で判定したセッションの判定は、取り込んだまま残ります(作り直しも書き換えもしません)。新しい文で判定し直すときは、上の「評価軸を変える前に判定したセッション」と同じく、そのセッションだけで作り直して渡します。

- **パケットには他のセッションの依頼文や応答がそのまま入っています。** その中に「このコマンドを実行せよ」のような文があると、ツールを使えるエージェントは従ってしまうことがあります。エージェントに渡すときは、シェルの実行と Web へのアクセスを許可せず、ファイルの書き込みは結果のファイル(`judgments.json`)だけにして、展開したフォルダだけを開かせてください。ファイルを書けない相手には、JSON を返答として出してもらい、それを貼るか保存して取り込みます。
- **エージェントを出力先(`out/`)で開かないでください。** `out/judgments.json` はこのツールの判定の保存先です。そこに「`judgments.json` に書いて」と頼むと、今回の分だけの中身で上書きされ、それまでの判定が消えます(`out/turn-judgments.json` も同じ)。`out/` にはほかのセッションの記録もあります。ZIP は別のフォルダに写してから展開し、書かせるならそのフォルダの中にします(`out/` の中で展開すると `out/bundle/` も書き換わり、画面は ZIP を「まだ作っていません」と表示します)。
- **ターミナルで動くエージェントには、結果をファイルに書かせてください。** 返答で返させて写すと、取り込めないことがあります。GitHub Copilot CLI(1.0.112)で確かめたところ、返答は画面の幅で折り返して出され、JSON の文字列の途中に改行が入り、コードブロックの印も消えて、「JSON を取り出せません」になりました。ファイルに書かせた `judgments.json` は、そのまま取り込めました。対話の画面(`-i`)でも、返答を画面から写したものは取り込めませんでした(返答の JSON は、文字列の途中で画面の幅に合わせて折り返して表示され、1 画面にも収まりません)。ファイルに書かせる形は、対話の画面でも通りました。`-p` で確かめたときの起動の仕方は次のとおりです(展開した `bundle` フォルダの 1 つ上で実行。シェルと URL を拒否し、書き込みは結果のファイルだけを許可する。使用量を記録する指定は省いています)。

  ```
  copilot -p "bundle フォルダの INSTRUCTIONS.md に従って判定し、結果を bundle フォルダの中の judgments.json に書いてください。" --stream off -s --no-ask-user --no-custom-instructions --disable-builtin-mcps --deny-tool shell --deny-tool url --allow-tool "write(bundle/judgments.json)" --model <モデル>
  ```

- 渡す相手が外部のサービスのときは、中身(本文、パス、リポジトリ名)を渡してよいか先に確かめてください。
- 返す形は JSON だけです(ZIP で返してもらう形は用意していません)。
- ローカルの LLM では、1 パケットが最大 24,000 字あるので、入力の上限が小さいモデルでは途中で切れることがあります。このツールでは確かめていません。
- 通して確かめたのは GitHub Copilot CLI だけです。ほかのコーディングエージェントでは確かめていません。

### 範囲を絞る(1 セッション)

画面の「判定する…」は、未判定のすべてのセッション(依頼)が対象です。1 セッションだけを判定する・判定し直すときは、コマンドでそのセッションだけの添付ファイルを作り、チャットに貼るか ZIP で渡します。

```
bin\atlas.exe bundle --session <id>,<id> --zip   # そのセッションだけで out/bundle/(と out/bundle.zip)を作り直す。ID は先頭の数文字でよい
bin\atlas.exe turns bundle --session <id> --zip  # 依頼ごとの採用(--unjudged を付けると、判定済みの依頼を除く)
```

できた添付ファイル(`out/bundle/parts/part-01.md` など)をチャットに貼るか、ZIP をエージェントに渡し、返答を取り込みます(画面の「判定する…」の手順 3、または `judge import`)。同じセッションの判定は、取り込んだもので置き換わります。作り直した添付ファイルは画面の「判定する…」にもそのまま出ます(画面の手順 1 で作り直すと、未判定のすべてのセッションの添付に戻ります)。

- **判定したかどうかの見分け方**: 詳細ページの表題の下の印の列に「LLM 判定(工数)✓ 済み / 未判定」と「LLM 判定(依頼ごと)n / m 件」(全部済めば ✓)が出ます。セッション一覧では、工数は「推定人手工数」の列の「未判定」、依頼ごとは「依頼」の列の件数の下の「未判定」「判定 n / m」「✓ 判定済み」で見分けます(依頼ごとの印は、レポートに依頼ごとの判定が 1 件でもあるときだけ出ます)。詳細ページには、判定を始めるボタンはありません。
- コマンドの `--session` は ID の先頭一致です([cli.md](cli.md))。

## llm-wiki のページごとの判定

工数の判定(上の 1・2)の中で、読んだ llm-wiki のページ 1 つずつについて「役立ったか」も LLM に見立てさせます。どの経路(チャットに貼る・M365 Copilot の自動操作・ZIP をエージェントに渡す)でも同じパケットと指示を使い、結果は同じ `judgments.json` の項目 `wikiPages` に入ります。レポートでは改善点の「llm-wiki のページごとの参照率と役立った率」と、詳細ページの「LLM による判定(推定)」に出ます([screen.md](screen.md))。**LLM の見立てで、測った値ではありません。** セッション全体の `wikiEffect`(−2〜+2)はそのまま残します。

| 項目 | 値 |
|---|---|
| `page` | パケットに書いたページの名前をそのまま(vault からの相対。vault を複数指定したときは先頭に vault の名前) |
| `helpful` | `yes`: そのページの中身が後の作業(判断・コード・回答)に使われ、作業を進めた / `no`: 読んだが使われなかった、または誤った方向に導いた / `unknown`: 記録から判断できない |
| `reason` | 根拠を 1 文で(どの抜粋・依頼・応答・変更から判断したか) |

- **パケットに載せるもの**: パケットの「指示ファイル・llm-wiki の参照」の中の「llm-wiki のページごとの判定」に、読んだページ(重複を除いて読んだ順)ごとに、読んだ時刻と何番目の依頼の中か、読んだ後に同じ依頼の中で呼んだツール(5 件まで。内部ツールを除く)、**抜粋**(そのページを読んだツールの結果の先頭)を並べます。その後の流れ(依頼・最終応答・変更ファイル)はパケットのほかの節にあるので、足していません。
- **抜粋を取る呼び出し**: ログの全文(スナップショットの `events.jsonl`)の呼び出しごとに、集計と同じ分類(今の設定 `atlas.config.json` の `wikis` の vault の指定)を当て、そのページを読んだと分類された呼び出しから取ります。書き込みのツールと、サブエージェントへの依頼(`task` など。引数は依頼文で、結果はページの中身ではない)は読み取りにしません。ページの名前の直後に名前の続きがあるもの(`a.md.bak` など)も、そのページの読み取りにしません。失敗した呼び出しと結果の本文が無い呼び出しは飛ばし、後の読み取りから取ります。結果(`result` の `content`、無ければ `detailedContent`)は、秘密らしい文字列を全文で伏せてから(秘密情報の検査と同じ規則)切ります。1 回の呼び出し(検索など)で複数のページを読んだときは、それらのページに同じ抜粋を載せ、「ほかのページと同じ結果の抜粋」と書きます。
- **設定に vault の指定が無いとき**(集計した後に設定を変えたなど): 引数に「/<ページ>」の形で名前が出る呼び出しを読み取りとします(区切りのまとめ方は集計と同じ)。この場合、vault の直下のページ(`AGENTS.md` など)は、プロジェクトの同じ名前のファイルと見分けられません。設定の指定が集計したときと違うと、ページの名前が合わず、抜粋を取れないことがあります。
- **抜粋が無いとき**: 成功して結果の本文がある読み取りがログに無いとき、読んだ呼び出しを特定できないとき、ログの全文が無いとき(`session-store.db` か sessions.json の抜粋で代用したとき)は「抜粋なし」と書き、名前と前後の流れだけで判断して、決め手が無ければ `unknown` にするよう指示に書いてあります。
- **上限**: 判定に載せるのは 1 セッション 10 ページまで(`crates/atlas-core/src/wiki.rs` の `WIKI_JUDGED_PAGES_MAX`。読んだ順の先頭から)で、残りはパケットに「上限のため判定しません」と件数を書き、未判定にします。抜粋は 1 ページ 400 字まで(`PacketLimits` の `wikiExcerptChars`)で、パケットが 24,000 字に収まらないときは、ほかの本文と一緒に段階的に短くします(ページの並びは変えません)。
- **返答の扱い**: `wikiPages` は必須ではありません(版 1 の指示で作った返答もそのまま取り込めます)。無いときは、ほかの判定を取り込み、そのセッションのページを未判定にします(知らせません)。壊れているとき(配列でない、または要素の形が合わない(`page` が無い、`helpful` が 3 つの値のどれでもない)・同じページが 2 回ある)は、ほかの判定を取り込み、壊れた分のページを未判定にして、ログに知らせます(`judge import`・M365 Copilot の自動操作のログ。画面の「取り込む」では画面には出さず atlas のログに書きます)。パケットに無いページの名前を返したものは、レポートを作るときに捨てます。
- **版**: `judgments.json` のスキーマの版は 2(`wikiPages` を足した版)です。版 1 の `judgments.json` も読み、その判定のページは未判定として数えます。書くときは、どの項目も `wikiPages` を持たない間は版 1 のまま書き、`wikiPages` を持つ項目ができたら版 2 で書きます。**版 2 で書いた `judgments.json` は、この機能より前の atlas.exe では読めず、`build`(レポートを作る)が止まります。** 前の版の atlas.exe に戻すときは、`judgments.json` を控えてから戻してください。バンドル(添付ファイル)を作り直してから判定し直すと(`bin\atlas.exe bundle --session <id>` で作り直した添付ファイルをチャットに貼る、または ZIP で渡す)、ページごとの判定が付きます。
- 判定は今までどおり利用者が回したときだけで、集計(`atlas.bat`・`build`・`export`)は LLM を呼びません。

## 3. 依頼ごとの採用

工数の判定(上の 1・2)とは別の判定です。工数はセッション 1 件を単位に、依頼ごとの採用は依頼 1 件を単位に判定します。渡す材料(工数はセッション全体の要約、採用は依頼とその次の依頼の文)も、結果のファイル(`judgments.json` と `turn-judgments.json`)も別々なので、片方だけを回せます。レポートでは、同じ表に別の列で並びます。

依頼(ターン)ごとに、AI の成果が利用者にどう扱われたかを LLM に判定させます。判定の単位は依頼 1 件で、材料はその依頼の文・AI の最後の応答・規則による推定(工程・ツールの回数・失敗・拒否・中断)と、**次の依頼の文**です。結果は `out/turn-judgments.json` に貯まり、次の `export`(画面の「レポートに反映する」「集計し直す」)でレポートの「工程と詰まり」と詳細ページ、表(`turns.csv` の「判定:」の列)に出ます。**推定です**。セッションの後に手で直した分やコミットしなかった分は、ログに無いので見えません。

| 項目 | 値 |
|---|---|
| `kind`(依頼の種類) | `task`(作業)/ `question`(質問)/ `fix`(修正)/ `revert`(差し戻し)/ `continue`(続行) |
| `outcome`(扱い) | 作業の依頼: `as_is`(そのまま採用)/ `fix_content`(中身を修正して採用)/ `fix_style`(体裁を修正して採用)/ `rejected`(不採用)/ `unknown`(判定不能)。質問の依頼: `helpful`(役に立った)/ `follow_up`(追加で聞いた)/ `off_target`(的外れ)/ `unknown` |
| `mismatch`(合わなかった点。中身・体裁の修正、不採用、的外れのときだけ) | `requirement`(意図・要件の取り違え)/ `defect`(誤り・不具合)/ `quality`(品質・体裁・決まりごと)/ `scope`(やり過ぎ・足りない)/ `environment`(環境・ツール・権限)/ `other` |
| `phase`(普段の工程) | `atlas.config.json` の `phases`(無ければ 要件定義 / 設計 / 実装 / テスト / レビュー / 調査 / 運用 / その他)のどれか |
| `confidence` / `note` | 確信度(0〜1)と、判定の理由(1〜2 文) |

- **セッションの最後の依頼**には次の依頼が無いので「判定不能」です。拒否・中断の回数は次の依頼の文の裏付けにだけ使い、回数だけでは不採用にしません。AI が確認や選択肢を返しただけの依頼も、まだ扱う成果が無いので判定不能です。レポートでは件数を出したうえで採用率の分母から外します。
- **判定に渡す順番**: 依頼は、続いた数件ずつの塊(`chunks/<番号>.md`)にまとめ、次の依頼がある依頼(採用を判定できる依頼)の塊を先に並べます。セッションの最後の依頼は、どのセッションでも 1 件だけの塊にして後ろへ回し、判定できる依頼と同じ添付ファイルには入れません。後ろの分は種類と工程だけが決まります。採用率だけを見たいときは、先頭の分だけ判定すれば足ります(そのとき、種類別・工程別の表には、最後の依頼は入りません)。どこまでが先頭の分かは、次のところに出ます。
  - 画面の「チャットに貼って判定する」: 手順 1 に「採用を判定できる依頼は N 件で、先頭の M ファイルに入っています」と出ます。ファイルの一覧では、後ろのファイルに「最後の依頼だけ」と付き、次に渡すファイルがそこに入ったら「ここで止めて手順 4 へ進めます」と出ます。
  - 画面の「ZIP にまとめてエージェントに渡す」: 手順 1 に「ZIP の中の先頭の K 個の塊(chunks/0001.md〜)に入っています」と出ます。ZIP の `INSTRUCTIONS.md` にも同じことを書き、採用率だけを求められているときは先頭の塊だけを判定すれば足りると伝えます。
  - コマンド: 添付ファイルを作ったときのログ(`turns bundle: 採用を判定できる依頼(次の依頼がある依頼)は N 件で、添付ファイル(parts/)の先頭の M ファイルと、先頭の K 個の塊(…)に入れました…`)と、`out/turn-bundle/manifest.json` の `decidable`(`turns`・`chunks`・`parts`)。
- **迷う場面の決め方**(2026-11-24 に指示に足しました。上の表の分類の意味は変えていません。フォルダで渡す指示とチャットに貼る添付ファイルの両方に入ります):
  - 次の依頼の本文が無い(「(本文なし)」)、応答の記録が無い、最後の応答が途中経過だけ(「…確認します」で終わるなど)のときは、`outcome` を `unknown` にし、`confidence` を低く(0.3 以下)します。
  - 質問の形をした依頼の `kind` は、文の形ではなく意図で決めます。前の成果を直させる意図なら `fix`、相談なら `question` です。
  - `question` の `outcome`: 同じ話を深掘りする追加の質問は `follow_up`(`mismatch` は null)、回答が的外れで聞き直したときは `off_target`(`mismatch` を付ける)。
  - AI が承認を求め、次の依頼が「承認」だけのときは `as_is`。承認までに中身を直させたときは、直させた成果を出した依頼(直しを求める依頼の 1 つ前)を `fix_content` にします。
  - 中断と再開が続き、次の依頼が「再開」「続けて」だけのときは、その依頼の `outcome` は `unknown` にします。
    - 例: 依頼 3「一覧の画面に検索欄を付けて」の途中で利用者が中断し(依頼 3 の間に中断が 1 回)、依頼 4 が「続けて」だけ、依頼 5 が「次は並べ替えを付けて」のとき。依頼 3 は成果が出る前に止まっていて扱いを読み取れないので `unknown`(`confidence` は低く)。依頼 4(続きの作業)は、依頼 5 が直しを求めずに次の作業へ進んでいるので `as_is` です。依頼 3 の間に中断が無く、依頼 4 が「続けて」だけなら、依頼 3 は今までどおり `as_is` です。
  - ツールや環境の設定・運用の依頼の `phase` は、次の順に決めます。どの工程名になるかは束を作るときの工程名で決め、指示の文にはその工程名を書きます(2026-11-24 に、2 と 3 の順を入れ替えました)。
    1. 工程名に「運用」があれば「運用」(既定の工程名にあるので、既定のままなら「運用」)。
    2. 無ければ、工程名の中で設定・運用にいちばん近いもの。「保守」「運営」「環境」「設定」「インフラ」「基盤」(英字は ops・infra・setup・config・maint。大文字と小文字は区別しません)のどれかを含む工程名を、この語の順に探します(同じ語なら工程名の並びの前のもの)。無ければ、名前が「運用管理」と同じ工程名を探します(「環境構築」「環境準備」は「環境」を含むので、その前に選ばれます。「構築」「管理」「準備」は「設計・構築」「進捗管理」「資料準備」のようにほかの工程の名前にも入るので、含むだけでは選びません)。
    3. それも無ければ「その他」。「その他」も無いときは、指示には「上の工程名のうち最も近いもの」と書きます(工程名の一覧に無い名前は、取り込みで受け付けないため)。

    「要件定義」は、作るものの要件・仕様を決める依頼だけです。
  - 上限: 1 セッションの先頭 200 依頼までを束に入れます。超えた依頼は判定しません。束を作ったときのログ(`turns bundle: 注意 1 セッションの先頭 200 依頼までを束に入れます。上限を超えて入れなかった依頼が N 件(M セッション)…`)と `manifest.json` の `overLimit`、レポートの「採用(LLM の判定)」の節に、上限を超えた依頼の数が出ます。
  - フォルダで渡すときは、結果のファイル(`turn-judgments.json`)を手で書いてよいと書きました。ファイルの読み書きのほかはツールを使わない決まりは、今までどおりです。
  - 前の指示で判定した依頼の判定は、取り込んだまま残ります(作り直しも書き換えもしません)。新しい指示で判定し直すときは、`turns bundle --session <id>` でそのセッションだけの束を作って渡します。
- **普段の工程名を変える**: リポジトリ直下の `atlas.config.json` に `"phases": ["要件定義", "設計", "実装", "テスト", "レビュー"]` のように書きます(2 つ以上、重複なし)。変えた後は判定し直すまで、前の名前の判定はそのまま残り、レポートでも前の名前の行に出ます。返答の取り込みでは、添付ファイルを作ったときの工程名と今の工程名のどちらも受け付けます(添付を作った後に名前を変えても、その添付への返答を取り込めます)。

### チャットに貼る(M365 Copilot など。既定)

「判定する…」で「依頼ごとの採用」と「チャットに貼って判定する」を選び、[2](#画面からおすすめ) と同じ 4 つの手順で進めます。**添付ファイルには、セッション ID・題名・プロジェクトのパス・依頼文(1 件 1,500 字まで)・AI の応答(900 字まで)がそのまま入ります**(応答にはユーザー名を含むパスが出ることがあります)。渡してよい相手か確かめてください。添付ファイルは依頼 24 件ずつ(`out/turn-bundle/parts/`、1 ファイル 6 万字ほどまで)で、ダウンロードの名前は `turns-part-01.txt` などです。全部の依頼を判定するには、依頼 1,000 件でおよそ 40〜50 往復です。採用率だけなら、画面の手順 1 に出る「先頭の M ファイル」までで足ります(上の「判定に渡す順番」)。

### ZIP にまとめてエージェントに渡す

「判定する…」で「依頼ごとの採用」と「ZIP にまとめてエージェントに渡す」を選び、工数の ZIP と同じ 4 つの手順で進めます(上の「[エージェントやローカルの LLM に渡す](#エージェントやローカルの-llm-に渡す)」。注意も同じです)。

- `turn-bundle.zip` を展開すると `turn-bundle` フォルダができます。中身は `INSTRUCTIONS.md`(指示)・`manifest.json`(塊の一覧。`chunks[].path` に、セッション `chunks[].sessionId` の依頼 `chunks[].turns`。指示では、確認用で全部を読まなくてよいとしています)・`schema.json`(返す JSON の JSON Schema)・`chunks/<番号>.md`(塊の本文。添付ファイルと同じ中身で、セッション ID と判定する依頼を書いてあります)です。`parts/` は入れません。
- 画面の依頼文は「turn-bundle フォルダの INSTRUCTIONS.md に従って判定し、結果を turn-bundle フォルダの中の turn-judgments.json に書いてください。」です。できた `turn-judgments.json` を手順 3 で選んで取り込みます(取り込みの検証はチャットの返答と同じです)。
- `out/turn-judgments.json` はこのツールの保存先なので、エージェントを `out/` で開かせないでください(上書きされると、それまでの判定が消えます)。

コマンドでは次のとおりです。

```
bin\atlas.exe turns bundle --unjudged        # out/turn-bundle/ を作る(判定済みの依頼を除く。LLM は呼ばない)
bin\atlas.exe turns bundle --unjudged --zip  # 同じものを out/turn-bundle.zip にもまとめる
bin\atlas.exe turns import 返答.md             # チャットの返答(またはエージェントが書いた turn-judgments.json)を out/turn-judgments.json に取り込み、レポートを作り直す(export)
```

## 4. 管理ツールのタスクへの紐づけ

管理ツールのタスク(設定の `tasks`。[README の「管理ツールのタスクと工数」](../README.md#管理ツールのタスクと工数任意))に、機械で紐づかなかったセッションを LLM で紐づけるときも、工数の判定と同じく外部の LLM に頼みます(チャットに貼る・ZIP をエージェントに渡す・M365 Copilot の自動操作)。頼んだときだけで、集計では LLM を使いません。

- **画面から**: 「判定する…」で判定するものに「タスクの紐づけ」を選びます(タスクの設定か記録があって、読むだけの画面でないときだけ出ます)。あとは工数と同じ 4 つの手順です。手順 1 のボタンは「紐づけの無い N 件で作る」で、ダウンロードの名前は `tasks-part-01.txt` などです。ZIP のときは `task-bundle.zip`(展開すると `task-bundle` フォルダ)を渡し、結果を `task-bundle` フォルダの中の `links.json` に書かせます。
- **コマンドで**:

  ```
  bin\atlas.exe tasks bundle                 # 機械の紐づけを決め直してから、紐づけの無いセッションを out/task-bundle/ にまとめる(--zip で out/task-bundle.zip も)
  bin\atlas.exe tasks bundle --session <id>  # そのセッションだけ(紐づけの無いものだけ。紐づいていれば理由を出して入れない)
  bin\atlas.exe tasks import 返答.md          # 返答を検証して task-links.json に書き、レポートを作り直す
  ```

  `--per-part <n>` で 1 ファイルに入れるセッションの数を変えられます(既定 10)。`--unjudged` は付けても付けなくても同じです(いつも紐づけの無いセッションだけです)。頼むセッションが 1 つも無いとき(`--session` で紐づいたセッションだけを指したときなど)は、前に作った束と ZIP をそのまま残し、理由を出します(画面では手順 1 に「作り直していません」と出ます)。
- **束の版**: この版の `tasks bundle` が作る束は版 2 です(候補の ID を `manifest.json` から `candidates.json` に分けた形)。前の版の atlas は版 2 の束を読めず、取り込み(`tasks import`・画面の取り込み・M365 Copilot の自動操作)が「`manifest.json` の形式が想定と違います」で止まります。束を作る人と取り込む人が違うとき、同じ出力先を前の版の atlas でも開くときは、**全員の atlas を更新してから使ってください**。この版は、前の版が作った版 1 の束も読めます。
- **束に入れるセッション**: 紐づけの無いセッションのうち、開いただけのもの(依頼・ツール・応答が無い)・題名も依頼の文も無いもの・候補のタスクが無いものを除いたものです(画面の件数と同じ決め方)。手で決めた紐づけと、前に LLM で決めた紐づけのあるセッションは入れません。頼み直したいときは、詳細ページで「自動に戻す」を押してから束を作り直します。
- **渡すもの**: セッションごとのパケット(`sessions/<セッション ID>.md`)に、セッションの題名と、最初の依頼から 3 件までの文(1 件 600 字まで。依頼 1 件が 1 つで、改行を含む依頼も 1 つ。スナップショットのログから読み、無ければ sessions.json の最初の依頼と各依頼の先頭(300 字まで)で代えます)、候補のタスクの ID と名前(100 件まで)を書きます。添付ファイル(`parts/part-<番号>.md`)は、指示・JSON Schema と数件のパケットを 1 ファイルにまとめ、パケットをファイルごとの乱数の境界で囲みます。パケットの中の指示には従わないよう、指示に書いています。セッションごとの候補の ID は、パケットと同じ並びで `candidates.json` に残します(返答の検証に使います。ZIP には入れません)。前の版は `manifest.json` に入れていましたが、タスクの数だけ ID が並んで `manifest.json` が数千行になり、外部のエージェントが一覧の確認に読むには大きすぎたので分けました。前の版で作った束(`manifest.json` に候補があるもの)も、そのまま取り込みの検証に使えます。
- **候補の選び方と並び**: 候補になるのは、未完了のタスクと、セッションの開始より後に完了を確認したタスクです(XML に無くなったものも入れます)。これを次の順に並べ、100 件で切ります。束(`tasks bundle`)・チャットに貼る添付ファイル・ZIP・M365 Copilot の自動操作・画面の「判定する…」は、どれも同じ並びです。
  1. 機械の紐づけで決まらなかったときに当たったタスク(名前で 2 つ以上に当たったものなど)。
  2. 残りは、パケットに書くセッションの文(題名と依頼の文)と、タスクの名前の**文字の重なり**の多い順です。重なりは、どちらの文も正規化(NFKC・小文字)し、隣り合う 2 文字の組(文字 bigram。空白と記号をまたがない組)のうち、タスクの名前の組が、セッションの文にいくつあるかで数えます。決まった規則で、LLM は使いません。分かち書きの無い日本語でも、英語でも同じ決め方で働きます。
  3. 重なりが同じものは、未完了のもの → 完了を確認した時刻が、セッションの最後の活動(`updatedAt`。無ければ開始)に近いもの → XML に無くなったもの → XML の順です。

  何日もかけて終えたタスクは完了の確認が遅いので、完了の早い順に並べると、開始の後に完了した多くのタスクの後ろに回り、上限で漏れることがあります。そのため、文字の重なりと、最後の活動からの近さで並べます。候補を上限で切ったときは、パケットの「候補のタスク」の見出しに「全 N 件のうち、題名と依頼の文に近いものから 100 件」と書き、作業したタスクが候補に無いと思うときは `[]` にしてよいと書きます(指示の「決めること」にも同じことを書いています)。上限の 100 件は、どの環境でも同じ決まった値です(どこかの環境のタスクの数に合わせた値ではありません)。
- **答えの形**: 

  ```json
  { "schemaVersion": 1, "links": [ { "sessionId": "<パケットのセッション ID>", "taskIds": ["<候補の ID>", …], "confidence": 0.7, "reason": "選んだ理由(1 文)" } ] }
  ```

  1 つのセッションで、いくつかのタスクの作業をすることもあるので、作業したタスクを 0 個以上選ばせます(10 個まで。空の並びは「どのタスクでもない」)。名前や話題が似ているだけで作業していないタスクは選ばないよう、指示に書いています。項目の並びだけ(`[ {...} ]`)や、項目 1 つだけの JSON、前の形の `taskId`(1 つか null)も読みます。
- **取り込みの検証**: 形が合わない項目が 1 件でもあると何も書かず、何件目のどのセッションの何が違うかを並べます(画面では「直す点をコピー」で写せます)。形の誤りとするのは、`sessionId` が無い・作った束に入っていないセッション、`taskIds` が並びでない、`confidence` が 0〜1 の数でない、答えたタスクの ID がどれもそのセッションの候補に無い、のときです。候補に無い ID がほかの ID と混ざっていたら、その ID だけを除いて知らせます。重なりは除き、10 個を超えた分は除いて知らせます。同じセッションが返答に何度か出てきたら、後ろのものを使います。
- **書き込み**: `task-links.json` のロックの中で読み直し、紐づけの出所を LLM にして書きます。取り込む前に手で紐づけたセッションと、前に LLM で紐づけたセッションは書き換えません。機械の紐づけは、タスクを選んだ答えなら置き換えます(LLM は機械より先に使う出所です)。「どのタスクでもない」の答えでは、タスクのある機械の紐づけ(束を作った後に機械の当たりが決まったもの)を消しません。書かなかったセッションと、除いた ID は、ログと画面(取り込みの結果の文の下)に出します。`tasks import` は、書いたセッションがあればレポートを作り直します(`export`)。画面では手順 4 の「レポートに反映する」で作り直します。
- 1 つのセッションに紐づいたタスクの実働と推定人手工数は、タスクの数で等分して数えます([README の「管理ツールのタスクと工数」](../README.md#管理ツールのタスクと工数任意))。
- 読むだけの画面(送り先から集計した・別のフォルダを開いた)の紐づけは送った人のものなので、ここでは頼めません(画面に出さず、API も断ります)。
- **設定のフォルダを使うとき**(共有の `AtlasSettings`。[README の「本番の置き方」](../README.md#本番の置き方sessionlog-と-atlassettings)・[cli.md の「設定のフォルダ」](cli.md#設定のフォルダ--settings)): 設定に `tasks` があれば、開いたフォルダの画面でも頼めます(紐づけは集計する人が行います)。束は開いたフォルダの出力先(`out-folders\<キー>\out\task-bundle\`)に作り、取り込みは設定のフォルダの `task-links.json` に書いて、レポートを作り直します。コマンドでは、`open` が出す出力先を `--out` に指します(設定のフォルダは開いたときの記録 `folder.json` から決まります。`--settings` でも指せます)。

  ```
  bin\atlas.exe tasks bundle --zip --out "out-folders\SessionLog-1a2b3c4d\out"
  bin\atlas.exe tasks import 返答.md --out "out-folders\SessionLog-1a2b3c4d\out"
  ```
