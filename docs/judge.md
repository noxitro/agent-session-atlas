# 推定人手工数の判定

[README](../README.md) に戻る。

「同じ作業を人が AI なしでやったら何時間かかるか」は LLM に推定させます。集計(LLM なし)とは別の手順で、結果は `out/judgments.json` に貯まり、次の `atlas build` でレポートに合成されます。判定は外部の LLM でも、このツールの中からでも回せます(どちらも同じ形式です)。

**推定は推定です。** レポートには幅(low〜high)と確信度を一緒に出しますが、人手での実測ではありません。

**合計は、大きな推定の数件で決まることがあります。** AI が数百ファイルを一度に生成したセッションは、成果物の量から数百〜数千時間と推定されやすく、1〜2 件で合計の大半を占めます。そのため次の 3 つをしています。

- 判定の指示(評価軸)で、成果物の量をそのまま工数にしないこと、動くか・使われたかをパケットから確かめられない大量生成は `hours` を確かめられた分に留め(量から見た上限は `high`)、`confidence` を 0.3 以下にして根拠に「大量生成・検証不能」と書くことを求めています。
- **レポートは、確信度が 0.3 以下の推定を合計に入れません。** 件数と時間を別枠で出します(幅・中央値・「推定人手工数 ÷ AI の実働」・モデル別の「人手工数 / AIU」も同じ。セッション一覧と詳細ページには値をそのまま出します)。評価軸を変えて大量生成のセッションを判定し直しても、確信度は 0.3 以下に下がる一方で、時間は数千時間のまま変わらなかったためです(2026-11-14 に 2 セッションで確認)。LLM が出す時間そのものは指示で抑えられないので、確信度を手掛かりにレポートの側で分けています。
- レポートは合計の横に中央値を出し、合計に入れたセッションのうち推定の大きい上位 5% が合計の半分以上を占めるときはその割合を知らせます([screen.md](screen.md) の「AI 投入量 vs 推定人手工数」)。

評価軸を変える前に判定したセッションは、前の基準のままです(確信度が高いまま、合計に入ります)。判定し直すには、そのセッションだけを指定します。このツールで判定するなら `bin\atlas.exe judge-flow --session <id>,<id> --force`(ID は先頭の数文字でよい。そのセッションだけで添付を作って判定し、最後にレポート全体を作り直します)、チャットで判定するなら `bin\atlas.exe bundle --session <id>,<id>` で添付を作り直して貼ります。1 件なら、`atlas.bat` から開いた詳細ページの「工数を判定し直す」でもできます([2b](#2b-このツールの中で判定する画面からまたはコマンドで))。`judge run --only`(と `--session`)は今の添付に入っているセッションだけを判定します。未判定だけで作った添付(`bundle --unjudged`・画面の「添付ファイルを作る」)には判定済みのセッションが入っていないので、判定し直すのには使えません。

## 1. 評価バンドルを作る(LLM は呼ばない)

```
bin\atlas.exe            # まだなら先に集計(out/sessions.json と out/snapshot を作る)
bin\atlas.exe bundle  # out/bundle/ を作る。--project / --since / --client などで対象を絞れる。--zip で out/bundle.zip も作る
```

`out/bundle/` の中身:

| ファイル | 内容 |
|---|---|
| `INSTRUCTIONS.md` | 判定する LLM への指示(役割・評価軸・出力形式・手順)。最初に読ませる |
| `manifest.json` | パケットの一覧(セッション ID とファイルの場所、件数、サイズ) |
| `schema.json` | 返してもらう `judgments.json` の JSON Schema |
| `sessions/<セッション ID>.md` | 評価パケット。依頼文、最終応答、変更ファイル、ツール / skill / agent / hook、ターン数・時間・トークン、摩擦、指示ファイル・wiki の参照(索引・ページ・wiki の skill・そのほかの呼び出し・書き込みの回数。vault に触れていなければ「参照なし」、vault を指定せずに集計したときは「この集計では数えていません」。どちらも wikiEffect は 0 にするよう指示に書いてある。ページを読んだセッションでは、ページごとの判定の材料(下の「[llm-wiki のページごとの判定](#llm-wiki-のページごとの判定)」))、compaction 要約 |
| `parts/part-<番号>.md` | ZIP やフォルダを渡せない相手(テキストの添付だけの M365 Copilot など)用。指示・JSON Schema と、パケット数件(既定 5 件。`--per-part <n>` で変更)を 1 ファイルにまとめたもの。パケットはファイルごとの乱数の境界で囲み、本文の中の指示に従わないよう指示に書いてある。中身は `sessions/` と同じ |

`--zip` を付けると、`INSTRUCTIONS.md`・`manifest.json`・`schema.json`・`sessions/` を 1 つの ZIP(`out/bundle.zip`。`--bundle <dir>` を指定したときは `<dir>.zip`)にもまとめます。展開すると `bundle` フォルダが 1 つできます。`parts/` は `sessions/` と同じ中身なので入れません。圧縮はしていません(依存を増やさないため。大きさは `sessions/` の合計とほぼ同じです)。ファイルが 65,535 個か全体が 4 GB を超えるときは作らずに止まるので、`--since` や `--unjudged` で絞ってください。

- `--zip` を付けずにバンドルを作り直すと(画面の「添付ファイルを作る」と「このツールが判定する」も同じ)、前に作った `bundle.zip` は消します。中身が今のバンドルと合わなくなるためです。
- 依頼の記録が無いセッション(開いただけで使っていないもの)はパケットにしません(`manifest.json` の `skipped` に理由付きで載ります)。含めたいときは `--include-empty`。
- 本文はスナップショットのログから全文を読み直しますが、1 パケット 24,000 字に収まるよう長い本文は中略します(中略した箇所には字数を書きます)。
- **パケットには依頼文や応答の本文、パス、リポジトリ名がそのまま入ります。** 外部のサービスに渡す前に中身を確認してください。

## 2a. 外部の LLM で判定する(M365 Copilot など)

### 画面から(おすすめ)

`atlas.bat` から開いた画面の「判定する…」で、判定するものに「工数」、判定の方法に「チャットに貼って判定する」を選びます。相手は M365 Copilot に限りません。ファイルの添付か貼り付けができる LLM なら、同じ手順で使えます(フォルダを読めるエージェントに ZIP で渡すときは、下の「[エージェントやローカルの LLM に渡す](#エージェントやローカルの-llm-に渡す)」)。あとは画面の 4 つの手順に沿って進めます。ターミナルもファイルの置き場所も気にしなくてかまいません。

1. **添付ファイルを作る**: 「未判定 N 件で作る」を押します。判定済みのセッションを除いて、5 件ずつのファイルにまとめます(LLM は呼びません)。作ったあとは「作成済み」と出ます。「作り直す」はファイルの番号が振り直されるので、途中のファイルをダウンロード済みなら押さないでください。作れなかったときは、ボタンの下に「添付ファイルを作れませんでした」と理由(処理が「atlas: 失敗しました: 」に続けて書いた文)、ログ(折りたたみ)が出ます。原因を直してから、もう一度押してください。新しいものは別の場所に作り終えてから入れ替えるので、作り直しに失敗しても、前に作った添付ファイルはそのまま使えます(「作成済み」のまま。返答の取り込みも続けられます)。途中で止めたときは「添付ファイルの作成を止めました」と出ます。この知らせは、ダイアログを閉じるか、次に作れたら消えます(画面を読み込み直した後には出ません)。
2. **チャットに渡す**: 「part-01.txt をダウンロード」を押し、ブラウザの保存先(ふつうは「ダウンロード」フォルダー)に入ったファイルをチャットに添付します。画面の依頼文(「添付したファイルの指示に従って判定し、JSON を返してください。」)を「依頼文をコピー」で写して送ります。添付できないときは「本文をコピー」で中身を貼り付けます。保存は `.txt` にしています。相手が `.md` を受け付けるか分からないためで、中身は `part-01.md` と同じです。
3. **返答を取り込む**: チャットの返答をまるごとコピーして欄に貼り、「取り込む」を押します。返答をファイルに保存してあるとき(エージェントやローカルの LLM に書かせた `.json`、保存した `.md` / `.txt`。5 MB まで)は、欄の下でそのファイルを選ぶと中身が欄に入るので、確かめてから「取り込む」を押します。説明文が混じっていてもかまいません(JSON のコードブロックだけを読みます)。形が合わない項目が 1 件でもあると何も取り込まず、何件目のどのセッションのどの欄が違うかを出します(貼った返答は欄に残ります)。その場合は「直す点をコピー」で一覧を写してチャットに貼り、「この点を直した JSON をもう一度返してください」と頼むか、同じファイルをもう一度判定させてください。取り込むと次のファイルに進みます。
4. **レポートに反映する**: 何ファイルか取り込んだら「レポートに反映する」を押します。レポートの作り直し(`export`)が終わると帯に「再読み込み」が出ます。

どの手順も AI クレジットを使いません(判定するのはチャットの側です)。「ファイルの一覧」を開くと、どのファイルが取り込み済みかを確かめられ、どのファイルでも保存・コピーできます。

### M365 Copilot のアプリを自動で操作する(Windows)

手順 2〜4 を手でする代わりに、開いている M365 Copilot のアプリをこのツールが操作します(Windows の UI Automation。Windows PowerShell で動きます)。

1. M365 Copilot のアプリを開いてサインインし、チャットの画面を出しておきます(Edge で `m365.cloud.microsoft` を開いた画面も探しますが、確かめたのはアプリだけです)。
2. 「判定する…」→「チャットに貼って判定する」で添付ファイルを作り、手順 2 の「M365 Copilot で自動で判定する」の「M365 Copilot で N ファイルを判定する」を押します。
3. 未判定のファイルを 1 つずつ、新しいチャットで送ります。1 つごとに、モデルの選択で **Think Deeper** を選び(既に選ばれていればそのまま)、依頼文を入れ、「画像とファイルのアップロード」でファイル(`part-01.txt` など)を添付して送り、返答が終わるまで待って、返答の文字を取り込みます。全部終わると、取り込めた分をレポートに反映します(`export`)。

- **終わるまで M365 Copilot の画面に触らないでください。** 1 ファイルに数分かかることがあります(1 ファイルの待ち時間の上限は 900 秒)。
- **ほかのアプリでの作業は続けられます。** 画面の部品を押すと M365 Copilot が前面に出ることがありますが、出たらすぐ、直前に使っていた窓へ戻します。依頼文は、M365 Copilot を一瞬(0.3 秒ほど)前面に出してキー入力で打ちます(UI Automation では、入力欄に文字が残っていると書き換えられないため)。クリップボードは使いません。その間に打った文字が入力欄に混ざったときは、送る前に気づいて消し、打ち直します。
- 途中で画面の操作が崩れたファイル(添付が見つからない、送れない、返答が始まらないなど)は、新しいチャットで 2 回までやり直します。M365 Copilot の画面が見つからないときはやり直しません。
- **M365 Copilot には 1 日の利用上限があります。** 上限に達すると返答が「1 日の上限に達しました」になるので、そこで止まり、残りのファイルは送りません。M365 Copilot に出ている時刻(翌朝)を過ぎてから、もう一度実行すると続きを送ります(「使用量を増やす」は有料なので、このツールは押しません)。Think Deeper で依頼 20 件ほどのファイルを送ったときは、50 ファイルほどで上限に達しました。
- 添付したファイルは、手で添付したときと同じく **OneDrive に入ります**(M365 Copilot の決まり)。
- 返答は `out/bundle/replies/<名前>.md`(依頼ごとの判定は `out/turn-bundle/replies/`)に残します。画面から読んだ文字はコードブロックに行番号とボタンの名前が混じるので、`<名前>.md` には ```json のブロックに組み立て直したものを、`<名前>.raw.txt` には読んだままの文字を置きます。形が合わずに取り込めなかった返答は、直して「返答を取り込む」に貼るか `judge import` で取り込めます。そのファイルは次の回にもう一度送ります。
- 画面の要素(「新しいチャット」、モデルの選択、「ソースの追加と管理」、送信、返答のコピーのボタンなど)が見つからないときは、やり直しても見つからなければ、何を探していたかを出して止まり、残りのファイルは送りません。M365 Copilot の画面の作りが変わると、この操作は動かなくなります。そのときは手順 2〜4 を手で行ってください。
- 判定するのは M365 Copilot なので、このツールは AI クレジットを使いません。

コマンドでは次のとおりです(`--model` は M365 Copilot のモデルの選択の名前。`Auto` / `Quick Response` / `Think Deeper`。`--limit` は送るファイルの数、`--timeout` は 1 ファイルの待ち時間の秒数)。

```
bin\atlas.exe bundle --unjudged     # 添付ファイルを作る(まだなら)
bin\atlas.exe judge m365            # 未判定のファイルを M365 Copilot で判定して取り込み、レポートに反映する
bin\atlas.exe turns m365 --limit 2  # 依頼ごとの判定(turns bundle --unjudged で作ったもの)を 2 ファイルだけ
```

### コマンドで

渡し方は、相手が受け取れる形で選びます。

- **テキストの添付だけのとき(M365 Copilot など)**: `out/bundle/parts/` の `part-01.md` を 1 つ添付し、「このファイルの指示に従って判定して」と頼みます。指示・JSON Schema・パケット数件が 1 ファイルに入っているので、ほかのファイルは要りません。返答を保存して取り込んだら、`part-02.md`、`part-03.md` … と続けます。1 ファイルは最大 12 万字ほど(5 件 × 24,000 字)です。途中のセッションの判定が抜けるときは `--per-part 2` などで件数を減らして作り直してください。
- **ZIP を渡せるとき**: 画面の「ZIP にまとめてエージェントに渡す」か `bin\atlas.exe bundle --unjudged --zip` で作った `out/bundle.zip` を添付して「`INSTRUCTIONS.md` に従って判定して」と頼みます。件数が多いときは何回かに分けて返してもらってかまいません。
- **フォルダを読めるエージェントやローカルの LLM に渡すとき**: 下の「[エージェントやローカルの LLM に渡す](#エージェントやローカルの-llm-に渡す)」。

返ってきた JSON(または JSON のコードブロックを含む返答をそのまま貼った `.md` / `.txt`)を保存し、取り込みます。分けて返ってきた分は 1 つずつ取り込めます。

```
bin\atlas.exe judge import 返答.md  # 検証して out/judgments.json に取り込む(同じセッションは上書き)
bin\atlas.exe export              # レポートに合成(画面の「集計し直す」でもよい)
```

形が合わない項目(範囲外の値、必須欄の欠け)が 1 件でもあると、何も取り込まずにどこが違うかを表示します。合成に素の `build` を使うと、セッション記録(`out/sessions/*.md`)が消えて詳細ページの「記録を読む」も消えるので、`export` か「集計し直す」を使ってください。

### エージェントやローカルの LLM に渡す

フォルダやファイルを読める相手(GitHub Copilot CLI を自分で開いたもの、ほかのコーディングエージェント、ローカルの LLM の画面など)には、バンドルをそのまま渡せます。このツールは LLM を呼ばず、費用は渡した相手の側で決まります。

画面からは、「判定する…」で判定するものに「工数」、判定の方法に「ZIP にまとめてエージェントに渡す」を選び、4 つの手順に沿って進めます。

1. **ZIP を作る**: 「未判定 N 件で ZIP を作る」を押します。判定済みのセッションを除いたバンドルと ZIP を、同じ回に作ります(下のコマンドと同じ。LLM は呼びません)。「チャットに貼って判定する」の添付ファイルも同じ中身で作り直され、ファイルの番号が振り直されます。
2. **エージェントに渡す**: 「bundle.zip をダウンロード」で保存し(ブラウザの保存先。ふつうは「ダウンロード」フォルダー)、そこで展開して、できた `bundle` フォルダだけをエージェントに開かせます。ZIP を受け取れる相手には、展開せずに添付してもかまいません。画面の依頼文(「bundle フォルダの INSTRUCTIONS.md に従って判定し、結果を bundle フォルダの中の judgments.json に書いてください。」)は「依頼文をコピー」で写せます。書き込みを許可するのは、この `judgments.json` だけにします。ファイルを書けない相手(チャットの画面など)には、依頼文の後ろを「JSON を返してください」に変えて頼みます。画面は、出力先の中の ZIP の場所(フルパス)を出しません。出力先でエージェントを開かせないためです(下の注意)。
3. **結果を取り込む**: エージェントに書かせた `judgments.json` か、返答を保存したファイルを選ぶと中身が欄に入るので、確かめてから「取り込む」を押します(5 MB まで。JSON を返答でもらったときは欄に貼り付けます)。
4. **レポートに反映する**: 「レポートに反映する」を押します。途中までの結果でも取り込めます(残りは、次に作る ZIP に入ります)。

依頼ごとの判定には ZIP がありません(ダイアログでも選べません)。3 の添付ファイルは 1 つで完結するので、そのままどの LLM にも渡せます。

コマンドでは次のとおりです。

```
bin\atlas.exe bundle --unjudged --zip  # out/bundle/ と out/bundle.zip を作る
```

1. `out/bundle.zip` を別のフォルダに写して渡す(または、そこで展開した `bundle` フォルダを開かせる。`out/` は開かせない)。フォルダを読めない相手には `parts/part-01.md` を 1 つずつ渡します(1 ファイルが相手の入力の上限に収まらないときは `--per-part 1` で作り直します)。
2. 「`INSTRUCTIONS.md` に従って判定し、結果を `judgments.json` という 1 つのファイルに書いてください」と頼みます。
3. できたファイルを取り込みます。画面なら「判定する…」→「ZIP にまとめてエージェントに渡す」(「チャットに貼って判定する」でも同じ)の手順 3 でファイルを選んで「取り込む」、コマンドなら `bin\atlas.exe judge import judgments.json` の後に `bin\atlas.exe export`。形が合わない項目が 1 件でもあると何も取り込まず、どこが違うかを出します。途中までの結果でも取り込めます(残りは次の `bundle --unjudged` に入ります)。

- **パケットには他のセッションの依頼文や応答がそのまま入っています。** その中に「このコマンドを実行せよ」のような文があると、ツールを使えるエージェントは従ってしまうことがあります。エージェントに渡すときは、シェルの実行と Web へのアクセスを許可せず、ファイルの書き込みは結果のファイル(`judgments.json`)だけにして、展開したフォルダだけを開かせてください(「このツールが判定する」(2b)は、この制限を付けて Copilot CLI を起動します)。ファイルを書けない相手には、JSON を返答として出してもらい、それを貼るか保存して取り込みます。
- **エージェントを出力先(`out/`)で開かないでください。** `out/judgments.json` はこのツールの判定の保存先です。そこに「`judgments.json` に書いて」と頼むと、今回の分だけの中身で上書きされ、それまでの判定が消えます。`out/` にはほかのセッションの記録もあります。`bundle.zip` は別のフォルダに写してから展開し、書かせるならそのフォルダの中にします(`out/` の中で展開すると `out/bundle/` も書き換わり、画面は ZIP を「まだ作っていません」と表示します)。
- **ターミナルで動くエージェントには、結果をファイルに書かせてください。** 返答で返させて写すと、取り込めないことがあります。GitHub Copilot CLI(1.0.112)で確かめたところ、返答は画面の幅で折り返して出され、JSON の文字列の途中に改行が入り、コードブロックの印も消えて、「JSON を取り出せません」になりました。ファイルに書かせた `judgments.json` は、そのまま取り込めました。対話の画面(`-i`)でも、返答を画面から写したものは取り込めませんでした(返答の JSON は、文字列の途中で画面の幅に合わせて折り返して表示され、1 画面にも収まりません)。ファイルに書かせる形は、対話の画面でも通りました。`-p` で確かめたときの起動の仕方は次のとおりです(展開した `bundle` フォルダの 1 つ上で実行。シェルと URL を拒否し、書き込みは結果のファイルだけを許可する。使用量を記録する指定は省いています)。

  ```
  copilot -p "bundle フォルダの INSTRUCTIONS.md に従って判定し、結果を bundle フォルダの中の judgments.json に書いてください。" --stream off -s --no-ask-user --no-custom-instructions --disable-builtin-mcps --deny-tool shell --deny-tool url --allow-tool "write(bundle/judgments.json)" --model <モデル>
  ```

- 渡す相手が外部のサービスのときは、中身(本文、パス、リポジトリ名)を渡してよいか先に確かめてください。
- 返す形は JSON だけです(ZIP で返してもらう形は用意していません)。
- ローカルの LLM では、1 パケットが最大 24,000 字あるので、入力の上限が小さいモデルでは途中で切れることがあります。このツールでは確かめていません。
- 通して確かめたのは GitHub Copilot CLI だけです。ほかのコーディングエージェントでは確かめていません。

## 2b. このツールの中で判定する(画面から、またはコマンドで)

`atlas.bat` から開いた画面の「判定する…」を押し、判定するものに「工数」、判定の方法に「このツールが判定する」を選ぶと、件数の上限(既定 10)を決める確認が出ます(判定には GitHub Copilot CLI の `copilot -p` を使います)。「〜件を判定する」を押すと、バンドルを作り直し、未判定のセッションを上限まで判定して、レポートを作り直します([screen.md の「画面からの操作」](screen.md#画面からの操作))。従量課金の `anthropic` とモデルの指定は画面からはできません(コマンドの `--backend anthropic` と `--model` だけ。画面からの判定は Copilot に設定してある既定のモデルを使います)。コマンドでは次のとおりです。

```
bin\atlas.exe judge-flow                                    # bundle → judge run → export(画面の「工数を判定する」と同じ)
bin\atlas.exe judge run --limit 5                           # まず 5 件だけ試す
bin\atlas.exe judge run --only <id>,<id>                    # 指定したセッションだけ(ID は先頭でよい。--session も同じ。今の添付に入っているものだけ)
bin\atlas.exe judge run --force                             # 判定済みも判定し直す
bin\atlas.exe judge run --model <モデル名>                      # 判定に使うモデルを指定
bin\atlas.exe judge run --model anthropic/claude-haiku-5-5  # Copilot に保存した自分のモデル(BYOK)を使う
bin\atlas.exe judge-flow --group <タスクタグ>                  # そのタスクタグのセッションだけ判定する
bin\atlas.exe judge-flow --session <id>                     # 1 セッションだけ判定する(--force で判定し直す)
```

### 範囲を絞る(タスクタグ・1 セッション)

- **タスクタグ**: 左の「タスクタグ」でタグを選んでから「判定する…」を開くと、「このツールが判定する」の確認に「判定する範囲」が出て、「タスクタグ「X」のセッションだけ」が選ばれています(「すべてのセッション」にも切り替えられます)。件数もそのタグの中の未判定の数になります。タグを選んでいないときは、タグの側は押せず、理由を出します。「チャットに貼って判定する」「ZIP にまとめてエージェントに渡す」の添付・ZIP は、今までどおり未判定のすべてのセッションで作ります。
- **1 セッション**: `atlas.bat` から開いた詳細ページの表題の下の「LLM 判定」に、「工数を判定する」と「依頼ごとに判定する(未判定 N 件)」が出ます。押すと件数・使うモデル・費用(AI クレジット、BYOK のモデルなら API の利用料)を確認してから、そのセッションだけを判定して、レポートを作り直します。工数が判定済みなら「工数を判定し直す」になり、前の判定を置き換えます(画面から判定し直せるのはここだけです)。依頼ごとは未判定の依頼だけを判定します。押せないときは、理由(依頼の記録が無い・全部判定済み・古い集計など)を下に出します。終わると「読み込み直す」が出ます(自動では読み直しません)。`file://` で開いた詳細ページには出ません。
- **判定したかどうかの見分け方**: 詳細ページの表題の下の印の列に「LLM 判定(工数)✓ 済み / 未判定」と「LLM 判定(依頼ごと)n / m 件」(全部済めば ✓)が出ます。セッション一覧では、工数は「推定人手工数」の列の「未判定」、依頼ごとは「依頼」の列の件数の下の「未判定」「判定 n / m」「✓ 判定済み」で見分けます(依頼ごとの印は、レポートに依頼ごとの判定が 1 件でもあるときだけ出ます)。
- 絞るのは判定する範囲(バンドル)だけで、最後の `export` はいつもレポート全体を作り直します。コマンドの `--group` は `atlas-notes/groups.json` のグループ(画面のタスクタグ)の名前、`--session` は ID の先頭一致です([cli.md](cli.md))。
- 絞ったときのバンドルは、共有の `out/bundle`・`out/turn-bundle`(「チャットに貼って判定する」と M365 Copilot の判定が使い回す、未判定のすべてのセッションの添付)を作り直さず、作業用の `out/judge-work/` に作って、終わったら(失敗しても)消します。判定の結果は、今までどおり `judgments.json`・`turn-judgments.json` に入ります。
- 別のフォルダを開いた画面(読むだけ)では、タスクタグは送った人のもの(画面に出ているもの)で絞ります。判定の処理には、そのタグのセッションの ID を `--session` で渡します([screen.md の「別のフォルダを開く」](screen.md#別のフォルダを開く))。

- `judge run` が判定するのは、作ってある添付(`out/bundle`)のセッションです。絞り込み(`--project`・`--since`・`--group` など)は添付を作るときのもので、`judge run` に付けると止まります(以前は黙って無視し、添付の全体を判定していました)。絞り込んで判定するときは `judge-flow` に付けるか、先に `bundle` に付けて添付を作ります。
- 判定済みのセッションは飛ばすので、途中で止めても続きから再開できます。失敗したセッションは `judgments.json` の `failures` に記録し、次へ進みます(最後に終了コード 1)。
- バックエンドは `--backend` で選びます。

| バックエンド | 中身 | 費用 |
|---|---|---|
| `copilot-cli`(既定) | `copilot -p` を空の作業フォルダで起動し、パケットをプロンプトに埋め込んで渡す | GitHub Copilot のサブスクリプション内で AI クレジット(旧課金では premium request)を消費します(1 セッション 1 回以上) |
| `anthropic` | Anthropic Messages API を直接呼ぶ(既定モデル `claude-sonnet-5-5`、環境変数 `ANTHROPIC_API_KEY` が必要)。**既定のビルドとリリースの `atlas.exe` には入っていません**(下記) | **従量課金**です。明示的に `--backend anthropic` を指定したときだけ使います |

- `anthropic` は、cargo の機能 `anthropic-backend` を付けてビルドした atlas にだけ入っています。HTTP と TLS の依存(ureq・rustls・ring・webpki-roots など 20 ほどのクレート)がこれだけのために要るので、既定のビルド・リリースの `atlas.exe`・起動用の `.bat` がこの PC でするビルドには入れていません。入っていない atlas で `--backend anthropic` を付けると、`judge run` と `skill-draft` は何もせずに、入っていないことと次のビルドの仕方を出して止まります。使うときは、このリポジトリで次を実行し、できた `target\release\atlas.exe` を使います(ビルドに要るものは [development.md](development.md))。

  ```
  npm run build:report
  cargo build --release -p atlas-cli --features anthropic-backend
  ```

- `copilot-cli` は `--add-dir` を使いません(そのフォルダの `.github/skills` / `agents` を信頼設定として読むため、他セッションの本文を含むバンドルが指示の注入口になりうるからです)。ユーザーの AGENTS.md 等も読ませません(`--no-custom-instructions`)。`--allow-all-tools` は既定で付けます(付けたくないときは `--no-allow-tools`)が、判定にツールは要らないので、シェル・ファイルの作成と変更・URL アクセス(`shell` / `write` / `url`)は常に `--deny-tool` で拒否します(`copilot help permissions` によれば拒否は `--allow-all-tools` より優先されます。パケット本文に「コマンドを実行せよ」のような文が含まれていても動かないようにするためです)。MCP のツールはこの 3 種類のどれにも当たらない(`copilot help permissions` で別の種類 `<サーバー名>(ツール名)`)ので、モデルに見せるツールを `--available-tools=view` に絞り(作業フォルダは空で、copilot は既定でその外のパスを読ませません)、組み込みの MCP を `--disable-builtin-mcps` で止め、`copilot mcp list --json`(LLM は呼びません)で得た各サーバーを `--disable-mcp-server` と `--deny-tool <サーバー名>` で止めます。一覧を取れなかったときはサーバーごとの指定を付けずに続け、その旨を判定の notes に残します(copilot 1.0.109 での実走を 2026-11-11 に確認しました。架空のデータで、判定の間にツールの呼び出しは 0 回でした。同じ引数で起動してモデルに尋ねると、使えるツールは `view` だけと答え、作業フォルダの外のファイルを `view` で読もうとすると拒否されました)。プロンプト中のパケットの境界には依頼ごとの乱数を付け、本文側で境界を偽装できないようにしています。
- **Copilot に保存した自分のモデル(BYOK)を使う**: Copilot CLI の `/model` で自分の API キーのモデルを保存してあれば(`~/.copilot/providers.json`。`copilot help providers`)、`--model <プロバイダー名>/<モデル ID>` で指定できます(例: `--model anthropic/claude-haiku-5-5`)。モデル ID だけを書くと `Model "…" is not available` で失敗します(copilot 1.0.109 で確認)。このとき GitHub の AI クレジットは使わず、**提供元の従量課金**になります(工数 2 件の判定で入力 1.3 万・出力 0.3 万トークンほどでした)。`turns run --model` と `bin\atlas.exe judge-flow --model` でも同じです。
- **いつも BYOK のモデルで判定する**: `atlas.config.json` に `"judgeModel": "anthropic/claude-sonnet-5-5"` のように書くと、`--model` を付けないときと、画面の「このツールが判定する」で、そのモデルを使います([cli.md の「判定に使うモデルの指定」](cli.md#判定に使うモデルの指定))。書かないと Copilot の既定のモデルで判定し、AI クレジットを使います。Copilot の既定のモデルは、Copilot CLI の設定(`~/.copilot/settings.json` の `model`)で決まります。そのモデルが使えなくなっていると、`Model "…" is not available` で失敗します。
- 判定自体の使用量は `copilot` の `--usage-output-file` から集計し、`judgments.json` の `judge.usage` に残します。
- `copilot` の場所は環境変数 `ATLAS_COPILOT_BIN` で指定できます(テストでは偽の copilot `fixtures/fake-copilot.mjs` に差し替えています)。
- 月間の AI クレジット(旧課金では premium request)を使い切っていると、どのモデルを指定しても `quota_exceeded HTTP 402` で失敗します(消費はありません)。`judgments.json` の `failures` に残るので、翌月や別のバックエンドで `judge run` を再実行すれば再試行されます。
- 出力の形を調べたいときは環境変数 `ATLAS_JUDGE_RAW_DIR` にフォルダを指定すると、`copilot` の生の stdout / stderr / usage をセッションごとに保存します(パケット本文を含むので共有しないでください)。

## llm-wiki のページごとの判定

工数の判定(上の 1〜2b)の中で、読んだ llm-wiki のページ 1 つずつについて「役立ったか」も LLM に見立てさせます。どの経路(チャットに貼る・M365 Copilot の自動操作・ZIP をエージェントに渡す・このツールが判定する)でも同じパケットと指示を使い、結果は同じ `judgments.json` の項目 `wikiPages` に入ります。レポートでは改善点の「llm-wiki のページごとの参照率と役立った率」と、詳細ページの「LLM による判定(推定)」に出ます([screen.md](screen.md))。**LLM の見立てで、測った値ではありません。** セッション全体の `wikiEffect`(−2〜+2)はそのまま残します。

| 項目 | 値 |
|---|---|
| `page` | パケットに書いたページの名前をそのまま(vault からの相対。vault を複数指定したときは先頭に vault の名前) |
| `helpful` | `yes`: そのページの中身が後の作業(判断・コード・回答)に使われ、作業を進めた / `no`: 読んだが使われなかった、または誤った方向に導いた / `unknown`: 記録から判断できない |
| `reason` | 根拠を 1 文で(どの抜粋・依頼・応答・変更から判断したか) |

- **パケットに載せるもの**: パケットの「指示ファイル・llm-wiki の参照」の中の「llm-wiki のページごとの判定」に、読んだページ(重複を除いて読んだ順)ごとに、読んだ時刻と何番目の依頼の中か、読んだ後に同じ依頼の中で呼んだツール(5 件まで。内部ツールを除く)、**抜粋**(そのページを読んだツールの結果の先頭)を並べます。その後の流れ(依頼・最終応答・変更ファイル)はパケットのほかの節にあるので、足していません。
- **抜粋を取る呼び出し**: ログの全文(スナップショットの `events.jsonl`)の呼び出しごとに、集計と同じ分類(今の設定 `atlas.config.json` の `wikis` の vault の指定)を当て、そのページを読んだと分類された呼び出しから取ります。書き込みのツールと、サブエージェントへの依頼(`task` など。引数は依頼文で、結果はページの中身ではない)は読み取りにしません。ページの名前の直後に名前の続きがあるもの(`a.md.bak` など)も、そのページの読み取りにしません。失敗した呼び出しと結果の本文が無い呼び出しは飛ばし、後の読み取りから取ります。結果(`result` の `content`、無ければ `detailedContent`)は、秘密らしい文字列を全文で伏せてから(秘密情報の検査と同じ規則)切ります。1 回の呼び出し(検索など)で複数のページを読んだときは、それらのページに同じ抜粋を載せ、「ほかのページと同じ結果の抜粋」と書きます。
- **設定に vault の指定が無いとき**(集計した後に設定を変えたなど): 引数に「/<ページ>」の形で名前が出る呼び出しを読み取りとします(区切りのまとめ方は集計と同じ)。この場合、vault の直下のページ(`AGENTS.md` など)は、プロジェクトの同じ名前のファイルと見分けられません。設定の指定が集計したときと違うと、ページの名前が合わず、抜粋を取れないことがあります。
- **抜粋が無いとき**: 成功して結果の本文がある読み取りがログに無いとき、読んだ呼び出しを特定できないとき、ログの全文が無いとき(`session-store.db` か sessions.json の抜粋で代用したとき)は「抜粋なし」と書き、名前と前後の流れだけで判断して、決め手が無ければ `unknown` にするよう指示に書いてあります。
- **上限**: 判定に載せるのは 1 セッション 10 ページまで(`crates/atlas-core/src/wiki.rs` の `WIKI_JUDGED_PAGES_MAX`。読んだ順の先頭から)で、残りはパケットに「上限のため判定しません」と件数を書き、未判定にします。抜粋は 1 ページ 400 字まで(`PacketLimits` の `wikiExcerptChars`)で、パケットが 24,000 字に収まらないときは、ほかの本文と一緒に段階的に短くします(ページの並びは変えません)。
- **返答の扱い**: `wikiPages` は必須ではありません(版 1 の指示で作った返答もそのまま取り込めます)。無いときは、ほかの判定を取り込み、そのセッションのページを未判定にします(知らせません)。壊れているとき(配列でない、または要素の形が合わない(`page` が無い、`helpful` が 3 つの値のどれでもない)・同じページが 2 回ある)は、ほかの判定を取り込み、壊れた分のページを未判定にして、ログに知らせます(`judge import`・M365 Copilot の自動操作のログ。画面の「取り込む」では画面には出さず atlas のログに書きます。`judge run` は該当したセッションの件数と ID を 1 行にまとめて出します)。パケットに無いページの名前を返したものは、レポートを作るときに捨てます。
- **版**: `judgments.json` のスキーマの版は 2(`wikiPages` を足した版)です。版 1 の `judgments.json` も読み、その判定のページは未判定として数えます。書くときは、どの項目も `wikiPages` を持たない間は版 1 のまま書き、`wikiPages` を持つ項目ができたら版 2 で書きます。**版 2 で書いた `judgments.json` は、この機能より前の atlas.exe では読めず、`build`(レポートを作る)が止まります。** 前の版の atlas.exe に戻すときは、`judgments.json` を控えてから戻してください。バンドル(添付ファイル)を作り直してから判定し直すと(`bin\atlas.exe bundle --session <id>` の後に `judge run --only <id> --force`、または作り直した添付ファイルをチャットに貼る)、ページごとの判定が付きます。
- 判定は今までどおり利用者が回したときだけで、集計(`atlas.bat`・`build`・`export`)は LLM を呼びません。

## 3. 依頼ごとの採用

工数の判定(上の 1〜2b)とは別の判定です。工数はセッション 1 件を単位に、依頼ごとの採用は依頼 1 件を単位に判定します。渡す材料(工数はセッション全体の要約、採用は依頼とその次の依頼の文)も、結果のファイル(`judgments.json` と `turn-judgments.json`)も、件数の上限も別々なので、片方だけを回せます。レポートでは、同じ表に別の列で並びます。

依頼(ターン)ごとに、AI の成果が利用者にどう扱われたかを LLM に判定させます。判定の単位は依頼 1 件で、材料はその依頼の文・AI の最後の応答・規則による推定(工程・ツールの回数・失敗・拒否・中断)と、**次の依頼の文**です。結果は `out/turn-judgments.json` に貯まり、次の `export`(画面の「レポートに反映する」「集計し直す」)でレポートの「工程と詰まり」と詳細ページ、表(`turns.csv` の「判定:」の列)に出ます。**推定です**。セッションの後に手で直した分やコミットしなかった分は、ログに無いので見えません。

| 項目 | 値 |
|---|---|
| `kind`(依頼の種類) | `task`(作業)/ `question`(質問)/ `fix`(修正)/ `revert`(差し戻し)/ `continue`(続行) |
| `outcome`(扱い) | 作業の依頼: `as_is`(そのまま採用)/ `fix_content`(中身を修正して採用)/ `fix_style`(体裁を修正して採用)/ `rejected`(不採用)/ `unknown`(判定不能)。質問の依頼: `helpful`(役に立った)/ `follow_up`(追加で聞いた)/ `off_target`(的外れ)/ `unknown` |
| `mismatch`(合わなかった点。中身・体裁の修正、不採用、的外れのときだけ) | `requirement`(意図・要件の取り違え)/ `defect`(誤り・不具合)/ `quality`(品質・体裁・決まりごと)/ `scope`(やり過ぎ・足りない)/ `environment`(環境・ツール・権限)/ `other` |
| `phase`(普段の工程) | `atlas.config.json` の `phases`(無ければ 要件定義 / 設計 / 実装 / テスト / レビュー / 調査 / 運用 / その他)のどれか |
| `confidence` / `note` | 確信度(0〜1)と、判定の理由(1〜2 文) |

- **セッションの最後の依頼**には次の依頼が無いので「判定不能」です。拒否・中断の回数は次の依頼の文の裏付けにだけ使い、回数だけでは不採用にしません。AI が確認や選択肢を返しただけの依頼も、まだ扱う成果が無いので判定不能です。レポートでは件数を出したうえで採用率の分母から外します。
- **判定に渡す順番**: 添付ファイルと `copilot -p` に渡す塊は、次の依頼がある依頼(採用を判定できる依頼)を先に並べます。セッションの最後の依頼は、どのセッションでも 1 件だけの塊にして後ろへ回し、判定できる依頼と同じ添付ファイルには入れません。後ろの分は種類と工程だけが決まります。採用率だけを見たいときは、先頭の分だけ判定すれば足ります(そのとき、種類別・工程別の表には、最後の依頼は入りません)。どこまでが先頭の分かは、次のところに出ます。
  - 画面の「チャットに貼って判定する」: 手順 1 に「採用を判定できる依頼は N 件で、先頭の M ファイルに入っています」と出ます。ファイルの一覧では、後ろのファイルに「最後の依頼だけ」と付き、次に渡すファイルがそこに入ったら「ここで止めて手順 4 へ進めます」と出ます。
  - コマンド: 添付ファイルを作ったときのログ(`turns bundle: 採用を判定できる依頼(次の依頼がある依頼)は N 件で、先頭の M ファイルと先頭の K 個の塊に入れました…`)と、`out/turn-bundle/manifest.json` の `decidable`(`turns`・`chunks`・`parts`)。GitHub Copilot CLI で回すときは、`turns bundle --unjudged` の直後に `turns run --limit N`(N は `decidable.turns`)で、先頭の分をちょうど回せます。
- **普段の工程名を変える**: リポジトリ直下の `atlas.config.json` に `"phases": ["要件定義", "設計", "実装", "テスト", "レビュー"]` のように書きます(2 つ以上、重複なし)。変えた後は判定し直すまで、前の名前の判定はそのまま残り、レポートでも前の名前の行に出ます。返答の取り込みでは、添付ファイルを作ったときの工程名と今の工程名のどちらも受け付けます(添付を作った後に名前を変えても、その添付への返答を取り込めます)。

### チャットに貼る(M365 Copilot など。既定)

「判定する…」で「依頼ごとの採用」と「チャットに貼って判定する」を選び、[2a](#画面からおすすめ) と同じ 4 つの手順で進めます。**添付ファイルには、セッション ID・題名・プロジェクトのパス・依頼文(1 件 1,500 字まで)・AI の応答(900 字まで)がそのまま入ります**(応答にはユーザー名を含むパスが出ることがあります)。渡してよい相手か確かめてください。添付ファイルは依頼 24 件ずつ(`out/turn-bundle/parts/`、1 ファイル 6 万字ほどまで)で、ダウンロードの名前は `turns-part-01.txt` などです。全部の依頼を判定するには、依頼 1,000 件でおよそ 40〜50 往復です。採用率だけなら、画面の手順 1 に出る「先頭の M ファイル」までで足ります(上の「判定に渡す順番」)。

コマンドでは次のとおりです。

```
bin\atlas.exe turns bundle --unjudged  # out/turn-bundle/ を作る(判定済みの依頼を除く。LLM は呼ばない)
bin\atlas.exe turns import 返答.md       # チャットの返答を out/turn-judgments.json に取り込む
bin\atlas.exe export                   # レポートに反映する
```

### GitHub Copilot CLI で回す

「判定する…」で「依頼ごとの採用」と「このツールが判定する」を選び、件数(依頼の数の上限。既定 60)を決めて実行します。依頼を最大 6 件ずつまとめて `copilot -p` を 1 回呼ぶので、AI クレジットは依頼 6 件ほどにつき 1 回分です(セッションの最後の依頼は 1 件で 1 回。後ろに回るので、件数の上限が判定できる依頼の数以下なら呼びません)。安全策(ツールの拒否、MCP の停止、空の作業フォルダ)は工数の判定と同じです。`--backend anthropic`(従量課金の API を直接呼ぶ)は、依頼ごとの判定には使えません。件数の上限は依頼のまとまりごとに確かめるので、上限を少し超えて判定することがあります(上限 12 で 14 件など)。工数と同じく、左でタスクタグを選んでいればそのタグのセッションの依頼だけに絞れ、詳細ページの「依頼ごとに判定する(未判定 N 件)」でそのセッションの未判定の依頼だけを判定できます([2b の「範囲を絞る」](#範囲を絞るタスクタグ1-セッション))。

```
bin\atlas.exe judge-flow --turns --limit 60             # turns bundle --unjudged → turns run → export
bin\atlas.exe turns run --limit 60                      # 判定だけ(先に turns bundle が要る)
bin\atlas.exe judge-flow --turns --group <タスクタグ>       # そのタスクタグのセッションの依頼だけ
bin\atlas.exe judge-flow --turns --session <id>         # 1 セッションの依頼だけ
```

判定できなかった塊(返答の形が合わない、クレジットの上限など)は `turn-judgments.json` の `failures` に残り、もう一度実行すると再試行します。
