# 推定人手工数の判定

[README](../README.md) に戻る。

「同じ作業を人が AI なしでやったら何時間かかるか」は LLM に推定させます。集計(LLM なし)とは別の手順で、結果は `out/judgments.json` に貯まり、次の `atlas build` でレポートに合成されます。判定は外部の LLM でも、このツールの中からでも回せます(どちらも同じ形式です)。

**推定は推定です。** レポートには幅(low〜high)と確信度を一緒に出しますが、人手での実測ではありません。

## 1. 評価バンドルを作る(LLM は呼ばない)

```
npm run atlas            # まだなら先に集計(out/sessions.json と out/snapshot を作る)
npm run atlas -- bundle  # out/bundle/ を作る。--project / --since / --client などで対象を絞れる
```

`out/bundle/` の中身:

| ファイル | 内容 |
|---|---|
| `INSTRUCTIONS.md` | 判定する LLM への指示(役割・評価軸・出力形式・手順)。最初に読ませる |
| `manifest.json` | パケットの一覧(セッション ID とファイルの場所、件数、サイズ) |
| `schema.json` | 返してもらう `judgments.json` の JSON Schema |
| `sessions/<セッション ID>.md` | 評価パケット。依頼文、最終応答、変更ファイル、ツール / skill / agent / hook、ターン数・時間・トークン、摩擦、指示ファイル・wiki の参照、compaction 要約 |
| `parts/part-<番号>.md` | ZIP やフォルダを渡せない相手(テキストの添付だけの M365 Copilot など)用。指示・JSON Schema と、パケット数件(既定 5 件。`--per-part <n>` で変更)を 1 ファイルにまとめたもの。パケットはファイルごとの乱数の境界で囲み、本文の中の指示に従わないよう指示に書いてある。中身は `sessions/` と同じ |

- 依頼の記録が無いセッション(開いただけで使っていないもの)はパケットにしません(`manifest.json` の `skipped` に理由付きで載ります)。含めたいときは `--include-empty`。
- 本文はスナップショットのログから全文を読み直しますが、1 パケット 24,000 字に収まるよう長い本文は中略します(中略した箇所には字数を書きます)。
- **パケットには依頼文や応答の本文、パス、リポジトリ名がそのまま入ります。** 外部のサービスに渡す前に中身を確認してください。

## 2a. 外部の LLM で判定する(M365 Copilot など)

### 画面から(おすすめ)

`atlas.bat` から開いた画面の「判定する…」で、判定するものに「工数」、判定の方法に「チャットに貼って判定する(M365 Copilot など)」を選びます。あとは画面の 4 つの手順に沿って進めます。ターミナルもファイルの置き場所も気にしなくてかまいません。

1. **添付ファイルを作る**: 「未判定 N 件で作る」を押します。判定済みのセッションを除いて、5 件ずつのファイルにまとめます(LLM は呼びません)。作ったあとは「作成済み」と出ます。「作り直す」はファイルの番号が振り直されるので、途中のファイルをダウンロード済みなら押さないでください。作れなかったときは、ボタンの下に「添付ファイルを作れませんでした」と理由(処理が「atlas: 失敗しました: 」に続けて書いた文)、ログ(折りたたみ)が出ます。原因を直してから、もう一度押してください。新しいものは別の場所に作り終えてから入れ替えるので、作り直しに失敗しても、前に作った添付ファイルはそのまま使えます(「作成済み」のまま。返答の取り込みも続けられます)。途中で止めたときは「添付ファイルの作成を止めました」と出ます。この知らせは、ダイアログを閉じるか、次に作れたら消えます(画面を読み込み直した後には出ません)。
2. **チャットに渡す**: 「part-01.txt をダウンロード」を押し、ブラウザの保存先(ふつうは「ダウンロード」フォルダー)に入ったファイルをチャットに添付します。画面の依頼文(「添付したファイルの指示に従って判定し、JSON を返してください。」)を「依頼文をコピー」で写して送ります。添付できないときは「本文をコピー」で中身を貼り付けます。保存は `.txt` にしています。相手が `.md` を受け付けるか分からないためで、中身は `part-01.md` と同じです。
3. **返答を取り込む**: チャットの返答をまるごとコピーして欄に貼り、「取り込む」を押します。説明文が混じっていてもかまいません(JSON のコードブロックだけを読みます)。形が合わない項目が 1 件でもあると何も取り込まず、何件目のどのセッションのどの欄が違うかを出します(貼った返答は欄に残ります)。その場合は「直す点をコピー」で一覧を写してチャットに貼り、「この点を直した JSON をもう一度返してください」と頼むか、同じファイルをもう一度判定させてください。取り込むと次のファイルに進みます。
4. **レポートに反映する**: 何ファイルか取り込んだら「レポートに反映する」を押します。レポートの作り直し(`export`)が終わると帯に「再読み込み」が出ます。

どの手順も AI クレジットを使いません(判定するのはチャットの側です)。「ファイルの一覧」を開くと、どのファイルが取り込み済みかを確かめられ、どのファイルでも保存・コピーできます。

### M365 Copilot のアプリを自動で操作する(Windows)

手順 2〜4 を手でする代わりに、開いている M365 Copilot のアプリをこのツールが操作します(Windows の UI Automation。Windows PowerShell で動きます)。

1. M365 Copilot のアプリを開いてサインインし、チャットの画面を出しておきます(Edge で `m365.cloud.microsoft` を開いた画面も探しますが、確かめたのはアプリだけです)。
2. 「判定する…」→「チャットに貼って判定する」で添付ファイルを作り、手順 2 の「M365 Copilot で自動で判定する」の「M365 Copilot で N ファイルを判定する」を押します。
3. 未判定のファイルを 1 つずつ、新しいチャットで送ります。1 つごとに、モデルの選択で **Think Deeper** を選び(既に選ばれていればそのまま)、「画像とファイルのアップロード」でファイル(`part-01.txt` など)を添付し、依頼文を入れて送り、返答が終わるまで待って、返答の文字を取り込みます。全部終わると、取り込めた分をレポートに反映します(`export`)。

- **終わるまで M365 Copilot の画面に触らないでください。** 1 ファイルに数分かかることがあります(1 ファイルの待ち時間の上限は 900 秒)。
- 添付したファイルは、手で添付したときと同じく **OneDrive に入ります**(M365 Copilot の決まり)。
- 返答は `out/bundle/replies/<名前>.md`(依頼ごとの判定は `out/turn-bundle/replies/`)に残します。画面から読んだ文字はコードブロックに行番号とボタンの名前が混じるので、`<名前>.md` には ```json のブロックに組み立て直したものを、`<名前>.raw.txt` には読んだままの文字を置きます。形が合わずに取り込めなかった返答は、直して「返答を取り込む」に貼るか `judge import` で取り込めます。そのファイルは次の回にもう一度送ります。
- 画面の要素(「新しいチャット」、モデルの選択、「ソースの追加と管理」、送信、返答のコピーのボタンなど)が見つからないときは、何を探していたかを出して止まり、残りのファイルは送りません。M365 Copilot の画面の作りが変わると、この操作は動かなくなります。そのときは手順 2〜4 を手で行ってください。
- 判定するのは M365 Copilot なので、このツールは AI クレジットを使いません。

コマンドでは次のとおりです(`--model` は M365 Copilot のモデルの選択の名前。`Auto` / `Quick Response` / `Think Deeper`。`--limit` は送るファイルの数、`--timeout` は 1 ファイルの待ち時間の秒数)。

```
npm run atlas -- bundle --unjudged          # 添付ファイルを作る(まだなら)
npm run atlas -- judge m365                  # 未判定のファイルを M365 Copilot で判定して取り込み、レポートに反映する
npm run atlas -- turns m365 --limit 2        # 依頼ごとの判定(turns bundle --unjudged で作ったもの)を 2 ファイルだけ
```

### コマンドで

渡し方は、相手が受け取れる形で選びます。

- **テキストの添付だけのとき(M365 Copilot など)**: `out/bundle/parts/` の `part-01.md` を 1 つ添付し、「このファイルの指示に従って判定して」と頼みます。指示・JSON Schema・パケット数件が 1 ファイルに入っているので、ほかのファイルは要りません。返答を保存して取り込んだら、`part-02.md`、`part-03.md` … と続けます。1 ファイルは最大 12 万字ほど(5 件 × 24,000 字)です。途中のセッションの判定が抜けるときは `--per-part 2` などで件数を減らして作り直してください。
- **ZIP を渡せるとき**: `out/bundle` フォルダを**フォルダごと ZIP にし**(エクスプローラーで右クリック →「圧縮先」→「ZIP ファイル」。このツールは ZIP を作りません。依存を増やさないため)、添付して「`INSTRUCTIONS.md` に従って判定して」と頼みます。件数が多いときは何回かに分けて返してもらってかまいません。

返ってきた JSON(または JSON のコードブロックを含む返答をそのまま貼った `.md` / `.txt`)を保存し、取り込みます。分けて返ってきた分は 1 つずつ取り込めます。

```
npm run atlas -- judge import 返答.md     # 検証して out/judgments.json に取り込む(同じセッションは上書き)
npm run atlas -- export                   # レポートに合成(画面の「集計し直す」でもよい)
```

形が合わない項目(範囲外の値、必須欄の欠け)が 1 件でもあると、何も取り込まずにどこが違うかを表示します。合成に素の `build` を使うと、セッション記録(`out/sessions/*.md`)が消えて詳細ページの「記録を読む」も消えるので、`export` か「集計し直す」を使ってください。

## 2b. このツールの中で判定する(画面から、またはコマンドで)

`atlas.bat` から開いた画面の「判定する…」を押し、判定するものに「工数」、判定の方法に「このツールが判定する」を選ぶと、件数の上限(既定 10)を決める確認が出ます(判定には GitHub Copilot CLI の `copilot -p` を使います)。「〜件を判定する」を押すと、バンドルを作り直し、未判定のセッションを上限まで判定して、レポートを作り直します([screen.md の「画面からの操作」](screen.md#画面からの操作))。従量課金の `anthropic` とモデルの指定は画面からはできません(コマンドの `--backend anthropic` と `--model` だけ。画面からの判定は Copilot に設定してある既定のモデルを使います)。コマンドでは次のとおりです。

```
npm run atlas:judge                               # bundle → judge run → export(画面の「工数を判定する」と同じ。伏せ字版は build)
npm run atlas -- judge run --limit 5              # まず 5 件だけ試す
npm run atlas -- judge run --only <id>,<id>       # 指定したセッションだけ
npm run atlas -- judge run --force                # 判定済みも判定し直す
npm run atlas -- judge run --model <モデル名>      # 判定に使うモデルを指定
npm run atlas -- judge run --model anthropic/claude-haiku-5-5   # Copilot に保存した自分のモデル(BYOK)を使う
```

- 判定済みのセッションは飛ばすので、途中で止めても続きから再開できます。失敗したセッションは `judgments.json` の `failures` に記録し、次へ進みます(最後に終了コード 1)。
- バックエンドは `--backend` で選びます。

| バックエンド | 中身 | 費用 |
|---|---|---|
| `copilot-cli`(既定) | `copilot -p` を空の作業フォルダで起動し、パケットをプロンプトに埋め込んで渡す | GitHub Copilot のサブスクリプション内で AI クレジット(旧課金では premium request)を消費します(1 セッション 1 回以上) |
| `anthropic` | Anthropic Messages API を直接呼ぶ(既定モデル `claude-sonnet-5-5`、環境変数 `ANTHROPIC_API_KEY` が必要) | **従量課金**です。明示的に `--backend anthropic` を指定したときだけ使います |

- `copilot-cli` は `--add-dir` を使いません(そのフォルダの `.github/skills` / `agents` を信頼設定として読むため、他セッションの本文を含むバンドルが指示の注入口になりうるからです)。ユーザーの AGENTS.md 等も読ませません(`--no-custom-instructions`)。`--allow-all-tools` は既定で付けます(付けたくないときは `--no-allow-tools`)が、判定にツールは要らないので、シェル・ファイルの作成と変更・URL アクセス(`shell` / `write` / `url`)は常に `--deny-tool` で拒否します(`copilot help permissions` によれば拒否は `--allow-all-tools` より優先されます。パケット本文に「コマンドを実行せよ」のような文が含まれていても動かないようにするためです)。MCP のツールはこの 3 種類のどれにも当たらない(`copilot help permissions` で別の種類 `<サーバー名>(ツール名)`)ので、モデルに見せるツールを `--available-tools=view` に絞り(作業フォルダは空で、copilot は既定でその外のパスを読ませません)、組み込みの MCP を `--disable-builtin-mcps` で止め、`copilot mcp list --json`(LLM は呼びません)で得た各サーバーを `--disable-mcp-server` と `--deny-tool <サーバー名>` で止めます。一覧を取れなかったときはサーバーごとの指定を付けずに続け、その旨を判定の notes に残します(copilot 1.0.109 での実走を 2026-11-11 に確認しました。架空のデータで、判定の間にツールの呼び出しは 0 回でした。同じ引数で起動してモデルに尋ねると、使えるツールは `view` だけと答え、作業フォルダの外のファイルを `view` で読もうとすると拒否されました)。プロンプト中のパケットの境界には依頼ごとの乱数を付け、本文側で境界を偽装できないようにしています。
- **Copilot に保存した自分のモデル(BYOK)を使う**: Copilot CLI の `/model` で自分の API キーのモデルを保存してあれば(`~/.copilot/providers.json`。`copilot help providers`)、`--model <プロバイダー名>/<モデル ID>` で指定できます(例: `--model anthropic/claude-haiku-5-5`)。モデル ID だけを書くと `Model "…" is not available` で失敗します(copilot 1.0.109 で確認)。このとき GitHub の AI クレジットは使わず、**提供元の従量課金**になります(工数 2 件の判定で入力 1.3 万・出力 0.3 万トークンほどでした)。`turns run --model` と `npm run atlas:judge -- --model` でも同じです。
- **いつも BYOK のモデルで判定する**: `atlas.config.json` に `"judgeModel": "anthropic/claude-sonnet-5-5"` のように書くと、`--model` を付けないときと、画面の「このツールが判定する」で、そのモデルを使います([cli.md の「判定に使うモデルの指定」](cli.md#判定に使うモデルの指定))。書かないと Copilot の既定のモデルで判定し、AI クレジットを使います。Copilot の既定のモデルは、Copilot CLI の設定(`~/.copilot/settings.json` の `model`)で決まります。そのモデルが使えなくなっていると、`Model "…" is not available` で失敗します。
- 判定自体の使用量は `copilot` の `--usage-output-file` から集計し、`judgments.json` の `judge.usage` に残します。
- `copilot` の場所は環境変数 `ATLAS_COPILOT_BIN` で指定できます(テストでは偽の copilot `fixtures/fake-copilot.mjs` に差し替えています)。
- 月間の AI クレジット(旧課金では premium request)を使い切っていると、どのモデルを指定しても `quota_exceeded HTTP 402` で失敗します(消費はありません)。`judgments.json` の `failures` に残るので、翌月や別のバックエンドで `judge run` を再実行すれば再試行されます。
- 出力の形を調べたいときは環境変数 `ATLAS_JUDGE_RAW_DIR` にフォルダを指定すると、`copilot` の生の stdout / stderr / usage をセッションごとに保存します(パケット本文を含むので共有しないでください)。

## 3. 依頼ごとの採用(段階 2)

依頼(ターン)ごとに、AI の成果が利用者にどう扱われたかを LLM に判定させます。判定の単位は依頼 1 件で、材料はその依頼の文・AI の最後の応答・規則による推定(工程・ツールの回数・失敗・拒否・中断)と、**次の依頼の文**です。結果は `out/turn-judgments.json` に貯まり、次の `export`(画面の「レポートに反映する」「集計し直す」)でレポートの「工程と詰まり」と詳細ページ、表(`turns.csv` の「判定:」の列)に出ます。**推定です**。セッションの後に手で直した分やコミットしなかった分は、ログに無いので見えません。

| 項目 | 値 |
|---|---|
| `kind`(依頼の種類) | `task`(作業)/ `question`(質問)/ `fix`(修正)/ `revert`(差し戻し)/ `continue`(続行) |
| `outcome`(扱い) | 作業の依頼: `as_is`(そのまま採用)/ `fix_content`(中身を修正して採用)/ `fix_style`(体裁を修正して採用)/ `rejected`(不採用)/ `unknown`(判定不能)。質問の依頼: `helpful`(役に立った)/ `follow_up`(追加で聞いた)/ `off_target`(的外れ)/ `unknown` |
| `mismatch`(合わなかった点。中身・体裁の修正、不採用、的外れのときだけ) | `requirement`(意図・要件の取り違え)/ `defect`(誤り・不具合)/ `quality`(品質・体裁・決まりごと)/ `scope`(やり過ぎ・足りない)/ `environment`(環境・ツール・権限)/ `other` |
| `phase`(普段の工程) | `atlas.config.json` の `phases`(無ければ 要件定義 / 設計 / 実装 / テスト / レビュー / 調査 / 運用 / その他)のどれか |
| `confidence` / `note` | 確信度(0〜1)と、判定の理由(1〜2 文) |

- **セッションの最後の依頼**には次の依頼が無いので「判定不能」です。拒否・中断の回数は次の依頼の文の裏付けにだけ使い、回数だけでは不採用にしません。AI が確認や選択肢を返しただけの依頼も、まだ扱う成果が無いので判定不能です。レポートでは件数を出したうえで採用率の分母から外します。
- **判定に渡す順番**: 添付ファイルと `copilot -p` に渡す塊は、次の依頼がある依頼(採用を判定できる依頼)を含むものを先に並べます。セッションの最後の依頼だけの塊(1 依頼だけのセッションなど)は後ろです。こちらは種類と工程だけが決まります。採用率だけを見たいときは、先頭の分だけ判定すれば足ります。何ファイル目までがそれに当たるかは、添付ファイルを作ったときのログ(`turns bundle: 採用を判定できる依頼…は N 件で、先頭の M ファイルに入れました`)と、`out/turn-bundle/manifest.json` の `decidable` に出ます。
- **普段の工程名を変える**: リポジトリ直下の `atlas.config.json` に `"phases": ["要件定義", "設計", "実装", "テスト", "レビュー"]` のように書きます(2 つ以上、重複なし)。変えた後は判定し直すまで、前の名前の判定はそのまま残り、レポートでも前の名前の行に出ます。返答の取り込みでは、添付ファイルを作ったときの工程名と今の工程名のどちらも受け付けます(添付を作った後に名前を変えても、その添付への返答を取り込めます)。

### チャットに貼る(M365 Copilot など。既定)

「判定する…」で「依頼ごとの採用」と「チャットに貼って判定する」を選び、[2a](#画面からおすすめ) と同じ 4 つの手順で進めます。**添付ファイルには、セッション ID・題名・プロジェクトのパス・依頼文(1 件 1,500 字まで)・AI の応答(900 字まで)がそのまま入ります**(応答にはユーザー名を含むパスが出ることがあります)。渡してよい相手か確かめてください。添付ファイルは依頼 24 件ずつ(`out/turn-bundle/parts/`、1 ファイル 6 万字ほどまで)で、ダウンロードの名前は `turns-part-01.txt` などです。全部の依頼を判定するには、依頼 1,000 件でおよそ 40〜50 往復です。

コマンドでは次のとおりです。

```
npm run atlas -- turns bundle --unjudged     # out/turn-bundle/ を作る(判定済みの依頼を除く。LLM は呼ばない)
npm run atlas -- turns import 返答.md         # チャットの返答を out/turn-judgments.json に取り込む
npm run atlas -- export                       # レポートに反映する
```

### GitHub Copilot CLI で回す

「判定する…」で「依頼ごとの採用」と「このツールが判定する」を選び、件数(依頼の数の上限。既定 60)を決めて実行します。依頼を最大 6 件ずつまとめて `copilot -p` を 1 回呼ぶので、AI クレジットは依頼 6 件ほどにつき 1 回分です。安全策(ツールの拒否、MCP の停止、空の作業フォルダ)は工数の判定と同じです。`--backend anthropic`(従量課金の API を直接呼ぶ)は、依頼ごとの判定には使えません。件数の上限は依頼のまとまりごとに確かめるので、上限を少し超えて判定することがあります(上限 12 で 14 件など)。

```
npm run atlas:judge -- --turns --limit 60     # turns bundle --unjudged → turns run → export
npm run atlas -- turns run --limit 60         # 判定だけ(先に turns bundle が要る)
```

判定できなかった塊(返答の形が合わない、クレジットの上限など)は `turn-judgments.json` の `failures` に残り、もう一度実行すると再試行します。
