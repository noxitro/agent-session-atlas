# 出力ファイル

[README](../README.md) に戻る。コマンドの一覧は [cli.md](cli.md) にあります。

## セッション記録(Markdown)

セッションの経過を 1 ファイルの Markdown にして、LLM に渡して振り返ったり、自分で経過を読んだりするための出力です。依頼文や応答・パスがそのまま入るので、人に渡すなら中身を確かめてからにしてください。集計と同じスナップショットから作り、LLM は呼びません。

```
bin\atlas.exe export                     # build と同じ絞り込みで、全セッションの .md を out/sessions/ に書く
bin\atlas.exe export --since 2026-10-01  # 期間で絞る(--project / --client / --model / --branch も同じ)
bin\atlas.exe export --tool-output all   # 成功したツールの結果も入れる(容量が数倍になる)
```

`atlas.bat`(`all`)は既定の中身(`--tool-output fail`、上限 20,000 字)で記録も作ります。`atlas.bat` から開いた詳細ページの「記録を読む」で、その場で読めます([screen.md の「画面からの操作」](screen.md#画面からの操作))。中身を変えたいとき(`--tool-output all`、`--max-chars`)は上のコマンドで作り直します。

記録 1 件(`out/sessions/<セッション ID>.md`)の中身:

| 節 | 内容 |
|---|---|
| 概要 | ID・プロジェクト・クライアント・リポジトリ・作業フォルダ・Copilot の版・開始と所要時間・依頼と応答の数・トークンと AIU・ツール呼び出し(失敗・拒否)・摩擦・変更行数 |
| 役 × モデルの消費 | 本体とサブエージェント(名前)× モデルごとのリクエスト数・入力・出力・キャッシュ読取・AIU と、待ち時間(最初のトークンまで / 全体)の中央値と p90。`session-store.db` と `usage_record` のリクエスト単位の明細から |
| ツールの内訳 | ツール別の回数・失敗・拒否 |
| 経過 | 開始からの相対時刻つきの時系列。依頼(本文、モード)、応答(本文、モデル)、ツール呼び出し 1 回 1 行(名前・引数の要約・成否・所要時間・失敗の理由)、サブエージェントの開始と完了(`[agent:名前]` を付けた中の発言とツール)、compaction(要約は折りたたみ)、権限確認、エラー、中断、モード・モデルの変更、終了時の変更行数。5 分以上の空白は「待ち」。依頼ごとに本体の消費(リクエスト数・トークン・AIU・所要)を 1 行 |
| 変更したファイル | 変更・作成・削除の一覧 |
| 秘密情報の検査 | 伏せた件数(下記) |
| 分析の観点 | LLM に渡して振り返るときの定型の観点(時間とトークンの内訳、手戻り、失敗と回復、compaction、委譲、依頼の質) |

- **既定ではツールの結果は失敗したときだけ入れます**(`--tool-output fail`)。成功した結果はログの容量の大半を占めるためで、必要なら `--tool-output all`。内部ツール(`report_intent`)は書きません。
- 長い本文は上限(`--max-chars`、既定 20,000 字。ツールの結果は 4,000 字)で中略し、中略した箇所に字数を書きます。LLM に渡す前に全体の長さを確認してください(長いセッションは 1 件で数十万字になります)。
- **秘密情報**: API キーやトークンらしい文字列(GitHub / OpenAI・Anthropic / AWS / Slack / Google のキー、秘密鍵、JWT、Bearer)は形式で見つけて `[伏せました: 種類]` に置き換え、件数を記録の末尾と `export` のログに出します。形式で探しているだけなので偽陽性・見逃しがあります。本物が見つかったら元の記録(`~/.copilot`)にも残っているので鍵を作り直してください。共有する前に中身は必ず確認してください。
- スナップショットに `events.jsonl` が無いセッション(`session-store.db` にだけあるもの、`--since` で複製対象外だったもの)は、`sessions.json` に残る最初の依頼と最後の応答だけの記録になり、その旨を書きます。
- `export` は `build` を含むので、レポートと詳細ページも作り直されます。逆に素の `build` を実行すると `.md` は消え、詳細ページのリンクも消えます(フィルタで減ったセッションの古い記録を残さないため)。`all`(`atlas.bat`・`bin\atlas.exe`・画面の「集計し直す」)と判定(画面の「工数を判定する」・`bin\atlas.exe judge-flow`)は記録も作るので消えません。
- 同じ目的の既存ツールとの関係: agent-toolkit の `copilot-session-export`(アプリの中から `/export` `/export-usage` でその場で書き出す)と `copilot-usage-export`(PowerShell だけで動く日次バッチ)は、1 セッションをその場で・自動で書き出すためのものです。atlas の `export` は、集計と同じ絞り込みでまとめて出すためのもので、節の構成は揃えていますが同じファイルにはなりません。

## 表(CSV)

依頼(ターン)ごと・セッションごと・ツールの失敗と拒否ごとの表を、表計算ソフトで開ける CSV(UTF-8、BOM 付き、行末 CRLF)で書きます。集計(`metrics`、`atlas.bat`・`all` を含む)のたびに `out/tables/` に書きます。空のセッションは入れません。前の版が書いた課題 × 条件の表(`conditions.csv`)は、集計し直すと消します。依頼文の先頭(200 字)・パス・エラー文・ツールの引数がそのまま入るので、共有する前に中身を確かめてください。`=` `+` `-` `@` で始まる文字列のセルには、表計算ソフトが式として読まないよう先頭に `'` を足します。

| ファイル | 1 行 | 主な列 |
|---|---|---|
| `turns.csv` | 依頼 1 件 | セッション ID・名前・プロジェクト、依頼番号・開始、依頼の種類・工程・次の依頼の種類、「次の依頼で直し・差し戻し」と「詰まり」(1 / 0)、実働と所要(秒)、ツールの数と種類別の回数(読む・編集・検証・git・シェル・計画・Web・委任・その他)、ツールの失敗・拒否・失敗の連続、編集・再編集(前の依頼で編集したファイル)・重ね編集(同じ依頼の中)、中断・エラー(うち利用上限)・サブエージェントの失敗・文脈圧縮・ask_user、入力 / 出力トークンと AIU(リクエストの記録の時刻で依頼に振り分けたもの。最初の依頼より前と 201 依頼目以降は含めない)、依頼文の先頭 |
| `sessions.csv` | セッション 1 件 | セッション ID・名前・プロジェクト・クライアント・ブランチ、利用者(送り先の人のフォルダ。無ければ空)、開始・終了、所要と実働(分)、依頼の数と依頼ごとの記録の数、詰まりのあった依頼・次の依頼で直し・差し戻しの数、応答、モデル、本体のモデルと本体の推論強度(サブエージェントを除いた本体のリクエストの 90% 以上が同じ (モデル, 強度) ならその組。届かなければ強度の列が「混在」、本体のリクエストの記録が無いか強度が不明なら「記録なし」で、どちらもモデルの列は空)、トークン・AIU・premium request、ツール・摩擦の内訳、再編集したファイル・余分な編集・失敗の連続、追加 / 削除行、推定人手工数(判定済みのものだけ)、管理ツールのタスク(`taskId`・`taskName`・`紐づけの出所`(機械 / LLM / 手動)・`タスクの数`。いくつかのタスクに紐づいたセッションは、`taskId` と `taskName` を `; ` でつなぐ(紐づけの順。1 件ずつは `session-tasks.csv`)。紐づけの出所はセッションごとに 1 つ。紐づいていなければどれも空。「どのタスクでもない」と決めたものは `taskId` が空で、出所と `タスクの数`(0)だけ入る。`タスクの数` は紐づいたタスクの数で、工数を等分する相手の数とは違うことがある(一覧に無いタスクと、完了を確認した後に始めたセッションのタスクには数えない。等分の割合は `session-tasks.csv` の `按分`)。`taskName` は名前が 1 つも分からなければ空(SQLite では NULL)。[下記](#管理ツールのタスク))、VCS の照合の列(照合してあるときだけ。下記)、テストの実行・最初に全部通った実行・最後に通っていないテスト・通るまでの実働(秒)と AI 使用量・読めなかった印の行と上限(1 セッション 5,000 件)で持たなかった結果の数(下記の「テストの結果」)、最初の依頼の先頭 |
| `vcs-hunks.csv` | AI の変更のまとまり 1 つ | セッション ID・まとまりの番号・パス・状態・照合不可の理由・VCS・開始時の基準(記録 / 推定。VCS と基準は、そのまとまりの照合に使ったリポジトリのもの)・状態別の行数。照合してあるときだけ |
| `failures.csv` | ツールの失敗か拒否 1 件(失敗の台帳の 1 行。[下記](#失敗の台帳)) | セッション ID・名前・プロジェクト、依頼番号(`turns.csv` と同じ番号。最初の依頼より前は空)・開始、種類(失敗 / 拒否)・要因、ツール、MCP サーバー・MCP のツール・MCP の設定元、モデル、エージェント・エージェントの呼び出し・エージェントへの依頼、所要(ミリ秒)、エラー文・引数(記録のまま。改行も残る)、その後(ツール / 利用者の次の依頼 / 続きなし)・次のツール・次の結果・呼び直し(1 / 0)、そろえたエラー文。失敗の台帳のある記録が 1 件も無いときは書かず、前に書いたものも消す |
| `test-runs.csv` | テストの実行 1 回(結果を出したツールの呼び出し。[下記](#テストの結果印つきの-1-行-json)) | セッション ID・名前、実行の番号・完了・依頼番号・ツール・サブエージェント(1 / 0)、結果の数・合格の数・まだ通っていないテストの数、そこまでの実働(秒)と AIU(累計。リクエストごとの記録が無ければ空)。テストの実行があるときだけ |
| `test-results.csv` | テストの結果 1 件(印つきの行 1 行) | セッション ID・実行の番号・結果の番号・テスト名・合否(1 / 0)・時刻。テストの実行があるときだけ |
| `test-counts.csv` | 結果の件数 1 つ(印つきの行の `counts` の 1 項目) | セッション ID・実行の番号・結果の番号・テスト名・名前(書いた側のまま)・値。テストの実行があるときだけ |
| `tasks.csv` | 管理ツールのタスク 1 件([下記](#管理ツールのタスク)) | `taskId`・`taskName`・`status`、完了(1 / 0)・XML に無い(1 / 0)、開始(紐づいたセッションのうち最も早い開始)・完了を確認した時刻・完了時刻の出所(記録 / 観測。未完了なら空)、稼働時間帯の工数・AI の実働・推定人手工数(時間。小数 2 桁)、セッション数・共有のセッション(ほかのタスクにも紐づいているセッションの数)・判定済み・確度が低い・判定なし、紐づけ(機械)・紐づけ(LLM)・紐づけ(手動)の数、比べられる(1 / 0。セッションが無ければ空)・比べない理由(未完了 / 完了の時刻が分からない / 完了の後に始まったセッション / 開始が分からない / 判定なし / 確度が低い)。いくつかのタスクに紐づいたセッションの実働と推定人手工数は、工数を数えるタスクの数で等分した分を入れる(タスクの一覧に無いタスクと、完了を確認した後に始めたセッションのタスクには数えない。セッション数などの数は等分しない)。設定に `tasks` が無く、タスクの記録も無いときは書かず、前に書いたものも消す |
| `session-tasks.csv` | セッション × 紐づいたタスク 1 組 | `セッションID`・`taskId`・`taskName`・`紐づけの出所`・`按分`(そのタスクに数えたセッションの値の割合。工数を数えるタスクの数で等分した値で、1 つなら 1、2 つなら 0.5。タスクの一覧に無いタスクと、完了を確認した後に始めたセッションのタスクは 0 で、残りのタスクで分ける)。「どのタスクでもない」・紐づけの無いセッションは載らない。`tasks.csv` を書くときだけ書き、書かないときは前に書いたものも消す |
| `atlas.sqlite` | — | 上の表と同じ中身の SQLite。表は `turns`・`sessions`・`tasks` と `session_tasks`(`tasks.csv` を書くときだけ)・`vcs_hunks`(照合してあるときだけ)・`failures`(失敗の台帳のある記録があるときだけ)・`test_runs`・`test_results`・`test_counts`(テストの実行があるときだけ)、列名は CSV の見出しそのもの(日本語なので SQL では `"…"` で囲む。例: `select "状態", count(*) from vcs_hunks group by 1`) |

## 管理ツールのタスク

設定の `tasks` に、管理ツールが書き出したタスクの XML を書いたときだけ作ります(設定の書き方と数え方は [README の「管理ツールのタスクと工数」](../README.md#管理ツールのタスクと工数任意))。XML は集計のたびと `atlas tasks sync` で読みます。LLM を使うのは、頼んだときの紐づけだけで、それも外部の LLM に頼みます(`atlas tasks bundle` で束を作り、`atlas tasks import` で取り込む。[judge.md の 4](judge.md#4-管理ツールのタスクへの紐づけ))。

**`atlas-notes/tasks.json`**(タスクの状態。XML を読むたびに更新する)

```json
{
  "version": 1,
  "source": { "file": "tasks.xml", "path": "D:\\export\\tasks.xml", "modifiedAt": "2026-10-23T12:00:00.000Z", "settings": "…" },
  "tasks": {
    "T-101": { "name": "画面の表示を直す", "status": "Resolved", "done": true, "firstSeenAt": "…", "doneAt": "2026-10-23T12:00:00.000Z", "lastSeenAt": "…", "missing": false, "doneObserved": true, "doneAtSource": "observed" }
  }
}
```

- `source.modifiedAt` は最後に読んだ XML のファイルの更新時刻(`source.path` はその場所)で、これを観測の時刻にします。同じ更新時刻で読み方も同じなら、読み直しても何も変えません。
- `doneAt` は完了の時刻です。設定の `tasks.doneAt` で XML の完了日時を読めればその日時、そうでなければ完了を最初に見た観測の時刻です(初めて見たときに完了していたら、そのときの時刻)。完了から戻ったら null に戻します。
- `doneAtSource` は完了の時刻の出所です。`recorded`(記録: XML の完了日時)か `observed`(観測: 完了を最初に見た書き出しの時刻)。未完了なら無く、前の版の `tasks.json` にも無い(観測として読む)。記録は XML を読むたびに読み直します。完了のまま記録が無くなった・読めなくなった・設定から `tasks.doneAt` を外したときは、前に決めた時刻と出所を残します(読めなくなった件数は「前の記録を残します」の注意に、観測で数えるものとは分けて出します)。
- `doneDateOnly` は、記録の完了日時が日付だけだったか(true のときだけ書きます)。`doneAt` はその日の稼働時間帯の終わりで、工数はそこまでを数えます。紐づけの候補と「完了の後に始まったセッション」の判定には、その日の終わり(翌日の 0 時)を使います。
- 完了日時の書き方は ISO 8601 と `YYYY-MM-DD`・`YYYY/MM/DD`(時刻 `HH:MM`・`HH:MM:SS` あり・なし)。時差の無い時刻は集計した PC の時刻、時刻の無い日付と時差の無い 0:00:00 ちょうどは日付だけ(その日の稼働時間帯の終わり。`workHours.end` が `24:00` なら翌日の 0 時)にします。暦に無い日などの読めない値と、2000 年より前・XML の更新時刻の 1 日後より後の日時は、件数をレポートとログの注意に出し、そのタスクは観測の決め方にします。
- `doneObserved` は、完了の時刻が分かるかです(未完了から完了に変わるのを見たか、記録がある)。初めて見たときに完了していて記録も無いタスクは false で、`doneAt` は完了した時刻ではないので、工数を数えず「完了の時刻が分からない」として比べません(完了とは出します)。
- 前に読んだものより更新時刻の古い XML は、状態を変えずに、注意をレポートとログに出します(古い書き出しで完了を戻さないため)。比べるのは、同じファイル(`source.path`)を同じ読み方で読んだときだけです。前に読んだ更新時刻が今より 1 日以上先(時計の狂い)なら止めません。直し方は注意に書きます(書き出し直す。古い書き出しを使うなら `tasks.json` を消して読み直す)。
- 記録が無いタスクで完了に変わるのを見た(`doneObserved: true`)とするのは、同じ読み方で読んだ 2 回の間に未完了から完了に変わったときだけです。読み方(`doneStatus` など)を変えたせいで完了になったものは、初めて見たときと同じく見ていないとします。`doneAt` を設定していない読み方の目印(`source.settings`)は前の版と同じなので、この機能の前に作った `tasks.json` もそのまま読み続けます(`doneAt` を足すと読み方が変わったものとして読み直し、記録のあるタスクはその日時にします)。
- `doneAt` を設定しているときは、`source.settings` に稼働時間帯も入れ(稼働時間帯を変えると、同じ更新時刻の XML でも読み直して、日付だけの完了日の時刻を決め直します)、稼働時間帯を除いた目印を `source.reading` に書きます。「同じ読み方」かは `source.reading`(無ければ `source.settings`)で比べるので、稼働時間帯を変えた回に完了したタスクも、完了に変わるのを見たとします。
- XML の節(要素・文字・コメントなど。属性は数えない)は、ファイルの大きさ ÷ 4 個(少なくとも 100,000 個)まで読みます。字下げした書き出しの節はおよそ 13 バイトなので、64 MB の書き出しも読めます。
- XML から消えたタスクは `missing: true` にして、最後に読んだ値を残します。
- XML を読めなかったとき(ファイルが無い・壊れている)は、前の状態のまま続け、レポートの「管理ツールのタスク」の節とログに理由を出します。

**`atlas-notes/task-links.json`**(セッションとタスクの紐づけ)

```json
{ "version": 2, "links": { "<セッション ID>": { "taskIds": ["T-101", "T-103"], "source": "machine", "reason": "ID が題名にある", "confidence": 0.7, "at": "…" } } }
```

- `taskIds` は紐づいたタスク(並びは決めた順。機械は XML の順、LLM は答えの順、手動は加えた順)。空の並び `[]` は「どのタスクでもない」です。1 つのセッションに 10 個まで(誤った当たりや壊れた記録で長くならないための安全のための上限。超えた分は読みません)。
- 前の版(`version` 1。`taskId` が 1 つか null)のファイルも読み、0 か 1 件の並びとして扱います。書くのは版 2 の形だけです(前の版の atlas は版 2 のファイルを読まず、書き換えもしません)。
- `source` は `machine`(機械)・`llm`(LLM)・`manual`(手動)で、セッションごとに 1 つです。`confidence` は LLM のときだけです。
- 機械の紐づけは集計のたびに決め直します。ID で当たったタスクだけなら、そのすべてに紐づけます。ID の当たりが無く、名前で当たったタスクがちょうど 1 つなら、そのタスクに紐づけます。名前だけの当たりがあって 2 つ以上のタスクに当たったときと、上限を超えたときは決めません。手動の紐づけと、LLM がタスクを選んだ紐づけは変えません。LLM が「どのタスクでもない」とした紐づけは、機械の当たりが決まれば置き換えます。紐づけの無いセッションは載りません。候補のタスクが 1 つも無いセッションは、LLM に頼む束に入れず、何も書きません。
- 書き手(画面の手動の紐づけ・LLM の返答の取り込み・集計)は別のプロセスのこともあるので、`task-links.json.lock`(と `tasks.json.lock`)を開いて OS のファイルのロックを取ってから読み直し、自分の変更だけを足して書きます。LLM の返答を取り込んでいる間に画面で手動で紐づけても消えません。ロックはファイルを開いている間だけ効くので、処理が落ちれば OS が外します(`.lock` のファイルそのものは残しておきます。消しても困りません)。15 秒待っても取れなければ止まり、serve は 409 を返します。

**`out/task-bundle/`**(紐づけを外部の LLM に頼む束。`atlas tasks bundle` と画面の「判定する…」の「タスクの紐づけ」が作る。LLM は呼ばない)

| ファイル | 内容 |
|---|---|
| `INSTRUCTIONS.md` | フォルダ(ZIP)ごと渡すときの指示(決めること・守ること・返す形)。最初に読ませる |
| `manifest.json` | パケットの一覧。`sessions[]` に `id`・`path`(`sessions/<セッション ID>.md`)・`candidates`(そのセッションの候補のタスクの ID。返答の検証に使う)・`chars`、`parts[]` に添付ファイルとその中のセッション、`perPart`・`scope`(`--session` で絞ったか) |
| `schema.json` | 返す JSON(`{ "schemaVersion": 1, "links": [ { "sessionId", "taskIds", "confidence", "reason" } ] }`)の JSON Schema |
| `sessions/<セッション ID>.md` | 1 セッションのパケット(題名・最初の依頼から 3 件までの文・候補のタスクの ID と名前) |
| `parts/part-<番号>.md` | チャットに添付するファイル。指示・JSON Schema と、パケット数件(既定 10 件)をファイルごとの乱数の境界で囲んだもの |
| `replies/` | M365 Copilot の自動操作で受け取った返答(`tasks m365` のとき) |

`--zip` を付けると `INSTRUCTIONS.md`・`manifest.json`・`schema.json`・`sessions/` を `out/task-bundle.zip` にまとめます(展開すると `task-bundle` フォルダ。結果は、その中の `links.json` に書かせます)。付けずに作り直すと、前の ZIP は消します。返答の検証と書き方は [judge.md の 4](judge.md#4-管理ツールのタスクへの紐づけ) にあります。

**レポートに埋め込むもの**: `atlas.html` の埋め込みデータの `tasks`(版 20 から。版 21 で `links` の `taskId` を `taskIds` の並びにし、工数を等分するタスク `countedTaskIds` と、タスクごとと合計に `sharedSessions`(いくつかのタスクに数えたセッションの数)を足した)。タスクごとの値と合計はここで決め、画面は数え直しません。タスクごとに `doneAtSource`(完了の時刻の出所)、合計に `doneSources`(完了したタスクの、出所ごとの数 `{ recorded, observed }`)と `includedSources`(比べられるタスクの、出所ごとの数)を入れます(古い埋め込みには無い)。記録と観測はどちらも比べられるタスクに入れ、件数を分けて出します(タスクの節の「比べられる完了タスク」の注記、全体サマリの表紙)。serve から開いた画面は `GET /api/tasks` で同じ形の今の値を読みます(詳細ページで直した紐づけも出ます)。`GET /api/tasks` は、レポートと同じ関数・同じ読み方の推定人手工数(`judgments.json`)で数えます。絞り込み(`--task`・`--session`・`--since` など)で作ったレポートは `tasks.scoped` が true で、画面は API の値で置き換えずに埋め込みの値を出します。

**送るとき**(`upload-project.bat`・自動で送るタスク): 紐づいたセッションの `atlas-session.json` と、`atlas-index.json` のセッションごとの項目に `tasks`(紐づいたタスクの並び)を添えます(「どのタスクでもない」と決めたセッションには添えません)。紐づけの出所と理由は、セッションごとの値を各タスクに添えます。紐づいたタスクがちょうど 1 つのときは、前の版の atlas でも読めるよう、前の版の形の `task`(同じ中身の 1 つ)も添えます(読む側は `tasks` があればそちらを使います)。`README.md` のセッションの一覧には「タスク」の列(名前と ID。いくつかあれば「、」でつなぐ)を出します。

```json
"tasks": [{ "id": "T-101", "name": "画面の表示を直す", "status": "Resolved", "done": true, "doneAt": "2026-10-23T12:00:00.000Z", "doneObserved": true, "doneAtRecorded": true, "lastSeenAt": "2026-10-23T12:00:00.000Z", "start": "2026-10-15T00:00:00.000Z", "source": "machine", "reason": "タスク名が依頼にある" }]
```

送り先で集計すると、XML を読まずに、この記録からタスクの一覧・絞り込み・工数を作ります(稼働時間帯は、送り先の設定の `tasks.workHours` か既定の値)。送り先ではタスクの紐づけを変えられません。前の版が送った記録(`task`。1 つのタスク)も、1 件の並びとして読みます。

- `tasks` の並びが 10 個を超えるとき・並びでないときは、そのセッションはタスクに紐づいていないものとして扱います。形の違う項目は飛ばし、同じ ID は先のものだけを使います。

- 同じタスクを何人かが送って記録が食い違うときは、いちばん新しく見た記録(`lastSeenAt` と `doneAt` の遅い方)の名前・状態・完了を使います。完了を確認した時刻は、いちばん新しい記録が XML の完了日時(`doneAtRecorded: true`。前の版の記録には無い)ならその日時、そうでなければ完了に変わるのを見た(`doneObserved`)記録のうち最も早いものです。見た記録が 1 つも無ければ「完了の時刻が分からない」です。開始は最も早いものです。
- 日時は 2000-01-01 から読んだ時刻の 1 日後までだけを受け付け、外れる記録は読みません。開始が完了を確認した時刻より後のもの、開始から 3,660 日を超えるものは、開始だけを捨てます(稼働時間帯の数え方は、どの期間でも最大で約 10 年分までしか数えません)。

## テストの結果(印つきの 1 行 JSON)

テストの合否と件数を、セッションごとに残すための取り込みです。テストの実行ファイルが、結果を決まった印つきの 1 行で標準出力に書くと、atlas がツールの結果(`events.jsonl`)から拾って、そのセッションの記録に持ちます。ログの中だけで決まるので、別のファイルとの突き合わせは要らず、アップロードした生ログから集計し直しても同じ結果になります。LLM は使いません。

```
ATLAS_TEST_RESULT {"v":1,"name":"描画","passed":false,"counts":{"assertFailures":2,"validationErrors":0,"shaderErrors":1,"imageDiffRate":0.031},"at":"2026-11-16T01:02:03.456Z"}
```

| 項目 | 中身 |
|---|---|
| `passed` | 合否(`true` / `false`)。**必須**。真偽でなければその行は「読めなかった」に数える |
| `name` | テストの名前(文字列。200 字で切る) |
| `counts` | 名前 → 数。件数でも割合でもよく、名前は書いた側のまま持つ(50 個まで。数でない値は読み飛ばす) |
| `at` | テストを実行した時刻(ISO 8601。UTC にそろえて持つ)。書くと、同じ行を 2 回数えずに済む(下記) |
| `v` ほか | 読み飛ばす。項目を足しても古い atlas で読める。新しい数は `counts` に足す |

- **書き方**: 1 つの結果を 1 行に書きます。行頭(前の空白は可)に `ATLAS_TEST_RESULT`、空白、JSON のオブジェクトの順です。行の途中にある印は拾いません(テストのソースを読んだ結果や、行番号・ファイル名の付いた検索の結果を数えないため)。テストの名前ごとに 1 行ずつ書いても、まとめて 1 行にしてもかまいません。
- **読む場所**: ツールの完了(`tool.execution_complete`)の結果の本文(`result.detailedContent`、無ければ `result.content`)です。結果が無い失敗(テストが落ちて終了コードが 0 でないときなど)は、エラーの文(`error.message`)から読みます。同じ呼び出しの中で 2 か所から重ねては数えません。サブエージェントが走らせたテストも数えます。
- **同じ行が 2 回出たとき**: 非同期で走らせたシェルの出力を後から読んだときや、保存したログを表示したときは、同じ行がもう一度出ます。`at` のある行は 2 回目から数えず、その数を `duplicates` に残します。`at` の無い行は別の実行と見分けられないので、重ねて数えます。
- **出力**: `sessions.json` の各セッションの `tests`。結果を出したツールの呼び出し 1 回ごとに、時刻(`at`)・依頼の番号(`turn`。1 から。最初の依頼より前と 201 依頼目以降は `null`)・ツール(`tool`)・呼び出しの ID(`toolCallId`)・サブエージェントの印(`subagent`)・結果の並び(`results`)と、下の推移の値を持ちます。ほかに、読めなかった行(`invalid`)・重ねて数えなかった行(`duplicates`)・1 セッションの上限(5,000 件)を超えて持たなかった結果(`dropped`)の数を持ちます。印の行が無いセッションにはキーを置きません。
- **推移(1 セッションの中)**: 結果を出したツールの呼び出し 1 回を「実行」と呼び、実行ごとに次を持ちます。
  - `failing`: その実行の後で、まだ通っていないテストの数。これまでに出たテストの名前ごとに、いちばん新しい結果が不合格のものを数えます。**0 なら「全部通った」**です。一部のテストだけを走らせ直した実行では、前に通ったテストは通ったままとみなします(走らせていないテストの結果はログから分からないため。毎回すべてのテストを走らせれば、その実行の結果だけで決まります)。名前の無い結果は、まとめて 1 つのテストとして扱います。
  - `activeMs`: セッションの始まりからその実行までの実働(5 分を超えて出来事が無かった区間を除く。セッションの実働時間と同じ数え方)。
  - `nanoAiu`: その実行までに記録されたリクエストの AI 使用量の累計(サブエージェントの分を含む)。リクエストごとの記録(時刻つき)が無いセッションは `null` です(0 にはしません)。
  - セッションには `firstPass`(最初に全部通った実行の番号。1 から)を持ちます。**実行が 1 回以上あって `firstPass` が `null` のセッションが「未達」**です。実行が 1 回も無い(印の行が無い・読めなかった行だけ)セッションは、未達には数えません。通るまでの繰り返し回数は `firstPass`、通るまでの実働と AI 使用量は、その実行の `activeMs` と `nanoAiu` です。
- **画面**: 詳細ページの「テストの推移」の節(印の行を読めたセッションだけ。[screen.md](screen.md#セッション詳細ページ))。レポートには、テストの実行があるセッションだけに、数だけの要約(実行の数・最初に全部通った実行の番号・最後の実行の後で通っていないテストの数・最初に全部通るまでの実働と AI 使用量・最後の実行までの AI 使用量)を埋め込みます。実行ごとの結果やテストの名前は埋め込みません。レポートの「比べる」(工程どうしを除く)は、この要約から、テストを実行したセッションのうち最初の実行で全部通ったセッションの割合と、最後に通っていないテストが残ったセッションの割合を並べます([screen.md](screen.md))。表は `out/tables/` の `test-runs.csv`(実行 1 回 1 行)・`test-results.csv`(結果 1 件 1 行)・`test-counts.csv`(件数 1 つ 1 行)と、同じ中身の `atlas.sqlite` の `test_runs`・`test_results`・`test_counts`、`sessions.csv` のテストの列([表(CSV)](#表csv))。
- **限界**: 試される側の AI が同じ形の行を出力すると、本物のテストの結果と区別できません。ログに残らなかった出力(長い出力をログがどう残すかは確かめていません)は拾えないので、印の行は短く、ほかの出力と分けて書いてください。

## AI の変更の残存(VCS の照合)

AI がセッションの中で足した行が、その後の VCS(Git / SVN / Perforce)のファイルに残っているかを数えます(`atlas vcs`。`atlas.bat` と `all` にも入る)。VCS は読むだけで、読む系の副コマンドだけを許可リストで通します(コマンドを呼ぶ前に毎回確かめ、通らないものは呼ばずに「読めなかった」にします。Perforce の `-o`(ファイルに書き出す)も止めます)。

残っているかの記録で、採用の意図や良し悪しの判定ではありません。「見つからない」「照合不可」を不採用とはみなさず、LLM の判定とも別の指標です。

| 出力 | 中身 |
|---|---|
| `out/vcs-retention.json` | 照合の条件(比べる版 `mode`・似た行の下限 `similarity`・パスの読み替えの数・照合した場所と日時・設定の `labels` と `note`)、全体の集計(`summary`。下の「記録の範囲」)、セッションごとの結果(`sessions`: 結果・照合不可の理由・VCS・開始時の基準と出所・比べた版と出所(`evaluated.source`)・照合に使ったリポジトリごとの基準と比べた版(`repos`。下の「複数の VCS にまたがるセッション」)・値の出所(`provenance`)・まとまりごとの状態と行数。まとまりには、似た本文で当てた行数 `similarLines`、ログのツール呼び出しの ID `toolCallId`、行の取り出し元 `from`(`diff` / `args`)、照合に使ったリポジトリの `vcs` と `root` も、あるときだけ入る)。パスが入るので共有しないでください |
| `sessions.csv` の列 | 照合の結果・照合不可の理由・VCS・開始時の基準(記録 / 推定)・照合した場所・状態別のまとまりと行の数。VCS は、照合できたまとまりのあるリポジトリの種類で、複数なら `git+svn+p4` の順に `+` でつなぎます。開始時の基準は、そのリポジトリのどれかが推定なら推定です。そのようなリポジトリが無い(`repos` の無い古い結果・すべて照合不可)ときは、セッションの VCS と基準です。照合していないセッションは空にします |
| `vcs-hunks.csv`・`atlas.sqlite` の `vcs_hunks` | まとまりごとの状態(上の「表」)。VCS と開始時の基準は、そのまとまりの照合に使ったリポジトリのもの(照合不可のまとまりでも、リポジトリが決まっていれば出します)。リポジトリの決まらなかったまとまりは空です。`repos` の無い結果は、今までどおりセッションの値です(古い結果のほか、どのまとまりもリポジトリが決まらなかった新しい結果もここに入ります。`repos` が空だと新旧を見分けられないため) |
| レポート | 「AI の変更の残存」の節と、詳細ページの同じ名前の節([screen.md](screen.md#画面の見方)) |

- **取り出し方**: ログの編集の完了イベントの diff(無ければ編集の引数)から、AI が足した行を取ります。同じセッションで後から書き直した行は最後の形だけ、失敗した編集・`session-state` の中・空白だけの行は数えません。
- **照合の仕方**: 開始時の基準のファイルと照合した時点のファイルを読み、基準から増えた行と AI の行を突き合わせます(同じ本文 → 空白を除いて同じ → 似た本文の順)。基準は Git ではログに残った開始時のコミット(記録)、無いときと SVN・Perforce は開始時刻の直前の版(推定)です。比べる版は既定で照合した時点の作業ツリーで、`fixed` ではセッションの終わりから決まった日数後の版です。セッションの終わりから比べた時点までの日数を、セッションごとに残します(`sessionEnd` と `evaluated.at`)。
- **記録と推定**: 開始時の基準の出所(`baseline.source`)は、`observed`(ログに残った版)か `estimated`(開始時刻から VCS の履歴で探した版)です。比べた版は、`fixed` のときだけ日時から決めた推定なので `evaluated.source` を `estimated` にします(無ければ、照合したときに VCS で見た版)。似た本文で当てた行は「直されて残る」に入りますが推定なので、行数を `similarLines`(まとまりと `summary`)に分けて残します。Perforce の日時は、`p4 info` のサーバーの時差で合わせます。時差は照合したときのものなので、夏時間をまたぐ過去の日時でもずれないよう、前後 1 時間の変更を取り込んだ時刻(UTC)で確かめます。補えるのは、照合したときと当時の時差の違いが 1 時間以内のときだけです(サーバーのタイムゾーンを変えたときなどは外れえます)。時差が読めなければ UTC のまま、取り込んだ時刻が出力に無ければ時差だけで決めた日時で探します(どちらも推定)。
- **複数の VCS にまたがるセッション**: ファイルごとに、照合に使うリポジトリを決めます。セッションの作業フォルダのリポジトリに入るファイルでも、ファイルのある場所でリポジトリを探し、その根がセッションのリポジトリの根より内側にあれば(Perforce のワークスペースの中の SVN の作業コピー、Git の中の別の Git のリポジトリなど)、いちばん内側のそれで照合します。この内側の作業コピーを探すときは、入れ子として意味のある種類だけを調べます(作業フォルダが Git なら Git、SVN と Perforce なら Git と SVN)。Perforce はサーバーに問い合わせるので、内側を探すときには呼びません。作業フォルダの外のファイルや、作業フォルダが VCS の管理外のとき(管理外のフォルダの下に Perforce と SVN の作業コピーがあるなど)は、ファイルのある場所で Git・SVN・Perforce を探したリポジトリで照合します。リポジトリを探すのはフォルダ(と調べる種類の組)ごとに 1 回です。照合に使ったリポジトリは、最初に使った順に `repos` に残します(各要素は `vcs`・`root`・開始時の基準 `baseline`(`rev`・`source`。決められなければ `null`)・比べた版 `evaluated`(`rev`。`fixed` は日時から推定したので `source` が `estimated`。調べられなければ `null`))。まとまりの `vcs`・`root` は、そのどれかです(照合不可のまとまりでも、リポジトリが決まっていれば付きます)。セッションの `vcs`・`root`・`baseline`・`provenance.baseline`・`evaluated` は、作業フォルダのリポジトリのものです。`baseline` もそのリポジトリの基準だけで、そのリポジトリで基準まで決まらなければ(基準を決められない・作業フォルダのリポジトリのファイルが無いなど)、ほかのリポジトリの基準で埋めずに `null` のままです。作業フォルダが VCS の管理外のときは、使ったリポジトリが 1 つだけなら、セッションの `vcs`・`root`・`baseline` もそれにします。2 つ以上なら `vcs`・`root` は `null` のままで、`baseline` は最初に基準の決まったリポジトリのものです。集計と表示は、セッションの値でなく `repos` を使います。`repos` とまとまりの `vcs`・`root` が無い古い結果も、そのまま読めます。
  - 作業ツリーは Git → SVN → Perforce の順に探して、最初に当たったものを使います。そのため、Git の作業ツリーの中に置いた SVN の作業コピー、SVN の作業コピーの中に置いた Perforce のワークスペースは、外側の VCS で照合します。Perforce のワークスペースの中の別のクライアント(Perforce の中の Perforce)も分けず、作業フォルダのクライアントで照合します。
- **記録の範囲**: `summary` には、渡したセッションの数(`sessions`)・AI の変更があった数(`withAiChanges`)・照合できた数(`measured`。割合の分母)・すべて照合不可だったセッションの理由別の数(`unattributable`)・照合できたセッションのうち基準を推定したもの(`baselineEstimated`)・VCS ごとの照合できたセッションの数(`byVcs`)を残します。このうち `baselineEstimated` と `byVcs` は、照合できたまとまり(そのまま残る・直されて残る・見つからない)が 1 つ以上あるリポジトリだけで決めます(まとまりの `vcs`・`root` で `repos` を引きます。照合不可のまとまりだけのリポジトリ・どのまとまりも指していないリポジトリは数えません)。基準は、そのリポジトリのどれかが推定なら推定に数え、推定を混ぜて記録とは数えません。VCS はその種類をセッションごとに 1 回ずつ数えるので、複数の VCS にまたがるセッションはそれぞれに入り、合計が `measured` を超えることがあります。`repos` の無い古い結果は、セッションの `vcs` と `baseline` で数えます。このほか、次を 0 でないときだけ残します: 取り出せなかった編集とそのセッションの数(`unreadEdits`・`unreadSessions`)、基準のファイルにもともとある行だけだったので数えなかったまとまり(`excludedHunks`)、似た本文で当てた行(`similarLines`)、比べた版を推定したセッション(`evaluatedEstimated`)。`atlas vcs` のログにも出します。
- **読めなかったと版が無いの区別**: VCS のコマンドが失敗したときは「VCS かファイルを読めなかった」(`read_error`)にし、「版が無い」(基準を決められない・比べる版を決められない)とは分けます。版が無いとみなすのは、VCS が「その版・変更が無い」と答えたときだけです(ファイルが開けないなどの環境の失敗は読めなかったにします)。`committed` で今の版を調べられなかったときも、取り込みが無い(`no_commits`)かを決められず、行を「見つからない」に数えるおそれがあるので、読めなかったにします。送った側の結果に理由が無いまとまりは、読めなかったとは決めずに「理由が記録されていない」(`unknown`)にします。
- **取り出せなかった編集**: ログの編集から diff も引数も読めなかったものは数えず、件数(`unreadEdits`)を残して、`atlas vcs` のログと画面に出します。Copilot のログの形が変わると増えます。
- **開始時に取り込んでいなかった変更**: 開始時の基準は版なので、セッションの開始時にコミットしていなかった変更は基準に入りません。そのため、開始時に手元だけにあった行と同じ本文の AI の行は、基準にあった行として除かれず、残っている側に数えることがあります(作業ツリーの状態はログに残らないので、atlas では補えません)。開始時の状態を基準にしたいときは、セッションの前にコミットしておきます。
- **SVN の作業コピーの版**: SVN はコミットしただけでは作業コピーの版が進みません(`svn update` するまで、ルートは前の版のまま)。`committed` で最新の取り込みと比べたいときは、照合の前に `svn update` してください。
- **コミットの無いセッション**: 比べる版が `fixed`(終わりから決まった日数後の版)か `committed`(最後に取り込んだ版)で、その版が開始時の基準と同じ(その間に取り込まれた変更が無い)ときは、AI の行は必ず見つからないので、まとまりを「見つからない」でなく照合不可(開始時から取り込まれた変更が無い。`no_commits`)にします。`worktree` は今のまま(ディスクのファイルと比べる)です。SVN の `committed` でもこの判定はしません(作業コピーの版は、ファイルを取り込んだだけでは進まず、基準と同じに見えても取り込みが無いとは言えないため。取り込んだ版のファイルを読んで照合します)。当該のファイルだけを取り込まなかった(ほかのファイルのコミットはある)ときは、見つからないのままです。
- **重なり**: 時間の重なる別のセッションも同じ行を足していたら、そのまとまりは照合不可にします。後のセッションも同じ行を足していたら、後のセッションの分として数えます。
- **アップロード**: 送る側で照合した結果を、セッションのフォルダに `atlas-vcs.json` として添えます。送り先で集計し直すときはこれを読み、無いセッションは「送った側で照合していない」にします。結果に項目が増えた版の atlas に上げた後の最初のアップロードでは、AI の変更のあるセッションの `atlas-vcs.json` が変わるので、それらを送り直します(送り先が新しい項目を読めるようにするため)。`repos` とまとまりの `vcs`・`root` は、照合にリポジトリを使ったセッションにだけ付くので、送り直すのはそのセッションです(すべてのまとまりが「作業フォルダがこの PC に無い」などでリポジトリの決まらなかったセッションは、中身が変わらないので送り直しません)。送り先で読み直した結果にも、`repos` とまとまりの `vcs`・`root` が残ります。
- **名前の差し替え**: 状態の名前と、画面の節の説明に足す一文は、設定(`atlas.config.json` の `vcs.labels`・`vcs.note`)で差し替えられます([cli.md](cli.md#vcs-の照合の指定))。

## 解析用の完全出力

出力データだけでローカルと同等の解析ができるようにするための出力です。**外部に出さない前提**で、原本の文字列をそのまま含みます。

```
bin\atlas.exe export --full            # snapshot / extract 済みの状態から、全件の全文記録と coverage.json を書く
bin\atlas.exe snapshot --snapshot-all  # rewind-snapshots / 一覧に無いフォルダ / logs/ も写す
```

1 セッションだけなら、`atlas.bat` から開いた詳細ページの「全文を作って読む」で、そのセッションの `out/full/<id>.md`(と `out/full/assets/<id>/`)だけを作ってその場で読めます。このときは `atlas.html`・詳細ページ・他のセッションの全文・`coverage.json` は作り直しません(網羅の検査は全件の `export --full` だけが書きます)。

| 出力 | 中身 |
|---|---|
| `out/snapshot/` | 原本の複製(スナップショット)。セッションフォルダの `plan.md` / `checkpoints/` / `policies/`、直下の `plans/` / `attachments/` / `chats/` の `*.md` も写す。写さなかったもの(`rewind-snapshots/` は 1 セッションで数十 MB、一覧に無い名前のフォルダ、`logs/`、`repos/`、`chats/` の `*.md` 以外。`files/` / `rewind-file-snapshots/` は集計で使わないので写さず、大きさも測らない)は `snapshot-manifest.json` の `extras.skipped` に名前と容量を残し(`snapshot-source.json` は、どこから集計したかの印。集計が途中で止まっても残り、別の場所のログを同じ出力先に足すのを止めます)、`--snapshot-all` で写す(`repos/` と `chats/` の `*.md` 以外は写さない) |
| `out/snapshot/desktop.json` | デスクトップアプリの `data.db` から、名前で固定した許可リストの列だけを読んだもの(下記) |
| `out/full/<id>.md` | 全文記録。依頼、応答、reasoningText、ツールの引数と結果(成功含む)、hook の入出力、system.message、compaction の要約、skill の本文、plan.md、チェックポイント、`policies/` などの一覧(`files/` / `rewind-file-snapshots/` は `--snapshot-all` で写したときだけ)、data.db の列を時系列で、上限なしで書く。除くのは暗号化・不透明データ(`encryptedContent`、`reasoningOpaque`、`reasoningBlocks` の中の base64 らしい値)と base64 の本体(画像などは `out/full/assets/<id>/` に書き出してリンク)だけで、除いた箇所に種別とバイト数を書く。hook の入力に入っているツールの結果がツールの結果と同一なら参照にする。API キーらしい文字列は形式検査で伏せて件数を末尾に書く |
| `out/coverage.json` | 網羅の検査。元データの event type × data のキーごとに件数・バイト数・扱い(`full` = 全文に出した / `ref` = 参照にした / `excluded` = 理由付きで除外)。扱いの表(`crates/atlas-report/src/coverage.rs`)に無いキーは `unclassified` として数え、`export` のログと全文記録の末尾にも出す(0 件なら欠損なし)。`data.db` の列も同じ表で(許可 = `full`、許可外 = `unclassified`、開かない表 = `excluded`) |
| `out/instructions.html` と `out/library/` | 指示文(AGENTS.md / CLAUDE.md / copilot-instructions.md 等の注入)と skill の本文を、重複なしで版(内容のハッシュ)ごとに置いたもの。見出しごとの版一覧、本文、使われたセッション、使われた期間・プロジェクト、前の版との差分。「版 N」は初回の利用日の順の通し番号(改善点の「版 N」と同じ)で、別のリポジトリの同じ見出しのファイルも同じ項目に入るため、番号が大きい版が今の版とは限らない。そのため最後に使われた版に印を付けて開き、項目の見出しにプロジェクトごとの最後の版を、期間が重なる版に「並行して使用」を出す。差分は同じプロジェクトで前に使われた版と比べる(無ければ 1 つ前の版と比べ、そう書く)。詳細ページの指示ファイルの行と skill からリンクし、サイドバーの付録にも入る。`instructions.html#session=<セッション ID>` で開くと(詳細ページの「このセッションの指示文と skill」)、そのセッションで使われた版だけを残し、上の帯に件数と「すべて表示」「セッションの詳細に戻る」が出る(使えただけで呼ばなかった skill は本文が無いので、詳細ページの表にだけ出る)。`--full` でなくても `export` で作る |

`--full` を付けない `export` や素の `build` は、前回の `out/full/` と `out/coverage.json`(と `instructions.html` / `out/library/`)を消しません(ユーザーの生成物を黙って消さないため。残っているときはログに生成日時を出します)。古い全文記録が残っている点に注意し、消したいときは `out/full/` フォルダと `out/coverage.json` を手で消してください(どちらかが残っている間は、ログに出ます)。

**data.db(デスクトップアプリ)**: 資格情報の列を含むため、次の形で読みます。ファイルは複製せず、`file:///…/data.db?immutable=1` の読み取り専用で開きます(`-shm` / `-wal` に触れません)。読むのは名前で固定した許可リストの列だけで(`sessions` の非資格情報の列、`session_context_usage`、`session_checkpoints`、`activity_items`、`projects` と `workspaces` の非資格情報の列)、`select *` はせず、`accounts` / `settings` / `app_state` / `model_providers` / `remote_environments` は開きません。許可リストに無い列は名前だけ数えます(値は読みません)。immutable で開くため `-wal` の未反映分は読めず、最近の更新が欠けることがあります(`desktop.json` と全文記録に WAL の大きさと更新日時を書きます)。結果は `sessions.json` の `desktop` 欄、全文記録、詳細ページの「デスクトップアプリの記録(data.db)」に出ます。

## 失敗の台帳

ツールの失敗と拒否を 1 件ずつ残した記録です。要因別の回数(`tools.results[].causes`)だけでは、同じ文で繰り返し失敗している所や、失敗の後に何をしたかを追えないので、1 件 1 行で持ちます。LLM は使いません。

**記録**(`sessions.json` の各セッションの `analysis.failures` と `analysis.failuresDropped`。スキーマ 18 から): 行は `tools.results` の失敗・拒否と同じ条件で作るので、行数 + `failuresDropped` は、そのセッションの失敗 + 拒否と一致します。1 セッション 500 行までで(時刻の早い順)、超えた分は `failuresDropped` に数だけ残します。以前の版で集計した記録には `failures` がありません。これは「台帳なし」で、失敗が 0 件という意味ではありません(集計し直すと付きます。新しく集計した記録は、失敗が 0 件でも空の配列を持ちます)。

| 項目 | 中身 |
|---|---|
| `tool`・`kind`・`cause` | ツール名、`failure`(失敗)か `denied`(拒否)、失敗の要因(拒否は null) |
| `error`・`args` | エラー文(`code: message` の形)と、ツールの引数(1 行の JSON)。秘密らしい文字列を `[伏せました: 種類]` に置き換えてから、1000 字で切ります(全文に掛けてから切るので、途中で切れた鍵が残りません)。URL の `user:pass@` と、`password=…` のような名前の付いた値も置き換えます |
| `mcpServer`・`mcpTool`・`mcpConfigSource`・`model` | 開始のイベントの MCP の項目と、モデル |
| `startedAt`・`durationMs` | 開始の時刻と、完了までの時間 |
| `turn` | 本体の依頼の番号(0 から。`turns.csv` の依頼番号 − 1)。最初の依頼より前は null。200 件を超えても数えます |
| `agent`・`agentCall` | サブエージェントの名前と、起動した親の呼び出し(`agents[].id` と同じ)。本体は null。サブエージェントへの依頼文は `agents[].prompt` に 1 回だけ持ちます(500 字まで) |
| `next` | 失敗の後に何をしたか。同じエージェントが、失敗の後に最初に呼んだツール(`tool`)とその結果(`outcome`)、同じツールを同じ引数で呼んだか(`retry`)。失敗が終わる前に始まっていた呼び出し(並行)と、失敗と同じ応答でまとめて要求された呼び出しは数えません。本体で、次のツールより先に利用者の依頼が来たら `user`、その後に呼び出しが無ければ `end` |
| `group` | そろえたエラー文。エラー文の 1 行目を小文字にし、URL・パス・16 進の ID・数字・引用した部分を印(`<url>` `<path>` `<id>` `<n>` `<q>`)に置き換え、記号を落としたもの。同じ文の失敗をまとめる鍵です |

あわせて、モデル別 × ツール別の結果を `tools.resultsByModel` に持ちます(数え方は `tools.results` と同じ)。

**見る所**:

- **セッション詳細ページ**: 「依頼ごとの経過」の「失敗・拒否の内訳」の欄(ツール・要因か拒否・回数)と、「失敗と拒否(1 件ごと)」の節(依頼・開始・ツール・種類と要因・エラー文・引数・その後)。エラー文は 400 字、引数は 200 字までを載せます。
- **表**: `out/tables/failures.csv` と、`atlas.sqlite` の `failures`([表(CSV)](#表csv))。エラー文と引数は記録のまま入ります。例: `select "ツール", "そろえたエラー文", count(*) from failures group by 1, 2 order by 3 desc`
- **集計のページ** `out/failures.html` と、同じ集計の `out/failures.json`(`build`・`export` のたびに書きます)。レポートの目次の「付録」と、利用ランキングの「失敗の要因」の説明から開きます。レポートに入れた記録の全体で計算し、レポートの画面の絞り込みは掛かりません。

**集計のページの数え方**: 対象は、空でなく台帳のあるセッションだけです。台帳の無い記録は「対象」の欄に件数を出し、分母にも入れません。

| 節 | 中身 |
|---|---|
| 対象 | 台帳のあるセッション、失敗、拒否、失敗率、台帳の無いセッション、台帳に残していない失敗・拒否(500 行の上限を超えた分) |
| 失敗の後 | 同じ引数で呼び直した(うち成功)、別の呼び出しで続けた(次の呼び出しが成功)、利用者の次の依頼、続きなし |
| 繰り返している失敗 | そろえたエラー文が同じ失敗が 3 回以上あるもの。回数、セッション、ツール、要因、呼び直し、最初のエラー文と出たセッション |
| ツール・MCP サーバー | 失敗か拒否のあったもの。呼び出し(結果の記録があるもの)、失敗、拒否、失敗率、セッション、主な要因、主なエラー文、呼び直し。MCP サーバーは、そのサーバーのツールの結果を足したもの |
| エージェント | 本体と、サブエージェントの名前ごと。起動、失敗・拒否のあった起動、失敗、拒否。結果の記録がある呼び出しの数はエージェントごとには分からないので、率は出しません |
| skill・指示文の版 | 失敗をそれに結び付ける記録は無いので、**それを使ったセッションの単位**で数えます(分かるのは相関まで)。使ったセッションと、それ以外のセッションの失敗率を並べます。skill は、そのセッションで最初に呼んだ後の失敗・拒否の数も出します |

回数と率の分母は `tools.results` から、要因・エラー文・呼び直しは台帳の行から数えます(台帳は 1 セッション 500 行までなので、回数は行からは数えません)。率は、結果の記録がある呼び出しが 20 回以上のものだけ出します(これより少ないと、1 回の失敗で率が 5 ポイントを超えて動きます)。skill と指示文の版の率は、さらに 5 セッション以上のものだけで、比べる 2 つの率は片方が出せないときは両方「—」にします。ページの表は多い順に 50 行までで、`failures.json` には全件を書きます。閾値は `crates/atlas-report/src/failure_stats.rs` の `thresholds` にまとめています。

## LLM の判定(judgments.json)

`out/judgments.json` は、セッションごとの LLM の判定(推定人手工数など。作り方は [judge.md](judge.md))です。設定のフォルダ(共有の `AtlasSettings`。[README の「本番の置き方」](../README.md#本番の置き方sessionlog-と-atlassettings))を使うときは、`out/` ではなく `AtlasSettings/judgments.json`(依頼ごとの判定は `AtlasSettings/turn-judgments.json`)に置き、集計する人のあいだで共有します。取り込みはどちらの置き場でも、ファイルのロック(`judgments.json.lock`)の中で読み直してセッションごとに混ぜて書きます。判定するのは外部の LLM で、利用者が返答を取り込んだときだけ増えます(集計もこのツールも LLM を呼びません)。スキーマの版(`schemaVersion`)は 2 で、版 1(下の `wikiPages` の無い版)の `judgments.json` と返答もそのまま読めます(書くときの版は下の注のとおり、`wikiPages` を持つ項目があるときだけ 2 にします)。

| 項目 | 中身 |
|---|---|
| `taskCategory` / `taskSummary` | タスクの分類と要約 |
| `humanEffort` | 推定人手工数(`hours`・`low`・`high`・`confidence`・`rationale`) |
| `aiOutcome` | AI が達成したか・質・手戻り |
| `instructionsEffect` / `wikiEffect` / `skillsAgentsEffect` | 指示ファイル・llm-wiki・skill と agent のセッション全体への効果(−2〜+2 と根拠) |
| `wikiPages`(版 2 から。任意) | llm-wiki のページごとの判定 `{ page, helpful, reason }` の並び。`helpful` は `yes`(中身が後の作業に使われ、作業を進めた)/ `no`(使われなかった・誤った方向に導いた)/ `unknown`(記録から判断できない)。判定のパケットに載せたページ(1 セッション 10 ページまで)が対象 |
| `notes` / `judge` | 判定上の注意と、判定した出所(バックエンド・モデル・時刻。取り込んだものは `external`。前の版がこのツールの中で判定したものは `copilot-cli`・`anthropic` で、そのまま読む) |

- `wikiPages` が無い項目も取り込み、そのセッションのページを未判定にします(知らせません)。壊れている(配列でない・要素の形が違う)ときは、ほかの判定は取り込み、そのセッション(要素が壊れていたときはそのページ)を未判定にして、ログに知らせます(`judge import`・M365 Copilot の自動操作のログ)。パケットに無いページの名前の判定は、レポートを作るときに捨てます(`judgments.json` には返答のまま残ります)。
- 書くときの版は、どの項目も `wikiPages` を持たない間は 1、持つ項目ができたら 2 です。版 2 の `judgments.json` は、この機能より前の atlas.exe では読めず、`build` が止まります。
- レポート(`atlas.html`)への埋め込み: 読んだページの名前は、データの上の辞書 `wikiPageNames` に 1 回だけ置き(本文は入れません)、セッションの要約の `wiki.pages`(重複を除いて読んだ順)はその番号です。判定は `judgment.wikiPages` に `[ページの番号, yes | no | unknown]` で入れます(理由は埋め込まず、詳細ページの「LLM による判定(推定)」にだけ出します)。大きな vault を何度も読む使い方でも、名前の分は増えないようにするためで、件数での切り捨てはしていません。埋め込みの版(`atlas.html` のデータの `version`)はこれらを足して 18 にしました。版 17 以前の `atlas.html` にはページの名前が無いので、改善点のページごとの表は出さずに理由を出します。

## 改善点(規則による分析)
レポートの「改善点」の節(目次「概況」の「要点」の次)と、全件のページ `out/insights.html`、機械可読の `out/insights.json` です。LLM は使わず、決まった規則で集計します(llm-wiki のページごとの表の「役立ったか」の列だけは、利用者が判定を回したときの LLM の見立てを読んで並べます)。**分かるのは相関まで**なので画面でも「傾向」と書いています。指示文の効果は直接は測れません(同じ版でも依頼が違う)。率は 5 セッション以上のものだけ出し、未満は「—」です(セッション数の列で分かります)。閾値は `packages/report/src/lib/insights.ts` の `THRESHOLDS` にまとめ、根拠は `docs/PLAN.md` の「改善点の分析」にあります。

レポートの節では、箱を計算の対象で 2 つの群に分けて並べます。上の群「絞り込みに従う」(指示文の傾向・skill の傾向・llm-wiki の利用・止まっている箇所・llm-wiki のページごとの参照率と役立った率)は上の絞り込みの対象だけで計算し直し、下の群「全記録で計算」(長いのに注入が少ない指示文・スキル化の候補)は絞り込んでも変わりません。1 つの箱に両方を混ぜません。

| 箱 | 中身 | 計算の場所 |
|---|---|---|
| 指示文の傾向 | 指示文(AGENTS.md / CLAUDE.md 等)の版(内容のハッシュ)ごとの字数・注入セッション数・ツールの失敗率・手戻り率(同じファイルを 2 回以上編集したセッションの割合)・compaction と出力トークン / セッション。「版を変えた前後で悪化」(前後とも 5 セッション以上で失敗率か手戻り率が 10 ポイント以上悪化)を挙げ、前後比較は判定できた組と判定できない組の数を常に出す。版の名前から `instructions.html` の版へ移動できる(`export` 後) | レポート内で絞り込みに従って再計算 |
| skill の傾向 | skill ごとの呼び出し(利用者 / エージェント)、本文の字数、呼んだセッションと呼ばなかったセッションの失敗率(ツールの失敗・拒否 / 呼び出し。5 セッション以上で呼ばれた skill が無ければ列を出さない。呼ぶかどうかは作業の中身で決まるので、差は skill が原因とは限らない)、インストール済みで未使用(今の設定で無効なものに印) | 同上 |
| llm-wiki の利用 | 件数だけの 2 つの表: セッションの数(参照した / うち書き込みもあり / 書き込みだけ / 参照なし)と、参照の内訳の回数(索引 / 個別ページ(読んだページの延べ)/ wiki の skill / 検索・一覧など)。率・差・差の幅は出さない(参照するかは作業の中身で決まり、引数に vault の場所が出ない読み(相対パスだけの読み、vault の場所を渡さない MCP 経由の読みなど)は数えないため。率を並べない理由を箱の注に書き、数え方は用語の説明の「llm-wiki」へリンクする)。数え方の細目は [cli.md の「wiki の指定」](cli.md#wiki-の指定)。vault を指定せずに集計したときは件数を出さず理由だけ | 同上。**画面だけ**(`insights.html` と `insights.json` には無い) |
| 止まっている箇所 | 待ち時間(TTFT の中央値 20 秒以上)、失敗の連続(3 回以上)、余分な編集の多さ(同じファイルの 2 回目以降の編集の全ファイルの合計が 3 回以上)、権限確認の多さ(10 件以上)、compaction(3 回以上)のどれかに当たるセッション(理由の数の多い順、同数なら余分な編集・失敗の連続の多い順)と、プロジェクト別の該当数(`insights.html` は理由の内訳付きの表) | 同上 |
| llm-wiki のページごとの参照率と役立った率 | ページ 1 行の表(幅いっぱいの箱)。列: ページ / 読んだセッション / 参照率(読んだセッション ÷ wiki を参照したセッション)/ 役立った / 役立たなかった / 分からない / 未判定 / 役立った率(役立った ÷(役立った + 役立たなかった))。役立ったかは判定(`judgments.json` の `wikiPages`。下の「[LLM の判定(judgments.json)](#llm-の判定judgmentsjson)」)の LLM の見立てで、ログで数えた参照率と別の列に並べ、1 つの点数にしない。分母が 5 セッション未満の率は「—」(閾値は他の率と同じ `THRESHOLDS.MIN_SESSIONS`)で、どのページも「—」の率は列ごと出さずに理由を注に書く。ページの名前は共通のフォルダと `.md` を除いて出し(元の名前は名前に重ねると出る)、名前を押すとそのページを読んだセッション(詳細へのリンク)とそれぞれの見立てが開く。列の見出しで並べ替える。ログで分かるのは読んだことまでで、回答の中で引用したかは見ない。vault を指定せずに集計したとき・指定の記録が無い古い集計・ページの名前の無い古い埋め込み(版 17 以前)では表を出さず理由だけ | 同上。**画面だけ** |
| 長いのに注入が少ない指示文 | 字数が全版の上位 25% で、注入されたのが 3 セッション未満の版(項目ごとに今の版=最後に読み込まれた版だけ、最後の読み込み日を添える)。全体での希少さの話なので絞り込みに従わない | レポート内で全記録から計算 |
| スキル化の候補 | (a) 似た依頼文の繰り返し: 依頼文を正規化(小文字、パス・URL・数字・id を印に)して文字 3-gram の Jaccard 類似度 0.6 以上を束ねる。(b) 同じツールの並びの繰り返し: 本体のターンごとのツール列から長さ 3〜6 の部分列(連続の重複は潰し、閲覧系以外のツールが 2 種類以上、周期的な繰り返しは除く)。どちらも 3 回以上・2 セッション以上。スコア = 回数 × 1 回の実働の中央値(分。1 分未満は 1 分、2 時間で頭打ち。実働はターンの中で 5 分を超えて出来事が無かった区間(返答待ちや放置)を除いた時間で、セッションの実働時間と同じ数え方)。相づち(OK / 続けて)と動作確認の定型文(行頭の reply with 等)、20 字未満は除く | `build` / `export` 時に全セッションで計算し、上位 30 件を埋め込む(箱には全件数を出す。全件は `insights.html`) |

### スキルの下書き(`atlas skill-draft`、任意)

```
bin\atlas.exe skill-draft <番号>  # out/insights.json の候補の番号。--backend copilot-cli(既定)/ anthropic、--model、--timeout
```

候補の繰り返し回数・代表の依頼文・ツールの並びを LLM に渡し、SKILL.md の形の下書きを `out/skill-drafts/<番号>-<名前>.md` に書きます。**明示したときだけ動き、`build` / `export` / `all` では呼びません**。このツールが LLM を呼ぶのはここだけです(判定は外部の LLM に頼みます。[judge.md](judge.md))。費用は 1 回の実行で 1 リクエストです。`copilot-cli` はモデル 1 リクエスト相当の AI クレジット、`anthropic` は Anthropic API の従量課金(`ANTHROPIC_API_KEY` が必要)を消費します(`anthropic` は機能 `anthropic-backend` を付けてビルドした atlas だけ。起動用の `.bat` がする既定のビルドには入っていません。[development.md](development.md))。モデルは `--model`、無ければ設定の `judgeModel`([cli.md の「skill-draft に使うモデルの指定」](cli.md#skill-draft-に使うモデルの指定))。`copilot-cli` は安全策(`--no-custom-instructions`、`shell` / `write` / `url` と MCP の拒否、`--add-dir` なし、空の作業フォルダ)を付けて動きます。下書きの作業フォルダは前の版の判定と同じ接頭辞にしており、次回の集計では「(atlas の判定)」に分類されて候補に戻りません。テストは偽の CLI(`ATLAS_COPILOT_BIN`)と fetch の差し替えで行い、本物は呼びません。下書きは案なので、使う前に読んで直してください。
