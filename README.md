# agent-session-atlas

Local-first analytics for GitHub Copilot session logs — visualize tokens, skills, agents, hooks, instruction files, and llm-wiki usage from `~/.copilot`, without an LLM.

GitHub Copilot のセッションログ(`%USERPROFILE%\.copilot`)を手元で集計し、ブラウザで読めるレポートにするツールです。集計に LLM は使わず、元のファイルも書き換えません(複製してから読みます)。

## 何が分かるか

- トークン・AI 使用量(AIU)・premium request・変更行数を、プロジェクト・月・モデル・クライアント別に
- 使ったツール・MCP サーバー・skill・agent・hook・指示ファイルの利用ランキングと、インストール済みで使っていない skill
- ツールの失敗を要因(時間切れ・対象が見つからない・引数の誤り・通信の失敗など)別に数え、どのツールがどの要因で失敗しているか。失敗と拒否は 1 件ずつ記録し(エラー文・引数・その後に何をしたか)、同じ文で繰り返している失敗と、ツール・MCP サーバー・エージェント・skill・指示文の版ごとの集計を別ページで見られる
- 摩擦(ツールの失敗、権限の確認、compaction、エラー)と待ち時間
- 依頼(ターン)ごとの工程(調査・実装・検証など)と、どの工程でどれだけ詰まったか(ツールの失敗・拒否・中断・再編集など)。依頼の種類(作業・質問・修正など)ごとの内訳
- AI の成果がどれだけ採用されたか(そのまま・中身を修正・体裁を修正・不採用)と、合わなかった点・普段の工程ごとの差(任意。LLM に判定させたときだけ)
- 依頼ごと・セッションごと・ツールの失敗と拒否ごとの表(CSV。Excel で開ける)
- 指示ファイルの注入と llm-wiki の参照(参照したセッション・書き込みだけのセッションの件数。画面・表・ログのどこでも同じ数え方)
- 改善点の傾向(指示文や skill の版の前後比較、llm-wiki の利用の件数、止まっている箇所、スキル化の候補)と、llm-wiki のページごとの参照率(読んだセッション ÷ wiki を参照したセッション)。工数を LLM に判定させたときは、ページごとの「役立ったか」の見立てと役立った率も別の列で並べます
- セッションごとの詳細ページ・経過の記録(Markdown)・自分用のメモ
- 推定人手工数(任意。LLM に判定させたときだけ)
- 管理ツールのタスクごとの工数(任意。管理ツールが書き出した XML を設定したときだけ)。AI を使わなかった場合の工数(推定人手工数)と、AI を使った場合の工数(開始から完了までの稼働時間帯の時間)を並べます
- AI が作った変更が、その後の VCS(Git / SVN / Perforce)のファイルに残っているか。VCS は読むだけで、LLM は使いません([docs/outputs.md](docs/outputs.md#ai-の変更の残存vcs-の照合))
- 2 つの条件(期間・プロジェクト・工程・推論強度・モデル・wiki の参照)の並べ比べ(人の記録があれば、人ごとの差も)
- テストの合否と件数、1 セッションの中の推移(何回目の実行で全部通ったか、そこまでの実働と AI 使用量、最後まで通らなかった「未達」)。テストの実行ファイルが印つきの 1 行 JSON を標準出力に書いたときだけ([docs/outputs.md](docs/outputs.md#テストの結果印つきの-1-行-json))
- 表は CSV に加えて、同じ中身の SQLite(`out/tables/atlas.sqlite`)でも書きます。テストの実行・結果・件数も入ります

## 使い方

前提: Git。このリポジトリを `git clone` して使います(配布用の zip はありません)。動かすのは 1 つの実行ファイル `bin\atlas.exe` で、起動用の `.bat` が、この PC でビルドして用意します。そのため Node.js 24 以上と Rust と、Windows では Visual Studio の C++ のビルドツールが要ります(下記「[atlas.exe の用意と更新](#atlasexe-の用意と更新)」。`atlas.exe` は配っていません)。

0. (任意)設定は、`atlas.bat` で開いた画面の右上の「設定…」で決められます(llm-wiki の vault・普段の工程名・アップロード先・まとめて送るプロジェクト)。黒い窓で決めたいときは、`setup.bat` も使えます(下記「[初期設定(setup.bat)](#初期設定setupbat)」)。llm-wiki の参照を数えないなら、どちらも飛ばして構いません。
1. リポジトリ直下の `atlas.bat` をダブルクリックします(初回は `bin\atlas.exe` をこの PC でビルドします。数分から十数分かかります)。
2. 集計が終わると、既定のブラウザにレポートが開きます。約 800 セッションで十数秒かかります。2 回目以降は、変わっていないファイルの複製を省きます。
3. 読み終わったらブラウザを閉じます。黒い窓とローカルサーバ(`127.0.0.1` だけに公開)も止まります。

もう一度 `atlas.bat` を実行すると集計し直します。新しい版は、`.bat` を開いたときに自動で取り込みます(`git pull` は要りません。下記「[atlas.exe の用意と更新](#atlasexe-の用意と更新)」)。前に開いた画面のサーバ(黒い窓やタブが開いたままのもの、画面や `open-folder.bat` で開いた別のフォルダのもの)が動いていれば、`atlas.bat` は最初にそれを止めてから、新しい版にして集計し、開き直します(「前に開いた画面のサーバを止めました」と 1 行出ます。開いたままの古いタブは閉じて構いません)。

集計・判定・送る操作(毎日自動で送るタスクを含む)が動いているときは、`atlas.bat` は何も止めずに続け(その旨を 1 行出します)、新しい版にもしません。前の版のサーバが動き続けていると、画面の上に「画面とサーバの版が違います」と出ます。そのときは、集計などが終わってから `atlas.bat` を開き直すか、次の `stop.bat` で止めてから開き直し、新しく開いた画面を使ってください(前の版で作ったページを開いたときも同じ帯が出ます。直し方は同じです)。

### atlas を止める(stop.bat)

画面のサーバは、どこかのブラウザのタブが開いたままだと動き続けます(タブを閉じずに放っておいたときは、画面からの知らせが途絶えてから 30 分で止まります)。画面から別のフォルダを開いたときのサーバは、黒い窓を出さずに動きます。`atlas.bat` は、開いたときに動いているのがそうした画面のサーバだけなら、自分で止めてから開き直します。集計・判定・送る操作などが動いているとき(画面の中で「集計し直す」などが動いているときも)と、環境変数 `ATLAS_NO_AUTO_UPDATE` が `1` のときは止めないので、その間は `atlas.bat` を開いても新しい版にせず、前のサーバを開き直すだけになります。

そういうときや、画面のサーバを `atlas.bat` を開かずに止めたいときは、リポジトリ直下の `stop.bat` をダブルクリックします。このフォルダの atlas をすべて止めます。

- 止めるのは、このフォルダの `bin\atlas.exe` で動いているものと、その中で動いているもの(集計・判定と、判定が動かした Copilot CLI など)だけです。別のフォルダの atlas やほかのアプリは止めません。
- 画面のサーバだけなら、尋ねずに止めます。集計・判定・送る操作(毎日自動で送るタスクを含む)が動いていれば、止める前に尋ねます(`y` で止めます)。途中で止めても、集計は次の集計で作り直し、判定は済んだ分が残ります。尋ねずに止めるなら `stop.bat -Yes` です。
- 止めた後、残った印(`out\.serve.json` など)を消します。開いたままのタブは閉じてから、`atlas.bat` を開き直してください。新しい版にしてから開きます。
- `bin\atlas.exe` の用意や更新はしません(実行ファイルが壊れていても止められるよう、PowerShell だけで動きます。`scripts\stop-atlas.ps1`)。

### 初期設定(setup.bat)

同じ設定は、`atlas.bat` で開いた画面の右上の「設定…」でも決められます(`setup.bat` を使わなくても構いません)。画面では、まとめて送るプロジェクトも選べます。

`setup.bat` は、`bin\atlas.exe` を用意し(初回だけ)、次の 3 つを順に尋ねて、リポジトリ直下に `atlas.config.json` を書きます。集計はしません。終わったら `atlas.bat` をダブルクリックします。

1. **llm-wiki の vault**: `y` を入れるとエクスプローラー(フォルダを選ぶ画面)が開くので、vault のフォルダを選びます。フォルダを黒い窓にドラッグするか、フォルダ名を入力しても決められます。フォルダ名だけで登録し(フルパスより確実です)、中に `wiki` フォルダがあれば個別ページの場所として勧めます。インストール済みの skill のうち、名前に `wiki` を含むものは「wiki の skill」として数えるか尋ねます。vault は続けて複数入れられます。何も入れずに Enter で次へ進みます。
2. **普段の工程名**: 依頼ごとの採用の判定で使う工程名です。Enter で今のまま(初回は既定)になります。変えるときは `設計 / 実装 / テスト` のように区切って入力します。
3. **アップロード先**: `upload-project.bat` で、セッションの生ログを写す基底のフォルダ(例: `E:\dev\atlas-logs`)です。まだ決めていなければ、Enter でエクスプローラーが開くので、フォルダを選びます(決めないなら `n`)。決めてあれば Enter で今のまま、`y` でエクスプローラーが開きます。フォルダを黒い窓にドラッグするか、フルパスを入力しても決められます。後から画面や `upload-project.bat` でも決められます。

最後に書き込む内容を表示し、確認してから書きます。前の設定は `atlas.config.json.bak` に残します。もう一度実行すると、今の設定を見ながら直せます。手で書くときの項目は [docs/cli.md の「wiki の指定」](docs/cli.md#wiki-の指定) にあります。

### 画面でできること

`atlas.bat` から開いた画面では、次の操作ができます。`out\atlas.html` を直接開いたときは閲覧と絞り込みだけです。

| 操作 | 場所 |
|---|---|
| 期間・プロジェクト・モデルなどで絞り込む | レポートの上部 |

| 設定…(llm-wiki の vault・普段の工程名・アップロード先・まとめて送るプロジェクト。`setup.bat` と同じ設定) | レポートの右上 |
| 判定する…(工数 / 依頼ごとの採用 / タスクの紐づけ。判定するのは外部の LLM で、チャットに貼るか ZIP にまとめて渡します。「タスクの紐づけ」は管理ツールのタスクを設定したときだけ) | レポートの右上 |

## atlas.exe の用意と更新

`atlas.exe` は配っていません。いつも、この PC で、このフォルダのソースからビルドします(GitHub のリリースで配るのは 2026-11-23 にやめました)。

起動用の `.bat`(`atlas.bat`・`setup.bat`・`upload-project.bat`・`schedule-upload.bat`・`open-folder.bat`。止める `stop.bat` は除く)は、最初に `scripts\ensure-atlas.ps1` を動かして、`bin\atlas.exe` が今のソースから作ったものかを確かめます。`bin\atlas.exe --version` に出る、作ったときのコミットが今のコミット(`HEAD`)と同じなら、そのまま使います。git が管理しているファイルを変えたまま作ったもの(コミットの後ろに `-dirty`。開発の手元だけ)は、同じとはみなしません。git で取得したフォルダでなければ、版を `Cargo.toml` の `version` と比べます(版はふだん上げないので、そういうフォルダでソースを変えたら `bin\atlas.exe` を消してから開きます)。違えば次のようにします(管理者の権限は要りません)。

1. ビルドに要るもの(下記)があれば、この PC でビルドして `bin\` に置きます(`npm ci` → `npm run build:report` → `cargo build --release`。経過は `bin\build.log`)。初めては、依存のビルドも含めて数分から十数分かかります(PC による)。2 回目からは、変わったところだけをビルドし直すので短くなります。
2. ビルドに要るものが無ければ、何を入れればよいかを出します。前のソースから作った `bin\atlas.exe` があれば、今回はそれで開きます(今のソースの変更は入っていないことを 1 行出します)。前のものも無ければ止まります。ビルドに失敗したときも同じです(`bin\build.log` の最後を出し、そのコミットを `bin\build-failed.txt` に書きます)。
3. 同じフォルダで 2 つ同時にはビルドしません(毎日自動で送るタスクがビルドしている間に `.bat` を開いたときなど。印は `bin\build.lock`)。前に作った `bin\atlas.exe` があれば、数秒待ってからそれで開きます。無ければ、ほかのビルドが終わるのを待ちます。

続けて、atlas を新しい版にします(`bin\atlas.exe self-update`。毎日自動で送るタスクの「送る前に、atlas を新しい版にします」と同じ確かめ方です。下記「[毎日自動で送る](#毎日自動で送るschedule-uploadbat)」)。`git fetch` で新しいコミットを取ってきて、早送りで取り込めるときだけ取り込み、その版の `bin\atlas.exe` をビルドします。ビルドできなければ、前の版のコミットに戻します(`bin\atlas.exe` は置き換えていないので、前と同じもので開きます)。ビルドできなかったコミットは、開くたびには試しません(もっと新しいコミットが出たら、それを試します。もう一度試すなら `bin\build-failed.txt` を消します)。コミットが変わったら、git が書き換えたかもしれない `.bat` を最初から開き直します。

- 次のときは新しい版にせず、今の版のまま開きます(理由を 1 行出します): `main` 以外のブランチにいる・手元にだけあるコミットがある・git が管理しているファイルを手で変えている・このフォルダの atlas が動いている(前に開いた画面のサーバだけなら、`atlas.bat` は先に止めるので当てはまりません。集計などが動いているときと、ほかの `.bat` を開いたときは止めないので、`stop.bat` で止めます。上記「[atlas を止める](#atlas-を止めるstopbat)」)・ネットワークにつながっていない(`git fetch` は 20 秒まで待ちます)・ビルドに要るもの(Node.js の版が `package.json` の `engines` より古い・`cargo` が動かないときも含む)が無い・前にこの PC でビルドできなかったコミットしかない・git で取得したフォルダではない。
- 最新なら何も出しません。
- 開くたびの更新をしないなら、環境変数 `ATLAS_NO_AUTO_UPDATE` を `1` にします(例: `set ATLAS_NO_AUTO_UPDATE=1` の後に、同じ黒い窓から `atlas.bat` を実行する。ずっとしないなら、Windows の「環境変数を編集」でユーザーの環境変数に足します)。このときは、`atlas.bat` は前に開いた画面のサーバも止めません(動いていれば、それを開き直します)。毎日自動で送るタスクの更新は、`schedule-upload.bat` の `u` で切り替えます。

この PC でビルドするのに要るもの(atlas を使う PC には、どれも要ります):

- Node.js 24 以上(<https://nodejs.org/>。画面のビルドに使います)
- Rust(<https://rustup.rs/>。stable の `cargo`)
- Windows では、Visual Studio Build Tools(<https://visualstudio.microsoft.com/visual-cpp-build-tools/>)の「C++ によるデスクトップ開発」(MSVC と Windows SDK)。Rust のリンカーと、atlas に入れる SQLite のコンパイルに使います。Visual Studio を入れてあって C++ のワークロードがあれば、それで足ります(rustup の Windows 用のインストーラーも、無ければ入れるよう案内します)。`scripts\ensure-atlas.ps1` は `vswhere.exe` で x64 の C++ のビルドツール(`Microsoft.VisualStudio.Component.VC.Tools.x86.x64`)を探し、見つからなければ PATH の `cl.exe` と `link.exe` を見ます。

- これらが無い PC では、`atlas.exe` を用意できません。前に作った `bin\atlas.exe` があれば、それを使い続けますが、新しい版にはなりません。
- 画面のサーバが前の `bin\atlas.exe` で動いたままでも置き換えられます(今のものはいつも `bin\atlas.prev.exe` に移してから置きます。その前の `atlas.prev.exe` が動いていて消せなければ、別の名前に移し、次に用意するときに消します)。`bin\atlas.prev.exe` は、新しい版が動かなかったときに、ビルドせずに戻すのに使います。
- `bin\` は git に入れません(消しても、次に `.bat` を開くとビルドし直します)。
- 既定のビルドには、skill-draft で従量課金の Anthropic API を直接呼ぶ経路(`--backend anthropic`)は入りません([docs/development.md](docs/development.md))。
- 前の版で使っていた環境変数 `ATLAS_BUILD_LOCAL`(リリースを取りに行かずにビルドする指定)は、もう読みません。付けたままでも害はありません。

## 共有するときの注意

**`out/` はそのまま渡さないでください。** スナップショット・セッション記録・全文記録には依頼文・応答・ツールの結果・ファイルのパスがそのまま入り、秘密情報が混じることがあります。`atlas.html` と詳細ページにも、プロジェクト名・パス・ブランチ、最初の依頼と最後の応答、メモ(`atlas.html` には先頭の 1 行、詳細ページには全文と画像)が入ります。

atlas には、名前やパスを伏せて出す機能はありません。渡すときは、中身を確かめてから、渡してよいファイルだけを渡してください。レポートがリンクしているファイルの一覧は [docs/cli.md の「レポートのファイル」](docs/cli.md#レポートのファイル) にあります。

## コマンドで使う

期間の絞り込み・記録の中身の調整・全件の全文記録など、細かい指定はコマンドで行います。

```
bin\atlas.exe all                     # atlas.bat と同じ集計(snapshot → extract → metrics → export)
bin\atlas.exe all --since 2026-07-01  # 7 月以降に更新されたセッションだけ
bin\atlas.exe export --full           # 解析用の全文記録(外に出さない前提)
bin\atlas.exe serve                   # 集計せずに画面だけ開く
bin\atlas.exe --help                  # 使い方
```

コマンドとオプションの一覧は [docs/cli.md](docs/cli.md)、出力ファイルの中身は [docs/outputs.md](docs/outputs.md) にあります。

## llm-wiki の参照を数えるとき

**vault を指定しないと、llm-wiki の参照は数えません。** そのレポートでは、wiki の件数を出さずに「数えていません(0 件という意味ではありません)」と出します。`setup.bat` で指定するか、リポジトリ直下に `atlas.config.json` を置いて、vault のフォルダ名を書いてください(雛形は `atlas.config.example.json`)。

```json
{ "wikis": ["my-wiki"] }
```

`path` にはフルパスよりもフォルダ名だけを書くほうが確実です。索引やページの場所の指定、数え方は [docs/cli.md の「wiki の指定」](docs/cli.md#wiki-の指定) にあります。wiki のあり / なしで結果が変わるかを確かめる手順は、[docs/screen.md の「skill・llm-wiki・MCP サーバー・推論強度の違いを確かめる」](docs/screen.md#skillllm-wikimcp-サーバー推論強度の違いを確かめる)にあります。

## 推定人手工数(任意)

「同じ作業を人が AI なしでやったら何時間かかるか」を LLM に推定させ、レポートに足せます。集計とは別の手順です。推定には幅と確信度を付けますが、人手での実測ではありません。同じ判定で、読んだ llm-wiki のページごとに「役立ったか」(役立った / 役立たなかった / 分からない)も見立てさせ、改善点のページごとの表に出します([docs/judge.md](docs/judge.md#llm-wiki-のページごとの判定))。

判定するのは、あなたが使っている外部の LLM です。このツールは LLM を呼ばず、渡すファイルを作って、返ってきた答えを取り込みます。

- **M365 Copilot のアプリを自動で操作して(Windows)**: 「チャットに貼って判定する」の手順 2 にある「M365 Copilot で自動で判定する」を押すと、開いている M365 Copilot のアプリをこのツールが操作し、未判定のファイルを 1 つずつ送って(モデルは Think Deeper)、返答を取り込みます。終わるまで M365 Copilot の画面に触らないでください([docs/judge.md](docs/judge.md#m365-copilot-のアプリを自動で操作するwindows))。
- **チャットに貼って(M365 Copilot など。ファイルの添付か貼り付けができる LLM なら使えます)**: 「判定する…」で「チャットに貼って判定する」を選びます。画面の 4 つの手順(添付ファイルを作る → ダウンロードしてチャットに添付する → 返答を貼って取り込む → レポートに反映する)に沿って進めます。ターミナルは使いません。
- **ZIP にまとめてエージェントに渡して**: 「判定する…」で「ZIP にまとめてエージェントに渡す」を選びます。未判定のセッションを 1 つの ZIP にまとめ、フォルダを読めるエージェントやローカルの LLM に渡して、書かせた `judgments.json` を取り込みます(渡すときの注意は [docs/judge.md](docs/judge.md#エージェントやローカルの-llm-に渡す))。

1 セッションだけを判定し直すときは、`bin\atlas.exe bundle --session <id>` でそのセッションだけの添付ファイルを作って渡します。手順と安全策は [docs/judge.md](docs/judge.md) にあります。

**取り込んだ後のレポートの作り直し**: 判定(工数・依頼ごとの採用)やタスクの紐づけを取り込めたら、レポートを作り直します。作り直しは、いつも既定の記録の出し方の `export` で行います。取り込みのコマンドに付けた `--full`・`--tool-output`・`--max-chars`(記録の出し方)は引き継がず、`--since`・`--project` などの絞り込みも引き継ぎません(取り込みの `import`・`m365` に絞り込みを付けると、何も取り込まずに止まります)。記録をすべて出したレポートや、絞り込んだレポートが欲しいときは、取り込んだ後に `bin\atlas.exe export --full` などを実行し直してください。

## 依頼ごとの採用(任意)

依頼(ターン)ごとに、AI の成果が利用者にどう扱われたか(そのまま採用 / 中身を修正して採用 / 体裁を修正して採用 / 不採用。質問なら 役に立った / 追加で聞いた / 的外れ)と、合わなかった点(意図の取り違え・誤り・品質・範囲・環境)、普段の工程名を LLM に判定させ、「工程と詰まり」の欄に足せます。判定の材料は次の依頼の文と、その依頼の間の拒否・中断です。LLM が勝手に動くことはありません。

- **チャットに貼って(M365 Copilot など。既定)**: 「判定する…」で「依頼ごとの採用」と「チャットに貼って判定する」を選び、工数と同じ 4 つの手順で進めます。
- **ZIP にまとめてエージェントに渡して**: 「依頼ごとの採用」と「ZIP にまとめてエージェントに渡す」を選ぶと、`turn-bundle.zip` を作ります。エージェントに書かせた `turn-judgments.json` を取り込みます。採用を判定できる依頼(次の依頼がある依頼)が ZIP の先頭のどの塊までかも出します。

普段の工程名は `atlas.config.json` の `phases` で変えられます(既定: 要件定義 / 設計 / 実装 / テスト / レビュー / 調査 / 運用 / その他)。詳しくは [docs/judge.md の「依頼ごとの採用」](docs/judge.md#3-依頼ごとの採用) にあります。

## 管理ツールのタスクと工数(任意)

管理ツールが書き出したタスクの XML を設定すると、セッションをタスクに紐づけ、タスクごとに工数を並べます。読むのはタスクの ID・名前・状態と、設定したときだけ完了日時です。XML の形は管理ツールによって違うので、読み方を設定で決めます。

`atlas.config.json` に `tasks` を書きます(`file` 以外は省けます。下の値が既定です。`doneAt` は既定では読みません)。

```json
{
  "tasks": {
    "file": "D:\\export\\tasks.xml",
    "item": "Task",
    "id": "Id",
    "name": "Name",
    "status": "Status",
    "doneStatus": ["Done", "Completed", "Closed", "完了"],
    "doneAt": "ClosedDate",
    "workHours": { "days": [1, 2, 3, 4, 5], "start": "09:00", "end": "18:00" }
  }
}
```

- `file`: 書き出した XML。相対パスは設定ファイルのフォルダから見ます。64 MB まで読みます。DTD(`<!DOCTYPE …>`)のある XML は読みません。
- `item`: タスク 1 件の要素の名前。入れ子になっていても、この名前の要素はすべて 1 件のタスクです。名前空間は見ません。大文字と小文字は区別しません。
- `id`・`name`・`status`: タスクの要素の、属性か子の要素の名前。属性を先に探し、無いか空なら子の要素の文字を使います。`"@key"` のように先頭に `@` を付けると属性だけを見ます。
- `doneStatus`: 完了とみなす状態(前後の空白を除き、大文字と小文字を区別せずに比べます)。
- `doneAt`(任意): 完了日時の属性か子の要素の名前(`id` などと同じ書き方で、`@` を付けると属性だけ)。完了のタスクのこの値を読めれば、それを完了の時刻にします(出所は「記録」)。読める書き方は ISO 8601(`2026-11-20T15:30:00+09:00`・`2026-11-20T06:30:00Z` など)と、`2026-11-20`・`2026/11/20`(月と日は 1 桁でも可。後ろに空白か `T` を挟んで `15:30` か `15:30:00` を付けられます)です。値が無いか読めないタスクは、今までどおり完了を見た書き出しの時刻にします(出所は「観測」。読めない値があると、件数を注意に出します)。
  - **時差の無い時刻**(`2026-11-20 15:30` など)は、**集計した PC の時刻**(その PC の時間帯)で読みます。管理ツールと集計する PC の時間帯が違うときは、時差を付けて書き出してください(稼働時間帯も同じく集計した PC の時刻で見ます)。
  - **日付だけの完了日**(`2026-11-20`)は、その日のうちに終わったとみなします。工数(稼働時間帯の工数)は、その日の**稼働時間帯の終わり**(`workHours.end`。`24:00` なら翌日の 0 時)までを数えます。紐づけの候補と「完了の後に始まったセッション」の判定には、その日の**終わり(24:00)**を使います(その日の夜に始めたセッションも、そのタスクの作業として数えます)。ただし、紐づいたセッションがどれもその日の稼働時間帯の終わりより後に始まったタスクは、工数が 0 時間になるので比べません(理由は「稼働時間帯に重ならない」)。読んだときの日付の文字(`2026-11-20`)を残し、工数と判定の時刻は、その日付と集計する PC の時間帯から決めます。画面の「完了を確認」の列と `tasks.csv` の「完了を確認した時刻」はその日付をそのまま出し(見る PC の時間帯で日付がずれません)、`tasks.csv` の「完了時刻の出所」は「記録(日付だけ)」です。
  - **0 時ちょうどの日時**(`2026/11/20 0:00:00`・`2026-11-20T00:00` など、時差の無い 0:00:00 ちょうど)も、日付だけとみなします。日付だけの項目を日時の形で書き出す管理ツールがあり、0 時に終えたとすると、その日の作業が工数に入らないためです。時差を付けた 0 時(`2026-11-20T00:00:00+09:00`)と、秒や小数のある時刻(`0:00:01`)は、書いたとおりの時刻です。
  - **読めない値**として観測に戻すのは、書き方の違うものと、2000 年より前のもの、XML の書き出し(ファイルの更新時刻)の 1 日後より後のもの(予定日の取り違えなど)です。
  - **前に記録で決めた完了の時刻は残します**: 完了のまま、値が読めなくなったとき(注意は「前の記録を残します」と、観測で数えるものとは分けて出します)や値が無くなったとき、設定から `doneAt` を外したときも、記録で決めたタスクは記録の時刻と出所のままです(外した後に完了したタスクは観測です)。初めから観測で数え直すときは、`tasks.json` を消して読み直します(そのときは完了済みのタスクの完了の時刻が分からなくなります)。
- `workHours`: 稼働時間帯。`days` は曜日の番号(1 = 月曜 … 7 = 日曜)、時刻はこの PC の時刻です。日をまたぐ時間帯は指定できません。

例えば、次のような XML なら `"item": "WorkItem", "id": "@key", "name": "Title", "status": "State"` と書きます。

```xml
<Export>
  <WorkItem key="T-101" Title="画面の表示を直す"><State>Resolved</State></WorkItem>
</Export>
```

**タスクの状態**: XML は、集計のたび(`atlas.bat`・画面の「集計し直す」)と `atlas tasks sync` で読み、タスクごとの状態を `atlas-notes\tasks.json` に残します。完了を確認した時刻は、`doneAt` で XML の完了日時を読めればその日時(記録)、そうでなければ完了と分かった XML のファイルの更新時刻(観測)です。どちらだったかも `tasks.json` に残し(`doneAtSource`)、タスクの節の「完了を確認」の列と `tasks.csv` の「完了時刻の出所」に出します。

**紐づけ**: 1 つのセッションは、いくつかのタスクに紐づくことがあります(1 つのセッションに 10 個まで。誤った当たりで長くならないための上限です)。1 つのタスクにも、いくつものセッションが紐づきます。

1. 機械: 集計のたびに、セッションの題名と依頼の文に、タスクの ID か名前(4 文字以上)が出てくるかを探します。ID で当たったタスクだけなら、そのすべてに紐づけます(`DEMO-101 と DEMO-103 を直す` なら 2 つ)。ID の当たりが無く、名前で当たったタスクがちょうど 1 つなら、そのタスクに紐づけます。当たりが無いとき、名前だけで当たったタスクがあって当たったタスクが 2 つ以上のとき、10 個を超えるときは決めません(LLM か手動で決められます)。数字だけの ID(`101` など)は、`#101` のように `#` を付けて書いたものだけを探します(ただの数字は件数などに当たりすぎるため。1 文字の ID は探しません)。`#101` はリポジトリの PR や課題の番号の書き方とも同じなので、数字だけの ID を使う管理ツールでは、PR の番号を書いた依頼が同じ番号のタスクに紐づくことがあります(違っていたら詳細ページで直してください)。`#101` と `#102` のように数字の ID をいくつか書いた依頼は、ID で当たったものとして、そのすべてのタスクに紐づきます。当たりが重なるときは長い方だけを使います(`DEMO-102-1` の中の `DEMO-102` は数えません)。
2. LLM: 機械で決まらなかったセッションを、頼んだときだけ外部の LLM に選ばせます(作業したタスクを 0 個以上選びます)。画面の「判定する…」で「タスクの紐づけ」を選び、工数の判定と同じく、チャットに貼るか ZIP にまとめて渡して、返答を取り込みます。コマンドでは `atlas tasks bundle` で作り、`atlas tasks import <ファイル>` で取り込みます([docs/judge.md の「管理ツールのタスクへの紐づけ」](docs/judge.md#4-管理ツールのタスクへの紐づけ))。
3. 手動: 詳細ページの「タスク」の行の「変える…」で、タスクを加える・外して保存する・どのタスクでもない・自動に戻すができます。「自動に戻す」は、手動の紐づけにも LLM の紐づけにも使えます。

紐づけの出所(機械・LLM・手動)はセッションごとに 1 つです。手動は LLM と機械より、LLM は機械より先に使います。ただし LLM が「どのタスクでもない」とした紐づけは、後で機械の当たりが決まれば機械の紐づけに置き換えます。紐づけは `atlas-notes\task-links.json` に残ります。セッション一覧の「タスク」の列にも出ます(列の見出しで並べ替えられます)。

**工数の数え方**: 概況の「管理ツールのタスク」の節と `out\tables\tasks.csv` に出ます(セッションとタスクの組ごとの按分は `out\tables\session-tasks.csv`)。

- AI を使わなかった場合の工数: 紐づいたセッションの推定人手工数(LLM の推定)の合計。確信度が 30% 以下の推定は入れません。工数の判定をしていなければ出ません。
- AI を使った場合の工数: 紐づいた最初のセッションの開始から、完了を確認した時刻までのうち、稼働時間帯に入る時間。完了の時刻が分かるタスクだけです(完了に変わるのを XML で見たか、XML に完了日時の記録があるもの。初めて見たときに完了していて記録も無いタスクは、完了した時刻が分からないので出しません)。完了を確認した時刻より後に始まったセッション(手動か LLM で紐づけたときだけありえます)は、開始に使いません。
- AI の実働: 紐づいたセッションの実働時間の合計。
- 複数のタスクに紐づくセッションの実働時間と推定人手工数は、タスクの数で等分して数えます(2 つなら半分ずつ)。タスクの一覧に無いタスクと、完了を確認した後に始めたセッションのタスクには数えず、残りのタスクで分けます。タスクの値を足すと、セッションの値を重ねずに全体の値になります。セッションの数は等分せず、紐づいたタスクごとに 1 つずつ数えます。AI を使った場合の工数(開始から完了まで)は等分しません。
- 詰まりの列(タスクの表の右側): 紐づいたセッションの人数(人の記録があるとき)・主なモデル(本体のリクエストがいちばん多いモデル)・摩擦(ツールの失敗・拒否、中断、文脈圧縮の数)と、依頼ごとの判定があれば判定した依頼の数と直し・不採用・的外れの数と割合。どれも紐づいたセッションすべてを 1 つずつ数えます(等分しません)。割合は、分母(直しと不採用は判定できた作業の依頼、的外れは判定できた質問)が 5 件に届かなければ「—」です。列の意味は [docs/screen.md の「画面の見方」](docs/screen.md#画面の見方)の「管理ツールのタスク」にあります。

合計は、完了の時刻が分かり、紐づいたセッションのすべてが完了を確認した時刻までに始まり、開始から完了までが稼働時間帯に重なり(稼働日でない日だけ・稼働時間帯の外だけで作業して完了したタスクは、工数が 0 時間になるので「稼働時間帯に重ならない」として比べません)、確信度の低くない推定があるタスク(比べられるタスク)だけで出します。完了の時刻が記録のものと観測のものは、どちらも比べるタスクに入れ、件数を分けて出します(タスクの節の「比べられる完了タスク」の注記と、全体サマリの表紙)。比べられるタスクが少ないうちは、2 つの工数の比を出しません。

**限界**: どれも実際に人が作業した時間ではありません。

- 完了を確認した時刻(観測)は、書き出しの間隔の分だけ、実際に完了した時刻より遅れます。毎日書き出すなら、最大で 1 日ほど遅れます。記録の完了日時は管理ツールに入っていた値で、日付だけのときはその日の稼働時間帯の終わりとして数えます。
- 祝日と休みの日は区別しません(平日の祝日も稼働時間帯に入ります)。
- 完了から戻ったタスクは、完了を確認した時刻を消します。もう一度完了になったら、その時の XML の時刻が入ります。
- XML から消えたタスクは、最後に読んだ値のまま残します。
- 前に読んだものより古い XML(同じファイルで、更新時刻が前)を置いたときは、状態を変えずに注意を出します。管理ツールから書き出し直せば読みます。古い書き出しを使いたいときは `atlas-notes\tasks.json` を消すと初めから読み直します(完了を確認した時刻は消え、完了しているタスクは「完了の時刻が分からない」ものになります)。別のファイルを指したとき・読み方の設定を変えたときは、ふつうに読みます。
- 読み方の設定(`doneStatus` など)を変えたせいで完了になったタスクは、完了に変わるのを見たとしません(「完了の時刻が分からない」。完了日時の記録があれば、その日時を使います)。

送ったセッション(下の `upload-project.bat`)には、紐づいたタスクを添えます。送り先で集計すると、XML が無くてもタスクの節が出ます。ただし送り先の上に設定のフォルダ(`AtlasSettings`)を置いたときは、添えたタスクは使わず、集計する人が紐づけます(下の「[本番の置き方](#本番の置き方sessionlog-と-atlassettings)」)。

## プロジェクトのセッションをまとめて送る(upload-project.bat)

集計のプロジェクト(画面の「プロジェクト別」と同じ単位)ごとに、そのセッションの生ログを決めた場所へまとめて送れます。送り先には、プロジェクトごとに次の形で写します。同じセッションは置き換え、ほかのフォルダには触れません。

```
E:\dev\atlas-logs\owner_app\README.md                        プロジェクト名・写した日時・セッションの一覧(題名・最終更新・メモの有無)
E:\dev\atlas-logs\owner_app\<セッション ID>\events.jsonl など  セッションの生ログ
E:\dev\atlas-logs\owner_app\atlas-index.json                 プログラムや AI が読む索引(セッションごとの題名・日時)
E:\dev\atlas-logs\owner_app\atlas-installed.json             送った人がインストールしている skill・プラグインの名前(中身は送りません)
E:\dev\atlas-logs\owner_app\<セッション ID>\atlas-session.json そのセッションの題名・日時・プロジェクト名・送った atlas の版
E:\dev\atlas-logs\owner_app\<セッション ID>\atlas-memo.md     そのセッションのメモ(画像は atlas-memo\ に)
```

写すのは、送る前に集計し直したときに複製したログです。写したフォルダは `bin\atlas.exe all --home "E:\dev\atlas-logs\owner_app" --out out-owner-app` でそのまま集計できます(`--out` は集計するフォルダごとに分けます。いつもの `out` や別のフォルダを集計した出力先を指定すると、セッションが混ざるので書かずに止まります。集計が途中で止まった出力先でも同じです。プロジェクト名は送った PC で決めた名前のままです)。このとき、セッションごとの読みやすい記録(`<出力先>\sessions\<セッション ID>.md`。依頼・応答・ツールの経過をまとめた Markdown)もできます(記録は生ログから作れるので、送るものには含めません。送り先の容量を使わないため)。生ログには依頼文や応答、パスがそのまま入るので、写す先を見られる人を確かめてください。

前の版で送ったタスクタグのフォルダ(`<送り先>\<タグ名>\`)は、そのまま残ります。集計し直すこともできます(前の版が添えたタスクタグは読みません)。

0. (任意・最初に一度)送るプロジェクトを決めておきます。`atlas.bat` の画面の「プロジェクト別」の表で、送るプロジェクトの「まとめて送る」に印を付けます。印は `atlas.config.json` の `uploadProjects` に残り、外すと消えます。印があれば、bat は番号を聞かずに印のプロジェクトをまとめて送ります。
1. `upload-project.bat` をダブルクリックします。最新のログを集計し直してから、送るプロジェクトを出します。
   - 集計: 進み具合は 1 行で出し、経過の細かい行は窓に出さずに `%TEMP%\atlas-upload-project.log` に書きます(1 行ごとにその場で書くので、途中で窓を閉じてもそこまでの経過が残ります)。窓に出すのは、送るものに関わる「注意」(ログの一部を今回は複製できず、前回の複製を使った、など)と、失敗したときの理由です。ほかの注意(記録で伏せた文字列の数など)は経過のファイルにだけ書きます。集計の中で警告が出たときは、警告があったことと経過のファイルの場所を 1 行で出します。
   - 質問が出るまでに押したキー(文字も Enter も)は捨てるので、次の質問の答えにはなりません。この間に Ctrl+C を押すと、その場で終わります(「続行するには何かキーを押してください」に進みます)。
   - 印があるとき: 「画面で印を付けた N プロジェクトを送ります」と出し、番号は聞きません。ログが無くて送れないセッションがあれば、その数を出します。印の無いプロジェクトは送らず、その数と、最近更新した 3 件の名前を出します(新しく始めたプロジェクトを送るなら、画面で印を付けてください)。
   - 印が無いとき: プロジェクトの一覧(番号・セッション数・最終更新)を出すので、送るプロジェクトの番号を入れて Enter を押します。`1 3 5-8` のように複数選べます。当たらない番号を入れたときは、入れ直せます(やめるなら何も入れずに Enter)。
2. 送り先がまだ決まっていなければ、フォルダを選ぶ画面が開くので、送り先のフォルダ(例: `E:\dev\atlas-logs`)を選びます。選んだ送り先は覚えておき、次からは聞きません(`atlas.config.json` の `uploadRoot`。画面の「設定…」と同じ設定です)。
3. 「送る前の確認」に、送り先・セッション数・大きさ・秘密らしい文字列を出します(何プロジェクトかを送るときは、プロジェクトごとの 1 行と合計)。`y` = 送る、`n` = 今回だけ別のプロジェクトを番号で選び直す(印は変えません)、`c` = 送り先を変える、何も入れずに Enter = やめる、です。
4. 送っている間は、進み具合を 1 行で出し(書き換えるので行は増えません)、プロジェクトを 1 つ送るごとに結果を 1 行出します。最後に、送ったプロジェクト・セッションの数と送り先をまとめて出します。途中でやめたときは「途中でやめました」と、送っていない残りのプロジェクトを出します。

止まるとき・聞き直すとき:

- 前に送ったときから何も変わっていなければ、「前に送ったときから変わったセッションはありません」と出し、`y` = 送り先の一覧(`README.md` と索引)だけ書き直す、`n` = 選び直す、`c` = 送り先を変える、Enter = やめる、を尋ねます。
- 何プロジェクトかを送る途中で 1 つ送れなかった(送り先のファイルが開かれているなど)ときは、残りを送ってから、送れなかったプロジェクトと理由を出して止まります。もう一度実行すれば送り直せます(送ったものは置き換えるだけです)。途中で止まったとき(確かめ直す間に画面で集計し直し始めたなど)も、ここまでに送ったプロジェクトを出します。
- 一度に送るプロジェクトのうち、フォルダ名が同じになるもの(`owner/app` と `owner_app` など)があれば、混ざるので何も送らずに止まります。
- 覚えている送り先が見つからない(ネットワークドライブの切断・フォルダの削除)ときは、その場でフォルダを選び直せます。
- 確かめてから `y` を押すまでの間に、`atlas.bat` の画面で集計し直してログが変わったときは、写さずにもう一度確かめます(確かめていない中身を送らないため)。
- `atlas.bat` の画面で集計し直している最中は、送らずに止まります。終わってからもう一度実行してください。
- 前に送ったセッションを置き換えたとき、前のフォルダが送り先で開かれていて消せなかったら、その場所を出します。閉じてから手で消してください。
- 送れなかったプロジェクトがあるときも、確かめ直しでやめて送らなかった残りは「残りの N プロジェクトは送っていません」と分けて出します。
- 一覧の「ほかに、ログが無くて送れないもの」は、`session-store.db` にだけ記録が残っているセッションです(ログの本体が無いので送れません)。
- 送り先のフォルダに、フォルダ名が同じになる別のプロジェクト(か、前の版で送ったタスクタグ)がすでに送られているときは、混ざるので送りません(送り先を変えてください)。

### 2 回目からは変わったものだけを送る

`upload-project.bat`・`schedule-upload.bat` の自動送信は、前に送ったときから中身が変わっていないセッションを写し直しません。終わったセッションの中身はもう変わらないので、2 回目からは、続けて使っているセッションと新しいセッションだけを送ることになり、送るのが速くなります。

- **変わったかどうかの見方**: 送るたびに、各セッションのフォルダの `atlas-session.json` に中身の要約(`contents`)を残します。要約は、セッションのフォルダのファイルの名前・大きさ・更新時刻と、atlas が添えるもの(DB の行・メモの本文と画像)から作ります。次に送るとき、要約が同じで、送り先のフォルダのファイルの並びと大きさもそのままなら、写しません。
- **写し直すとき**: ログが書き足された・メモを書いた・DB の行が変わった、などで要約が変わったとき。送り先でファイルが消されたり足されたりしていたときも、写し直して元に戻します(送り先のフォルダを開いただけで OS や NAS が作るもの、`Thumbs.db`・`ehthumbs.db`・`desktop.ini`・`.DS_Store`・`._<名前>`(Mac)と、フォルダの `@eaDir`(Synology)・`.@__thumb`(QNAP)・`.AppleDouble` は数えません)。この版より前に送ったセッションは要約が無いので、初回だけ全部を写し直します。
- **題名・atlas の版だけが変わったとき**: ログは写し直さず、`atlas-session.json` と `README.md`・索引だけを書き直します。送り先で開かれているなどで書き直せなかったときは、送るのは止めずに、そのセッションを結果に出します(次に送るときにもう一度書き直します)。
- **デスクトップアプリのセッション**: プロジェクトを開いた日時・サイドバーの表示・ワークスペースの更新日時と最後の差分・通知の既読など、セッションの中身と関係なく変わる列は、要約に入れません(アプリでプロジェクトを開いただけで写し直さないため)。そのため、送り先の `atlas-session-store.json` のこれらの列は、そのセッションを次に写すまで古いままです。
- **送る前の確認**: 件数・大きさ・秘密らしい文字列は、今回写すものだけを数えます。変わっていないものは「前に送ったときから変わっていない N セッションは、送り先にあるものをそのまま使います(送りません)」と件数だけ出します(前に送ったときに確かめているため、中身を読み直しません)。確認の後に写すときは、確認のときに変わっていないと確かめたセッションの、送り先のファイルの一覧を読み直しません(NAS を 2 度読まないため。送り先は変えない前提です)。
- **送り先の一覧**: `README.md` と `atlas-index.json` には、今回写したものと、変わっていないので写さなかったものの両方を載せます。

送り先には `<送り先>\<プロジェクト名>\<セッション ID>\` の形で写します(プロジェクト名のフォルダ名に使えない文字は `_` にします。例: `owner/app` → `owner_app`)。空のセッションは送りません。

毎日決まった時刻に自動で送るなら、下記「[毎日自動で送る](#毎日自動で送るschedule-uploadbat)」で登録できます。

## 毎日自動で送る(schedule-upload.bat)

`upload-project.bat` を毎回手で実行しなくても、毎日決まった時刻に自動で送れます(1 日に何回かでも送れます)。Windows のタスク スケジューラに、自分のユーザーで動くタスクを 1 つ登録します(タスクの名前は `agent-session-atlas-upload`)。

先に決めておくこと(どちらも一度だけ):

- **送り先**: `upload-project.bat` を一度使うか、`atlas.bat` の画面の「設定…」で決めます。
- **送るプロジェクト**: `atlas.bat` の画面の「プロジェクト別」の表で、「まとめて送る」に印を付けます。自動で送るのは、印のあるプロジェクトだけです。

登録のしかた:

1. `schedule-upload.bat` をダブルクリックします。今の様子(登録の有無・送り先・印を付けたプロジェクト)と、自動で送るときの決まりを出します。
2. 送る時刻を入れて Enter を押します(例: `17:30`。何も入れずに Enter なら `18:00`。やめるなら `n`)。1 日に何回か送るなら、`12:00,18:00` のように `,` で区切って入れます(6 回まで。早い順に並べ、同じ時刻は 1 つにまとめます)。
3. 「今すぐ 1 回送って試しますか?」に `y` で答えると、その場で 1 回送り、終わるまで待って結果を出します。

自動で送るときの決まり:

- **送る前に、atlas を新しい版にします**(`git pull` と同じ。版が変わっていれば、`atlas.bat` と同じく、その版の `bin\atlas.exe` をこの PC でビルドします。`.bat` を開いたときにも同じ更新をします)。`atlas.bat` を開かなくても、新しい版で送れます。ただし、次のときは新しい版にせず、今の版のまま送ります(記録と、`schedule-upload.bat` の前回の結果に、理由とどうすれば新しい版になるかを出します):
  - atlas のファイルを手で変えている(`git status` に出る変更がある。`out\` や `atlas.config.json` のような git が管理していないファイルは見ません。`package-lock.json` だけが変わっているときは、npm が書き換えたものとして元に戻してから新しい版にします)
  - `atlas.bat` の画面や「集計し直す」・別のフォルダを開いた画面が動いている(動いているもののコードを入れ替えないため。次の回に新しい版にします)
  - `main` 以外のブランチにいる、または手元にだけあるコミットがある(早送りで新しい版にできない)。手元にだけあるコミットが無く、`main` の履歴が書き換えられた(force push)ために早送りできないだけなら、新しい `main` に合わせ直します
  - 新しい版を取りに行けない(ネットワークにつながっていないなど。次の回にもう一度試します)
  - この PC に、ビルドに要るもの(Node.js・Rust・Windows では C++ のビルドツール。上記「[atlas.exe の用意と更新](#atlasexe-の用意と更新)」)が無い。新しい版を取り込まず、今の `bin\atlas.exe` のまま送ります。自動で送るだけの PC でも、新しい版にするにはこれらが要ります。入れると、次の回から新しい版にします
  - 新しい版の `bin\atlas.exe` をビルドできなかった(前の版のコミットに戻し、今の `bin\atlas.exe` のまま送ります。実行ファイルは置き換えていないので、ビルドに頼らずに送れます。同じコミットは 1 日に 1 回まで試し、もっと新しいコミットが出たらそれを試します。経過は `bin\build.log`)
  - コミットは最新でも、`bin\atlas.exe` が今のソースから作ったものでなければ(手で `git pull` したときなど)、`bin\atlas.exe` をビルドし直します。その回は、もう動いている前の版のまま送り、新しい `bin\atlas.exe` は次の回から使います。ビルドに要るものが無ければ、今の `bin\atlas.exe` のまま送ります
- **新しい版がその PC で動かなかったとき**(読み込みで止まるなど、結果を残さずに終わったとき)は、前の版のコミットに戻し、`bin\atlas.exe` も置き換える前のもの(`bin\atlas.prev.exe`)に戻します(ビルドはしません)。その回は、もう動いている前の版がそのまま送ります。その版は `out\auto-update.json` に覚え、もっと新しい版が出るまで使いません。コミットを戻せなければ、Windows の通知で知らせます。
- 決めた時刻になるたびに、窓を出さずに最新のログを集計し直してから、印のあるプロジェクトを送り先へ送ります。中身は `upload-project.bat` と同じです(`<送り先>\<プロジェクト名>\<セッション ID>\`)。前に送ったときから変わっていないセッションは写し直しません(上記「[2 回目からは変わったものだけを送る](#2-回目からは変わったものだけを送る)」)。
- その時刻に PC が止まっていたら、次に PC を使い始めたときに送ります。ログオンしている間だけ動きます(NAS やネットワークドライブへ、いつもの資格情報で書けるように)。電池で動いているときも送ります。
- **送る前の確認は出しません**。秘密らしい文字列があっても送り、その数を結果に残します。送り先を見られる人を、登録の前に確かめてください。
- 印の無いプロジェクトは送りません。新しく始めたプロジェクトは、画面で印を付けてください(印の無いもののうち最近更新したものの名前を、記録に残します)。
- `atlas.bat` の画面で集計し直している最中なら、終わるまで待ってから始めます(1 時間待っても終わらなければ、その回は送りません)。
- 送れなかったときは、Windows の通知で知らせます。送り先が見つからない・印が無いなど、尋ねないと進めないときも、何も送らずに通知します。

登録した後にもう一度 `schedule-upload.bat` を開くと、送る時刻・次の回・前回の結果(送ったプロジェクトとセッションの数、送れなかった理由)を出します。そこで `t` = 時刻を変える(Enter だけなら今の時刻を全部そのまま。1 日 1 回に戻すときは時刻を 1 つだけ入れます)、`s` = 今すぐ 1 回送る、`u` = 送る前に atlas を新しい版にするかを切り替える(既定はする)、`d` = 自動で送るのをやめる(登録を消す。送ったものは残ります)を選べます。前回、atlas を新しい版にしたとき・できなかったときは、その結果も出します。Node.js で動いていたころ(atlas.exe より前の版)に登録したタスクも、そのまま送れます(前の版の入口 `packages\cli\src\upload-auto.ts` が `bin\atlas.exe` を動かします)。`schedule-upload.bat` を開くと、時刻と自動更新の設定はそのままで、`bin\atlas.exe` を直接動かす形に登録し直します。

結果は `out\auto-upload.json`、経過は `out\auto-upload.log`(集計の経過は `out\auto-upload-aggregate.log`)に、回ごとに書き直します。登録はタスク スケジューラ(`taskschd.msc`)でも見られます。窓を出さずに動かすため、タスク スケジューラの「前回の実行結果」はいつも成功(0x0)と出ます。送れたかどうかは `schedule-upload.bat` か `out\auto-upload.json` で確かめてください。

Windows 以外では登録できません。cron などから `bin/atlas upload-auto` を動かすと、同じことをします(送る前に atlas を新しい版にしないなら、後ろに `--no-update` を付けます)。

## アップロードされたセッションを集計する(別のフォルダを開く)

いつもの画面(この PC のセッション)とは別に、アップロード先のフォルダを選んで集計し、新しいタブで開けます。この PC の集計はそのまま残ります。

送り先が人ごとに分けてあるとき(`<送り先>\<名前>\<プロジェクト>\<セッション ID>\`)は、選ぶフォルダで集計する範囲が決まります。

| 選ぶフォルダ | 集計する範囲 |
|---|---|
| `<送り先>`(例: `\\server\share\log`) | 全員の分(2 段下まで読みます) |
| `<送り先>\<名前>` | その人の分 |
| `<送り先>\<名前>\<プロジェクト>` | そのプロジェクトの分 |

`<送り先>` を選んで開いたレポート(全員の分)には、絞り込みに「人」が、内訳に「人別」の表が加わります(`<名前>` のフォルダごとの集計。名前を押すとその人に絞り込みます)。人のフォルダやプロジェクトのフォルダを選んだとき、この PC の集計には出ません。

1. `atlas.bat` で開いた画面の右上の「別のフォルダを開く…」を押します。
2. 「エクスプローラーで選ぶ…」でフォルダを選ぶか、フォルダのフルパスを入れて「調べる」を押します。何を読むか(例: 「下のフォルダ 2 件をまとめて集計します」)が出ます。集計できないフォルダなら、理由が出ます。
3. 「集計して開く」を押します。集計が終わると、新しいタブで開きます(一覧の「表示する」からも開けます)。開いた画面は、上部に「対象: <フォルダ名>」と出ます。
4. 一度開いたフォルダは「開いたことのあるフォルダ」に並ぶので、次からは「集計して開く」を押すだけです(開くたびに集計し直します)。

**初めからフォルダを選んで開く(open-folder.bat)**: いつもの画面を開かずに、アップロード先のフォルダだけを見たいときは、リポジトリ直下の `open-folder.bat` をダブルクリックします。フォルダを選ぶ画面(エクスプローラーの「フォルダーの選択」)が出るので、上の表のどれかのフォルダを選ぶと、集計してブラウザで開きます。2 回目からは、前に開いたフォルダの場所で選ぶ画面が出ます。

- フォルダを `open-folder.bat` に重ねて離す(ドラッグ アンド ドロップ)と、選ぶ画面を出さずにそのフォルダを開きます。
- 選ぶ画面で「キャンセル」を押すと、何もせずに終わります。集計できないフォルダを選んだときは、理由を出して止まります(何も書きません。もう一度 `open-folder.bat` を実行してください)。
- 出力先は、画面の「別のフォルダを開く…」で開いたときと同じ場所です(同じフォルダなら、どちらから開いても同じレポートになります)。この PC の集計(`out\`)には触れません。
- 2 回目からは速く開きます: フォルダは毎回読み直しますが、変わっていないファイルは写し直さず、前に開いたときから何も変わっていなければ、レポートも作り直さずにそのまま開きます(必ず作り直したいときは、開いた画面の「集計し直す」)。
- 黒い窓は、ブラウザのタブを閉じるまで残ります(閉じるとサーバも止まります。`atlas.bat` と同じです)。

- **開いた画面は読むだけです**(上部に「読むだけ」と出ます)。メモは、送った人が付けていたもの(送った時点のもの)を出し、この画面では書き換えません。「集計し直す」と「判定する…」は使えます(この PC の出力先に書くだけで、送り先は書き換えません)。設定のフォルダ(`AtlasSettings`)を使うときは、判定は設定のフォルダに書いて集計する人のあいだで共有し、管理ツールのタスクの紐づけもこの画面で行います(下の「本番の置き方」)。
- 集計の出力は、いつもの `out\` には混ぜず、フォルダごとに `out-folders\<フォルダごとの名前>\out\` に置きます(フォルダごとの名前は、フォルダ名とパスから決まります)。
- 開いたタブを閉じると、そのフォルダのサーバは止まります(いつもの画面と同じ決まりです)。画面から開いたときのサーバには黒い窓が無いので、手で止めるときは `stop.bat` を使います(上記「[atlas を止める](#atlas-を止めるstopbat)」。`atlas.bat` を開いたときも、集計などが動いていなければ止めます)。「一覧から外す」は一覧から消すだけで、集計の出力とメモは残ります。
- 同じ id のセッションが何人かのフォルダにあるときは、`events.jsonl` が大きいほうだけを数えます。
- コマンドでも開けます: `bin\atlas.exe open "\\server\share\log\<名前>"`、選ぶ画面から選ぶときは `bin\atlas.exe open --pick`([docs/cli.md](docs/cli.md#別のフォルダを開くopen))。
- 生ログには依頼文や応答、パスがそのまま入っています。集計の出力(`out-folders\`)も、見られる人を確かめて扱ってください。

操作の細かい決まりは [docs/screen.md の「別のフォルダを開く」](docs/screen.md#別のフォルダを開く) にあります。

## 本番の置き方(SessionLog と AtlasSettings)

チームで使うときは、共有の場所に 2 つのフォルダを並べて置きます。

```text
\\server\share\
  SessionLog\                    全員がセッションを送るアップロード先
    alice\<プロジェクト>\<セッション ID>\
    bob\<プロジェクト>\<セッション ID>\
  AtlasSettings\                 集計の設定と、管理ツールが書き出したタスクの XML
    atlas.config.json
    tasks.xml
    tasks.json                   (atlas が作る: タスクの状態)
    task-links.json              (atlas が作る: セッションとタスクの紐づけ)
    judgments.json               (atlas が作る: 工数の判定。集計する人のあいだで共有)
    turn-judgments.json          (atlas が作る: 依頼ごとの判定。同じく共有)
    tasks.json.lock など          (atlas が作る: 書くときのロック。消さずに置いておきます)
```

- `SessionLog`: 送る人は、`upload-project.bat` や `schedule-upload.bat` の送り先(`uploadRoot`)を `\\server\share\SessionLog\<自分の名前>` にします。送る人の PC での紐づけと送り方は、今までと変わりません。
- `AtlasSettings`: 集計の設定 `atlas.config.json` と、管理ツールが書き出した XML を置きます。名前は `AtlasSettings` に決まっています(開いたフォルダから上へ探すときの名前)。

`AtlasSettings\atlas.config.json` の例(相対パスは、この設定ファイルのフォルダから見ます):

```json
{
  "tasks": {
    "file": "tasks.xml",
    "doneStatus": ["Done", "完了"],
    "workHours": { "days": [1, 2, 3, 4, 5], "start": "09:00", "end": "18:00" }
  }
}
```

**集計する人の開き方**: `open-folder.bat` で `SessionLog`(か、その中の人やプロジェクトのフォルダ)を選びます。atlas は、開いたフォルダから 1 段ずつ上がり、`<そのフォルダ>\AtlasSettings\atlas.config.json` があればそれを使います(ドライブや共有の根まで上がります。`\\server\share\SessionLog\alice` を開いても `\\server\share\AtlasSettings` が見つかります)。開いた画面の上部に「設定: AtlasSettings」と出ます(マウスを重ねるとフルパス)。「別のフォルダを開く…」で調べたときも、使う設定のフォルダが出ます。

- 使う設定のフォルダは、`--settings <フォルダ>` で指したもの → そのフォルダを前に開いたときに使ったもの → 上へ探して見つけたもの、の順に決めます。どれも無ければ今までどおりです(タスクは送った人の記録を読むだけ)。別の場所に置いたときは、`bin\atlas.exe open "<フォルダ>" --settings "<設定のフォルダ>"` で一度開けば、次からは `open-folder.bat` でも同じ設定のフォルダを使います。
- 集計(画面の「集計し直す」と、判定を取り込んだ後の作り直しも)は、`AtlasSettings\atlas.config.json` を設定として読みます(`--config` や `ATLAS_CONFIG` より先に使います)。稼働時間帯(`workHours`)もここのものです。効くキーと効かないキーは、下の「[共有の設定で効くキー](#共有の設定で効くキー)」にあります。
- 開いた画面の「設定…」で wiki や工程名を変えると、`AtlasSettings\atlas.config.json` に書きます。ほかの集計する人の結果も変わるので、ダイアログにそのことが出て、ボタンも「共有の設定に保存」などになります。書き換えたことは黒い窓のログに 1 行残ります。

**判定は共有します**: 設定のフォルダを使うときは、工数の判定(`judgments.json`)と依頼ごとの判定(`turn-judgments.json`)を、いつも `AtlasSettings` に置きます(設定に `tasks` が無くても同じです)。集計する人や開いたパスが違っても(`SessionLog` と `SessionLog\alice`、UNC のパスと割り当てたドライブ)、同じ判定を使います。

- 取り込み(画面に貼る・ZIP の返答・M365 Copilot・`judge import`・`turns import`)は、ファイルのロックを取って読み直し、セッションごと(依頼ごとの判定はセッションと依頼番号ごと)に混ぜて書きます。同じものは、後から取り込んだものに置き換えます(前の値は残しません)。ほかの人が取り込んだ別のセッションの判定は消えません。
- 判定済みかの判断(`--unjudged` の束・画面の未判定の数)、レポートに入る判定、タスクの「AI を使わなかった場合の工数」は、どれも共有の判定から数えます。ほかの人が判定を取り込むと、次に開いたときに作り直します(前に開いたときから判定のファイルが変わっていれば、使い回しません)。
- 前に開いたフォルダの出力先(`out-folders\<名前>\out\`)に判定があったときは、初めて共有の置き場を使うときに混ぜて移します。共有の側にあるセッションは共有の側のままにし、無いものだけを足します(判定に失敗した記録は、セッションごとに 1 つにします)。前のファイルは `judgments.json.moved-<日時>` などに名前を変えて残し(前に移したものを上書きしません)、移したことを黒い窓に 1 行出します。
- 設定のフォルダを使うのをやめると(`AtlasSettings` を消した・別の場所に移した・`--settings` で指さなくなった)、判定は開いたフォルダの出力先に戻りますが、出力先の判定は移したときに名前を変えてあるので、**出力先には判定が無い状態**になります。続けて使うときは、`AtlasSettings\judgments.json` などを出力先に写してください。
- 判定には、依頼の要約(`taskSummary`)、推定の根拠、依頼ごとの判定の理由(`note`)が入ります。依頼の内容が読み取れることがあるので、`AtlasSettings` を見られる人を確かめてください。
- 設定のフォルダが無いときは、今までどおり開いたフォルダの出力先に置きます(集計する人ごと・開いたパスごとに別の判定です)。

**人の軸**: 絞り込みの「人」と内訳の「人別」の表は、`SessionLog` の根を開いたときだけ付きます。人のフォルダ(`SessionLog\alice`)やプロジェクトのフォルダを開いたときは付きません(判定とタスクの紐づけは、どちらで開いても同じものを使います)。

**AI の変更の残存**: 送り先から集計するときは、送った人の PC が照合した結果(セッションごとの `atlas-vcs.json`)を読みます。比べる版(`vcs.mode`・`vcs.lagDays`)は、全員の送る側の PC の `atlas.config.json` でそろえてください。共有の設定の `vcs.mode`・`vcs.lagDays`・`vcs.pathMap` は、送り先の集計には効きません(照合し直さないため)。

#### 共有の設定で効くキー

`AtlasSettings\atlas.config.json` を読んで送り先を集計するときに、効くキーと効かないキーです。

| キー | 効くか | 使うところ |
|---|---|---|
| `tasks`(`file`・`item`・`id`・`name`・`status`・`doneStatus`・`doneAt`・`workHours`) | 効く | タスクの状態・紐づけ・工数 |
| `wikis` | 効く | llm-wiki の参照の数え方(集計のとき) |
| `phases` | 効く | 依頼ごとの判定の束と取り込みの工程名(画面のジョブと、`--settings` か開いたフォルダの出力先を指したコマンド) |
| `vcs.labels`・`vcs.note` | 効く | 「AI の変更の残存」の状態の名前と、節の説明の一文 |
| `judgeModel` | 効く | `skill-draft` に使うモデル(判定はツールの中では回しません) |
| `vcs.mode`・`vcs.lagDays`・`vcs.pathMap` | 効かない | 送り先では送った人の PC の照合結果を読むため。比べる版は送る側の設定でそろえます |
| `uploadRoot`・`uploadProjects` | 効かない | 送る側の PC の設定(送り先と、まとめて送るプロジェクト)。集計する画面は読むだけなので書き換えもしません |

**新しいキーを足す前に、全員の atlas を更新してください**: atlas は、設定ファイルに知らないキーがあると止まります(書き間違いを黙って無視しないためです)。共有の `atlas.config.json` に新しいキー(`tasks.doneAt` など)を足すと、そのキーを知らない前の版の atlas で開いた集計する人は、設定を読めずに止まります。キーを足す前に、`AtlasSettings` を使う全員の atlas を、そのキーを読める版に更新してください。

**タスクの紐づけの束(版 2)も、全員の atlas を更新してから使ってください**: この版の `tasks bundle` が作る束(`task-bundle/`・`task-bundle.zip`)は版 2 で、候補の ID を `manifest.json` から `candidates.json` に分けています。前の版の atlas は版 2 の束を読めず、取り込み(`tasks import`・画面の「判定する…」・M365 Copilot の自動操作)で止まります。束を作る人と取り込む人が違うとき、同じ出力先を前の版の atlas でも開くときは、先に全員の atlas をこの版に更新してください(この版は、前の版が作った版 1 の束も読めます)。

**タスクの紐づけは集計する人が行います**: 設定に `tasks` があれば、集計のたびに XML を読んでタスクの状態を更新し、機械の紐づけを決め直します(この PC で集計するときと同じ決まり)。タスクの状態と紐づけは `AtlasSettings\tasks.json`・`AtlasSettings\task-links.json` に書きます。送った人が添えたタスクの記録は使いません。

- 開いた画面は、メモについては読むだけのままですが、タスクの紐づけは変えられます: 「判定する…」の「タスクの紐づけ」(LLM。束は開いたフォルダの出力先 `out-folders\<名前>\out\task-bundle\` に作ります)と、詳細ページの手動の紐づけです。
- コマンドでは、`open` が出す出力先を `--out` に指します(例: `bin\atlas.exe tasks bundle --out out-folders\SessionLog-xxxxxxxx\out`。設定のフォルダは開いたときの記録から決まります。[docs/cli.md の「設定のフォルダ」](docs/cli.md#設定のフォルダ--settings))。

**複数人で同じ設定のフォルダを使うとき**:

- 何人かの集計する人が同じ `AtlasSettings` を使えます。`tasks.json` と `task-links.json` は、書くたびにファイルのロックを取って読み直し、変えたところだけを書きます(同時に書いても、どちらの変更も残ります)。紐づけはセッション ID ごとなので、人のフォルダだけを開いた人と、全員の分を開いた人が書いても混ざりません。
- 機械の紐づけを決め直すのは、開いたフォルダにあるセッションだけです。手動と LLM の紐づけは、ほかの人の分も消しません。同じセッションを何人かが手で直したときは、後から保存したものが残ります。
- 開いた画面は、開いたときか「集計し直す」のときの紐づけを出します。ほかの人が後で紐づけを変えたら、「集計し直す」か、`open-folder.bat` で開き直すと出ます(前に開いたときから XML・タスクの状態・紐づけのどれかが変わっていれば、作り直します)。
- XML を読めないときは、前に読んだタスクの状態のまま続け、画面に注意を出します(この PC での集計と同じです)。設定のフォルダの `atlas.config.json` を読めないとき(共有がつながっていないなど)は止まります(送った人の記録に黙って戻しません)。
- `AtlasSettings` に入るのは、タスクの ID・名前・状態と、セッション ID ごとの紐づけと理由です。LLM の紐づけの理由には、依頼の内容が短く入ることがあります。見られる人を確かめて置いてください。

## 集計する人の手順

`SessionLog` と `AtlasSettings` を置いた後([本番の置き方](#本番の置き方sessionlog-と-atlassettings))、集計する人が行う順番です。判定はどれも外部の LLM が行い、atlas は渡すファイルを作って返答を取り込むだけです。

1. **開く**: リポジトリ直下の `open-folder.bat` をダブルクリックし、`SessionLog` を選びます(全員の分。人のフォルダを選ぶとその人の分)。開いた画面の上部に「設定: AtlasSettings」と出ていれば、設定のフォルダが見つかっています(マウスを重ねるとフルパス)。出ていないときは、`bin\atlas.exe open "<SessionLog>" --settings "<AtlasSettings>"` で一度開きます([別のフォルダを開く](#アップロードされたセッションを集計する別のフォルダを開く))。
2. **タスクの紐づけ**: 機械の紐づけは開いたときの集計で決まります。決まらなかったセッションは、画面右上の「判定する…」で「タスクの紐づけ」を選び、「ZIP にまとめてエージェントに渡す」か「チャットに貼って判定する」(M365 Copilot の自動操作もここ)で LLM に選ばせ、返答を取り込みます。取り込むとレポートを作り直します。違っていたら詳細ページの「タスク」の行の「変える…」で直します([紐づけ](#管理ツールのタスクと工数任意)・[docs/judge.md の 4](docs/judge.md#4-管理ツールのタスクへの紐づけ))。コマンドでは `bin\atlas.exe tasks bundle --out <出力先>` → `tasks import <ファイル> --out <出力先>`(出力先は `open` が出したもの)。
3. **工数の判定**: 「判定する…」で「工数」を選び、同じ方法で判定させて取り込みます。タスクの「AI を使わなかった場合の工数」になります([推定人手工数](#推定人手工数任意))。コマンドでは `bundle --unjudged` → `judge import <ファイル>`(M365 Copilot は `judge m365`)。
4. **依頼ごとの判定**: 「判定する…」で「依頼ごとの採用」を選び、判定させて取り込みます(任意)。採用率だけを見るなら先頭のファイルで止められます。1 セッションの先頭 200 依頼までが対象で、超えた分の数は「工程と詰まり」の「採用(LLM の判定)」に出ます([依頼ごとの採用](#依頼ごとの採用任意))。コマンドでは `turns bundle --unjudged` → `turns import <ファイル>`(`turns m365`)。
5. **見る順**:
   1. 全体サマリの表紙の「タスクの所要」(比べられる完了タスクの 3 つの時間)。
   2. 「管理ツールのタスク」の節: タスクごとの 2 つの工数・AI の実働と、比べない理由。右側の詰まりの列(人数・主なモデル・摩擦・依頼の判定)で、時間のかかったタスクの事情を見ます。列の見出しで並べ替えられます。
   3. 「比べる」の節: 単位に「モデル」「推論強度」「wiki の参照」を選んで並べ、人の記録が 2 人以上あれば下の「人ごとの差」も見ます。AI の変更の残存の行は、開始時の基準(記録・推定)と比べた版の内訳、照合不可の理由と一緒に読みます(比べた版が混ざった側の割合は出しません)。推論強度は [推論強度どうしを比べる](#推論強度どうしを比べる) の手順で集めたものを使います。
   4. 「工程と詰まり」の節: 工程ごとの詰まりと、依頼ごとの判定の採用・合わなかった点。
   5. 「人別」の表: 人ごとの量と、依頼ごとの判定(判定した依頼・採用率・直しの割合・合わなかった点のいちばん多いもの)。
   6. 目次の付録の「失敗の台帳の集計」(`failures.html`): ツールの失敗と拒否の理由。
6. **複数人で集計するとき**: 判定とタスクの紐づけは `AtlasSettings` で共有します。同じセッションを何人かが判定すると、後から取り込んだものが残ります。作業を分けるときは、人のフォルダ(`SessionLog\<名前>`)ごとに開いて分担すると重なりません。ほかの人の取り込みは、「集計し直す」か開き直すと出ます。共有の設定に新しいキーを足す前と、タスクの紐づけの束(版 2)を使う前は、全員の atlas を更新してください([複数人で同じ設定のフォルダを使うとき](#本番の置き方sessionlog-と-atlassettings))。

取り込んだ後の作り直しは、既定の記録の出し方で作ります(`--full` などと絞り込みは引き継ぎません。[推定人手工数](#推定人手工数任意) の「取り込んだ後のレポートの作り直し」)。

## 推論強度どうしを比べる

何人かで推論強度(例: medium と xhigh)を週ごとに入れ替えて使い、結果を比べるときの手順です。比べるのは、送り先の全員の分を開いた画面の「比べる」の節で、単位に「推論強度」を選びます(モデル・A と B の強度・期間を選びます)。

1. **比べる人はそれぞれ、自分の PC の `atlas.config.json` で、比べる版を `fixed` にします**(既定は `worktree`)。AI の変更の残存は送る側の PC で照合するためです。`fixed` は「セッションの終わりから `lagDays` 日後(既定 7 日)の版」と比べるので、古いセッションと新しいセッションを同じ条件で比べられます(`worktree` は照合した日の作業ツリーと比べるので、古いセッションほど後から人が手を入れた分が混ざります)。

   ```json
   { "vcs": { "mode": "fixed", "lagDays": 7 } }
   ```

2. **強度を切り替えたら、新しいセッションで始めます。** 本体のリクエストの 90% 以上が同じ強度のセッションだけを数え、途中で切り替えたセッションは「混在」として比べる対象から外します(件数は表の下に出ます)。サブエージェントの強度は数えません。
3. **作業の結果は 7 日以内(`lagDays` の日数以内)にコミットします。** 比べる版までにコミットされていない行は「見つからない」と数えます。セッションの後に 1 件もコミットが無いときは、比べる版が開始時と同じになるので「照合不可(開始時から取り込まれた変更が無い)」にして、割合に入れません。

表の下の「利用者 × 週」の表で、割り当てどおりの強度で使われたかを確かめられます。差の幅(95%)は、同じ人のセッションの似かたを入れていない近似なので、実際の幅はこれより広くなります(画面の説明と、用語の説明のページ `out\glossary.html` の「差の幅」)。
